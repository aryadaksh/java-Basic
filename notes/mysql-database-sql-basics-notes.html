Where We Are — The Standalone Application Problem
  • So far we developed applications that were standalone: you run it, it performs some activity, then it shuts down. Run it again and it starts from the beginning.
  • Think of an application that takes your order and, once the order is paid, delivers it to your doorstep.
  • So far we were not able to save data. The application used an in-memory mechanism — the collection classes (List, Set, Map) — to hold data.
  • When the application completes or you shut it down, that data is destroyed.
  • But when the user comes back next time, he should know how many orders he placed and see his transaction history — we couldn't do that.
What a Database Gives You — Permanent Storage

A database lets you store data permanently. "Permanently" means: you shut down your system, you shut down your application, and when you start again the data is still available.

Many Databases, Learn a Few
  • There are hundreds of databases in the market. You don't need to learn all of them — learn one, two or three. Every database has its own books/learning material.
  • A real application uses many different databases — the instructor said 10 to 15, and that Amazon might use 20–30 (rough figures from class). Each one has its own purpose. Don't think Amazon runs on a single database.
Starting With a Relational Database — MySQL
  • We start with a relational database: MySQL. From today onward, our program will interact with a database.
  • For learning, you install the database locally on your own system.
  • In a company it's different: a team installs the databases on some other machine and gives you the host name, user ID and password; you just connect.
  • Relational basics (a subject you had in engineering): a database has tables, and a table has fields (columns).
  • Your program interacts with the database, and the database stores data permanently — if you shut the application down and start it again tomorrow, you can read the data back.

Who Talks to Whom — The Amazon Example

  • Read: I search for "iPhone 18 Pro" → my request goes to the Amazon backend platform ("can you give me the result for this?") → the backend connects to the database, reads the data and returns the result.
  • Write: when I place an order or add to cart, the backend writes to the database.

Real-world applications have databases attached — and multiple databases, not only one. The instructor's view: "without databases you cannot even work for a day", apart from some small utilities. Enterprise applications always have them.

SQL — The Language the Database Understands
  • To give instructions to a computer, you use a programming language. To give instructions to a database, you use SQL — Structured Query Language.
  • A database doesn't understand Java. It has its own language: SQL.
  • As a Java backend engineer you must know the minimum of SQL; becoming an expert in SQL is a separate stream that takes another couple of months.
  • If you don't know SQL: first learn the basic concepts — what is a table, a database, a foreign key, a primary key, data types. The instructor mentioned an online portal/course called "Namaste SQL" for the basics (spelling uncertain in the transcript), and suggested using ChatGPT to learn SQL today.
  • His expectation: about 10% of SQL query knowledge — what a table, database, relationship, composite key, foreign key, primary key and data type are; indexing will come as the course moves forward. You'll write queries every day, so learn alongside.
MySQL Server and MySQL Client
  • MySQL comes with a MySQL server and a MySQL client. Installing the server asks you to install the client as well.
  • The server is a Windows service — it's up and running automatically when your Windows machine starts. You don't have to start it.
  • The client is what you open to connect to the database and give instructions: read or write instructions ("insert data", "give me data"), and you get a response back.
  • In the instructor's diagram, both are on one machine (his computer): a database symbol (the cylinder used to represent a database) and the MySQL client.
  • The client is just a kind of UI. The server stores the data — it holds the tables and all the data. Same as Amazon: the app is the client/UI; the request goes to the Amazon server (backend), then to the database. Client and server are both running on the backend system, and you interact through the client.
localhost, Host, User, Password, Port — and the Connection
  • If you connect from the same computer the database runs on, you're connecting to localhost — the host of the same computer.
  • To connect, the client needs the host, username, password and port.
  • Using these you create a connection — "this client is connected to the database".
  • Analogy: to talk to a friend over the phone you dial a number; it connects to the nearest tower, then onward through other towers. Without a connection you cannot communicate at all.
Connecting From the Command Prompt

Instead of the client window, open CMD and type mysql -u root -p (-u = user; the instructor's user was root), then enter the password you set. Now this CMD window is connected to the database, and you can send instructions written in SQL — the language the database understands.

The Hierarchy — Server → Databases → Tables → Columns
  • The database server contains databases; a database contains tables; a table contains columns (fields).
  • A database is a name under which you segregate data — an order database, a payment database, etc.
  • Under the order database you might have tables such as order history, order failed, order passed, order unpaid, order canceled.

Data Really Is Persistent — The Client Is Just a UI

The instructor closed the client, then started it again with mysql -u root -p and the password, ran show databases, selected his database with use, ran show tables — and the table and its data were still there. Don't think the data lives in the client: the data is stored inside the MySQL database (server), which is why you can see it again. That is permanent storage in action.

Reading Only What You Need — Filters and Columns
  • Filter rows with where: to see only the paid orders, add where status = 'paid' to the select — in the demo that returned the only one paid record.
  • Pick columns: instead of select *, name just the fields you want — e.g. item name and price — and only those come back.
  • Why: a real-world table might have 200 columns; you don't need to read everything — only the columns you're interested in.
Primary Key
  • A primary key uniquely identifies a particular record. You choose it while creating the table. (The demo table had no primary key yet.)
  • If you declare a column as the primary key and mark it auto increment, the database server increases the ID automatically — so while inserting you don't have to supply the ID again and again.
Foreign Key

The primary key of one table sits inside another table as a reference — that is a foreign key. It is the connection / parent-child relationship you create between tables. The instructor noted that these fundamentals were already taught in one engineering semester, and now is the right time to revise them.

Audit Columns — Always Add Them
  • Whenever you create a table, include audit columns — as part of the database design. Examples he gave: created date (when the record was created), updated date (when it was updated), and when it was deleted; the transcript also lists status among them.
  • Why? Without them, you don't know who updated a record — the user, the system, or somebody else.
  • Debugging story: a profile shows as deleted. Maybe the user himself asked to deactivate it; maybe a friend did it, and the person is calling the call centre saying "my data got deleted". With audit columns you can investigate. If your code marks, at delete/deactivate time, that it was deleted by the user (with the person's name), you can say: "the request came from your mobile — we don't know where your mobile was, but the request to deactivate came from your account."
  • Without audit columns, investigation is really tough — you can't tell who deleted what.
Client vs Server (Q&A) and the Workbench Advice
  • MySQL client and MySQL server: the server stores the data (tables, all data); the client is only the UI through which you interact with MySQL.
  • Workbench: there is also a MySQL Workbench tool, but the instructor said please do not install it for now — he said it would slow down your system (and noted it "corrects queries automatically" — part of that remark is garbled). Start with the command prompt (CMD).
💡 Added clarification — terms and details the lecture didn't spell out:
  • Read/write is often called CRUD: Create, Read, Update, Delete. In SQL: insert = create, select = read, update = update, delete = delete. "Write" in the lecture covers insert, update and delete.
  • delete vs drop vs truncate: delete removes rows (all rows if there is no where); drop table removes the table itself; truncate table quickly empties all rows. In the transcript the instructor says the delete command "can delete the table as well" and also shows deleting data — the recording doesn't make clear whether he deleted one row or all rows (data is present again later in the demo), so check these three statements yourself.
  • Always use where with update and delete: without it, every row is changed or removed. A safe habit is to run a select … where … first and reuse the same condition.
  • Syntax details: SQL keywords aren't case-sensitive; text values go in single quotes ('paid'); a table name can't contain spaces, so "order history" becomes order_history.
  • Data types: varchar(100) = variable-length text up to 100 characters. For money, decimal(10,2) is usually preferred over floating-point types like double because of rounding errors.
  • Composite key: a primary key made of two or more columns together. The lecture only listed the term.
  • Auto-increment syntax: id int primary key auto_increment. Auto-generated IDs come from the server, so you leave id out of the insert.
  • Foreign key syntax: foreign key (customer_id) references customer(customer_id) — and the referenced (parent) table must exist first.
  • Typical audit columns: created_date, created_by, updated_date, updated_by, and for deletions deleted_date, deleted_by or a status/flag column. Marking a record as deleted instead of physically removing it is called a soft delete — it is what makes "who deleted this?" answerable.
  • Port and JDBC (preview): MySQL's default port is 3306, and root is the default administrator account. The lecture didn't give the port number; tomorrow's JDBC topic is where host/port/user/password get used from Java, typically in a URL like jdbc:mysql://localhost:3306/<database>.

📌 Lecture Takeaways

  • Standalone apps with collections lose data on shutdown; databases store data permanently.
  • Learn one to three databases; real applications use many, each with its own purpose.
  • We start with the relational database MySQL, installed locally; in companies you get host, user ID and password.
  • Every system divides into read and write; the application does both against the database.
  • The database understands SQL, not Java; a Java backend engineer needs at least basic SQL (~10%).
  • MySQL = server (stores data, always running) + client (UI); you connect with host, user, password, port.
  • Structure: server → databases → tables → columns.
  • Commands: show databases, create database, use, show tables, create table, describe, select, insert, update … where, delete; end with a semicolon.
  • Use where to filter rows and name columns to read only what you need.
  • Primary key uniquely identifies a record (auto increment generates IDs); a foreign key links tables.

🚧 Common Interview Traps

  • "Collections are fine for storing data." Only while the application runs; they're not permanent.
  • "One database per application." Real systems use many databases for different purposes.
  • Thinking data lives in the client. It's in the server; closing the client changes nothing.
  • Forgetting the semicolon — the command won't execute.
  • Forgetting use <database> — your table could end up in (or be searched in) the wrong database.
  • select * everywhere. Read only the columns you need.
  • Update/delete without where. Added It affects every row.
  • Mixing up delete, truncate and drop. Added
  • Skipping audit columns — you'll be unable to say who changed or deleted data.
  • Skipping the MySQL installation — tomorrow's JDBC session depends on it.
