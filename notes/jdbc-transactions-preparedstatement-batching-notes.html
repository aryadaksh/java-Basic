🔁 Class 1 — Transactions: Commit and Rollback

Why Take JDBC Seriously

The instructor's push: understand JDBC properly, because every program ends up interacting with a database. Later tools — Hibernate and Spring Data — use JDBC internally; JDBC needs a lot of code while Hibernate automates much of it (and is easy to start with, "one program in half an hour"). Skipping JDBC means you can write programs but don't know what happens internally.

Why a Transaction? — The Order-Placement Scenario

Placing an order is not one query. The application updates the orders table with status created → initiates payment (a hit to a third party) → confirms payment and marks the order paid → maybe applies a reward such as free delivery on the first order, which updates a delivery charge to 0 somewhere. Each is an individual query.

If one step fails, the earlier ones must be undone too. Otherwise the order exists but the payment failed — and anyone pulling a report gets wrong data. This is a database concept (commit and rollback), not something specific to JDBC.

Commit and Rollback — Data Doesn't Go Straight to the Tables
  • Don't assume the data you write is stored permanently at once — you might make an accidental update. If every write were permanent, that would be a problem.
  • In any database's design there is a temporary storage before the tables, inside the database server. The instructor called it the write-ahead log (also mentioning commit/audit logs).
  • Your data is written there first. Commit moves it permanently into the tables. Rollback simply removes it from the log — it never reaches the tables.
  • Databases work this way to give the user the option to discard changes.

Auto-Commit
  • The MySQL command-line client has auto-commit on: every statement is flushed to permanent storage immediately, so other people can see it.
  • To get transaction behaviour you set auto-commit to false: the system stops committing by itself and leaves the choice to you.
  • In JDBC, a connection is auto-commit true by default.

What Is a Transaction? — The Boundary

A transaction is multiple database updates happening as one unit; if any one query fails, the earlier ones are rolled back.

  • Picture Query 1 and Query 2 succeeding and Query 3 failing. Run as individual queries, you can't undo 1 and 2.
  • So you create a transaction boundary, decided programmatically: it starts here and ends there. Everything inside is one transaction.
  • All succeed → commit. Any fails → rollback, and the data returns to its original state. Transactions are handled with commit and rollback.
Doing It in JDBC — The Demo
  • Setup: a new Maven project with just the MySQL connector dependency; two tables, orders and payment. Don't name a table order — it is a reserved keyword in MySQL.
  • The three queries (all with executeUpdate, ids hard-coded to 1 for the demo): create the order record → create the payment record (initiated) → payment fails because the user has no balance, so update the payment status.
  • Without a transaction: the instructor forced an exception (calling .length() on a null string) just before the third query. Result: the order and payment rows were created, but the update never happened — inconsistent data.
  • With a transaction — only two extra ideas: setAutoCommit(false) at the start (what you did in the command prompt), and commit() at the end of the try, with rollback() in the catch.
  • Reaching the commit line means no exception occurred; any exception jumps straight to the catch, where everything rolls back. With the forced exception the tables stayed empty; with it removed, the commit went through and the rows persisted.

💡 Added clarification (Class 1):
  • The log is a simplified model. Real engines (e.g. MySQL's InnoDB) use redo/undo logs and buffers, but "write to temporary space → commit moves it to the tables → rollback discards it" is the intended mental picture. Other clients not seeing uncommitted rows is the engine's default isolation behaviour.
  • Atomicity: "all or nothing" is the A in ACID (Atomicity, Consistency, Isolation, Durability).
  • start transaction (or begin) opens a transaction in the MySQL client without switching auto-commit off for the session.
  • Restore auto-commit after you're done (set autocommit = 1 / setAutoCommit(true)), especially on a connection that gets reused.
  • DDL commits implicitly in MySQL: statements like create table or truncate can't be rolled back — which is why truncating the tables between demo runs worked regardless of the transaction.

⚡ Class 2 — PreparedStatement and Batch Processing

The Problem Statement — Upload 10,000 Products

An e-commerce application: sellers want to upload 10,000 products. The UI is built; the data arrives in a CSV file (comma-separated values — one product per line). The class had 10–15 minutes, no ChatGPT, to write a 5–6 step approach on paper — not code.

The instructor's hint: how many database hits? The naive answer is one per record — 10,000. With 1 lakh products that's 1 lakh queries: "that's not going to work."

Why Every Hit Is Expensive
  • Each hit means the program connects to the database and executes a query; the database lives elsewhere, so every hit also crosses the network.
  • 10,000 continuous hits can take minutes, and meanwhile the database responds slowly to other queries. Time is cost to the company.
  • Rule: whenever you develop an application, minimise database hits.
Batching — The Solution, With Everyday Analogies
  • 100 family members visiting a temple: hire 100 cars (100 drivers, 100 petrol bills) or 4 buses of 25? The buses are cheaper.
  • Dmart: buy tea powder, then sugar, then milk on separate trips — or everything in one trip. Your time counts as cost too.
  • For the upload: collect 1,000 records per batch and hit the database once per batch → 10 hits instead of 10,000.
  • "Batching is everywhere" — it isn't a Java invention. Programming optimisations mirror daily-life ones.
  • Is the database time the same? Possibly, at the database level. But from the application side you stop repeating connect → build query → execute for every record, so the total is less. Batch writes are always optimised on the database side: one insert of 1,000 records beats 1,000 separate inserts.
💡 A 5-step approach for the CSV upload (my reconstruction of the exercise — the instructor asked for it but the transcript doesn't give a model answer):
  1. Read the CSV file line by line.
  2. Split each line into product fields.
  3. Bind the fields into a PreparedStatement and add the row to a batch.
  4. Every N rows (say 1,000) execute the batch.
  5. After the last row, execute the leftover batch, then commit — rolling back if anything failed.
Statement vs PreparedStatement
  • "In industry we will not be using Statement" — use PreparedStatement.
  • "Compile" here means the database compiling the SQL query, not Java compilation.
  • Statement: the query is hard-coded text, so every different value is a different query and gets compiled again — update a record 1,000 times and it compiles 1,000 times.
  • PreparedStatement: write the query once with question marks (wildcards), set the values, and the query text stays the same → compiled only once. You keep changing the values.

The demo (updating a payment's status): load the driver, create the connection, call prepareStatement with update payment set status = ? where id = ?, set the values by position (first ?, second ?), and call executeUpdate. The returned count tells you whether it worked — greater than 0 means updated, otherwise "unable to update". He set the status of id 1 to blocked and verified it in MySQL.

Batch Insert Demo
  • The query has three placeholders: insert into payment with id, ref id and status. The goal in the demo: insert about 100 products.
  • Inside a loop, set the values for each record (status init for all) and call addBatch(). Nothing executes yet — each record is just added to the batch.
  • After the loop, call executeBatch(): all the records go to the database in one hit. Auto-commit was set to false first, with a commit once the batch executed.
  • Batch size: add a counter — with a batch size of 10, execute the batch whenever the record number is a multiple of 10 (% and == 0). That's 10 database hits for 100 records. Choose whatever size suits you.
  • The leftover batch: if the record count isn't a multiple of the batch size, the last few never reach the condition. The instructor saw 90 rows, realised the last 9 were still sitting in the batch, and added one more executeBatch() after the loop — then all 99 appeared.

💡 Added clarification (Class 2):
  • "Compiled once" depends on the driver. MySQL Connector/J prepares statements on the client side by default (server-side preparation is a separate setting, useServerPrepStmts). What you always get from ? placeholders: values are sent as data rather than glued into the SQL string, which prevents SQL injection, plus cleaner, reusable code.
  • Make batching really pay off in MySQL: add rewriteBatchedStatements=true to the JDBC URL so the driver rewrites batched inserts into multi-row inserts. Without it the gain can be small — which is why the homework says to measure.
  • executeBatch() returns an int[] of update counts and clears the batch. On failure it may throw BatchUpdateException.
  • Link to Class 1: run the batch with auto-commit off and you get all-or-nothing for the whole upload — a failure lets you roll back every batch.

2. A JDBC transaction — commit at the end, rollback in the catch (Class 1):

public void placeOrder() {
    Connection con = null;
    try {
        Class.forName("com.mysql.cj.jdbc.Driver");
        con = DriverManager.getConnection(
                "jdbc:mysql://localhost:3306/your_database", "root", "your_password");

        con.setAutoCommit(false);                // transaction boundary STARTS here

        Statement stmt = con.createStatement();

        // 1. create the order record
        stmt.executeUpdate("insert into orders (id, item, status) values (1, 'Laptop', 'created')");
        // 2. create the payment record
        stmt.executeUpdate("insert into payment (id, ref_id, status) values (1, 1, 'initiated')");

        // String name = null; name.length();    // uncomment to force an exception and test the rollback

        // 3. payment failed (no balance): update the payment status
        stmt.executeUpdate("update payment set status = 'failed' where id = 1");

        con.commit();                            // reached only if nothing above threw
        System.out.println("Committed");

    } catch (Exception e) {
        System.out.println("Problem: " + e + " -> rolling back");
        try {
            if (con != null) con.rollback();     // undo queries 1 and 2 as well
        } catch (SQLException ex) {
            ex.printStackTrace();
        }
    }
}

3. PreparedStatement — one query, new values each time (Class 2):

private static final String URL = "jdbc:mysql://localhost:3306/your_database";
private static final String USER = "root";
private static final String PASSWORD = "your_password";

public void updatePayment(String status, int id) throws ClassNotFoundException, SQLException {
    Class.forName("com.mysql.cj.jdbc.Driver");                      // dynamic class loading
    Connection con = DriverManager.getConnection(URL, USER, PASSWORD);

    String sql = "update payment set status = ? where id = ?";     // the query text never changes
    PreparedStatement ps = con.prepareStatement(sql);

    ps.setString(1, status);     // first ?
    ps.setInt(2, id);            // second ?

    int rows = ps.executeUpdate();
    System.out.println(rows > 0 ? "Record updated" : "Unable to update the record");
}
// updatePayment("blocked", 1);   -> check in MySQL: id 1 now has status blocked

4. Batch insert with a batch size and the leftover batch (Class 2):

// added: rewriteBatchedStatements makes MySQL batching genuinely faster
Connection con = DriverManager.getConnection(
        URL + "?rewriteBatchedStatements=true", USER, PASSWORD);
con.setAutoCommit(false);

String sql = "insert into payment (id, ref_id, status) values (?, ?, ?)";   // three placeholders
PreparedStatement ps = con.prepareStatement(sql);

int batchSize = 10;
for (int i = 1; i <= 99; i++) {
    ps.setInt(1, i);                 // id
    ps.setInt(2, i);                 // ref id (illustrative)
    ps.setString(3, "init");         // status "init" for all, as in class
    ps.addBatch();                   // only queued -- NOT executed yet

    if (i % batchSize == 0) {        // every 10th record
        ps.executeBatch();           // one database hit for 10 records
    }
}

con.commit();                        // commit once everything has executed

❓ Doubts / Questions Raised in Class

QuestionAnswer Given in Class
Is setAutoCommit(false) a database-wide setting?No — it applies to that client/connection only. Another client or another class can keep auto-commit true.
Can we roll back after we have committed?No — once committed, the data is in the permanent tables. You'd need a backup/checkpoint (say, a backup taken up to 12 PM) and restore that snapshot. Manual deletion isn't realistic with millions of transactions, though a small program could delete a single record.
If auto-commit stays on, can we still roll back?No — each statement is written the moment it arrives, so you get no chance. Disable auto-commit first.
After the demo, do we set auto-commit back?Yes — set it back to true afterwards.
If the database time is the same, how does batching help?The application stops repeating connect, build query and execute for every record, so the overall time is less; batch writes are also optimised on the database side.
