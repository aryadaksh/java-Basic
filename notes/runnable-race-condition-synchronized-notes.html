🧠 Key Concepts

Recap: Two Ways to Create a Thread

(1) Extending the Thread class — covered previously. (2) Implementing the Runnable interface — the new approach covered in this session.

Runnable — A Functional Interface

Runnable is a functional interface (exactly one abstract method): public void run(). To use it: your class implements Runnable and overrides run() with your desired logic — this is where your business logic goes, exactly like before.

Creating a Thread via Runnable — The Steps
  1. Create a class that implements Runnable.
  2. Override public void run() with your task's logic.
  3. Create an object of your Runnable-implementing class.
  4. Pass that object into a Thread constructor: new Thread(yourRunnableObject).
  5. Call .start() on the resulting Thread object.
Why the run() Return Type Question is a Guaranteed Interview Trap

Explicitly flagged: interviewers WILL ask "what does run() return?" If you answer correctly (void), they move to the next question. If you get this wrong, it signals you don't genuinely understand threading — described as an immediate red flag with essentially "no chance" of passing that line of questioning.

Thread vs Runnable — Functionally Identical, Structurally Different

The actual LOGIC inside run() doesn't change between the two approaches — only HOW you set up the class changes. With Thread, you extend the Thread class. With Runnable, you implement an interface instead.

Why Runnable is Considered "Better" — The Key Interview Answer

Java does not support extending multiple classes (no multiple inheritance via classes). If your class extends Thread, it has already "used up" its one allowed superclass — it cannot also extend any other class it might need. If your class instead implements Runnable, it remains free to also extend a different class if your design requires it — giving you strictly more flexibility. This is exactly the answer expected when asked "which is better, and why?" in an interview.

Thread.sleep() — Pausing a Thread for a Specified Time

Calling Thread.sleep(milliseconds) puts the currently executing thread into a temporary paused state for that duration. This moves the thread into the TIMED_WAITING state (from the thread lifecycle covered previously) — it does nothing at all during that time, then automatically becomes eligible to run again once the CPU picks it up.

Why sleep() Requires a try-catch Inside run()

Thread.sleep() throws a checked exception (InterruptedException). But since Runnable's run() method signature does NOT declare any throws clause, you cannot let that exception propagate out of run() — it must be caught and handled with a try-catch block directly inside run() itself.

Real-World Use Case for Thread.sleep()

Example given: a process is sending an email that needs a file attachment, but that file is being generated by another process which takes a couple of seconds to complete. Rather than the thread busy-waiting (wasting CPU), it can sleep() for the expected duration, then wake up, fetch the now-available file, attach it, and send the email. The instructor noted: "there will be thousands of examples" depending on the specific real-world requirement.

Demonstrating Mixed/Interleaved Output

When two threads (T1, T2) are both started and both call the SAME task's logic (e.g. both incrementing/printing numbers), the printed output comes out interleaved/mixed — direct, visible proof that both threads are genuinely executing concurrently, with the CPU switching between them mid-task.

The New Requirement: Sometimes You Need NO Interleaving

Some real requirements demand the opposite: "once a thread starts this task, let it FULLY complete before any other thread is allowed to start the same task." Without any special handling, Java does NOT guarantee this — threads run concurrently by default, and their outputs can freely mix. Achieving strict "one-at-a-time, fully complete" behavior requires an explicit mechanism: synchronized.

Observed Behavior With synchronized Added

Live demonstration: the SAME program, once synchronized is added to the shared method, changes behavior — instead of mixed/interleaved output, one thread now runs to full completion before the second thread is even allowed to begin. Which thread goes first is still not guaranteed (that's still up to the CPU) — but once a thread starts, it's guaranteed to finish uninterrupted before another thread can enter that same synchronized method on the same object.

Is Synchronization Always "Good Practice"? — It Depends

Analogy: "Do you need a locker at home?" The honest answer isn't yes or no — it depends entirely on whether you actually have something valuable worth protecting. Similarly: "Is synchronization good practice?" — depends on context. For a financial transaction, yes, absolutely. For something like simply sending an email (where mixed/interleaved execution causes no real harm), forcing synchronization may be unnecessary overhead, not a benefit.

💳 The Core Problem: A Detailed Race Condition Walkthrough

Setup: You have an SBI bank account with a balance of ₹1,000. Multiple apps/methods are all linked to this SAME account: Google Pay, PhonePe, ATM card, and Cred. You give your ATM card to your brother (who's living with you, preparing for UPSC) so he can use it whenever needed.
The Coincidence: At the exact same moment (nanosecond-level precision) — you initiate a Google Pay transaction sending ₹600 to a friend (for a haircut), while simultaneously, your brother uses the ATM card to withdraw ₹700 (to buy a book). Neither of you knows the other is transacting at that exact instant — this is a genuine coincidence, but at the scale of billions of transactions happening every second across a real banking system, this exact kind of collision will happen to some small percentage of transactions. "Don't assume this never happens."
T1 (Google Pay thread): reads balance → sees ₹1,000
T2 (ATM thread): reads balance → ALSO sees ₹1,000 (T1 hasn't updated it yet!)
T1: checks: is ₹600 ≤ ₹1,000? YES → proceeds with withdrawal
T2: checks: is ₹700 ≤ ₹1,000? YES → proceeds with withdrawal (using the SAME stale ₹1,000!)
T1: completes — withdraws ₹600
T2: completes — withdraws ₹700
TOTAL withdrawn: ₹1,300 — from an account that only had ₹1,000!
What Just Happened — This is a Race Condition

Both threads read the SAME initial balance before either one had a chance to update it. Because their validation checks happened against the same stale value, BOTH withdrawals were incorrectly approved. A race condition occurs when two or more threads access and modify the same shared resource (the same method/object's data) at nearly the same instant, and the final result becomes incorrect because neither thread was aware of the other's in-progress change.

Is This a "Scam"? — A Direct Clarification

The instructor noted that people frequently ask whether this kind of banking glitch counts as a "scam." Answer: no — it's not intentional fraud on anyone's part; it's a genuine software bug resulting from unsynchronized concurrent access to shared data. That said, it's noted that some people have actually exploited this exact vulnerability in real life — using two phones and attempting simultaneous withdrawals, hoping to hit this race condition (succeeding maybe 1 out of 10 attempts) to withdraw more money than their actual balance allows.

The Fix Java Provides: One Thread At a Time, On the Relevant Method

Java's answer to this problem: ensure that only one thread at a time can access the critical method (e.g. the withdrawal logic) for a given shared object. Whichever thread gets there first completes its ENTIRE operation (check balance → withdraw → update balance) before the second thread is even allowed to begin checking the balance — eliminating the stale-read problem entirely.

Walking Through the FIXED Sequence

Thread 1 (GPay) starts: checks balance (₹1,000) → withdraws ₹600 → updates balance to ₹400 — all while Thread 2 (ATM) is forced to WAIT. This wait is typically just a few milliseconds — imperceptible to the user. THEN Thread 2 starts: checks balance — now correctly sees ₹400 → tries to withdraw ₹700 → correctly rejected as insufficient balance. The system now behaves correctly.

⚠️ Critical Misconception, Explicitly Corrected in Class

synchronized does NOT mean "only ONE thread in the ENTIRE WORLD/SYSTEM can execute this method at a time." If that were true, while YOU are doing a Google Pay transaction, literally nobody else on Earth could use Google Pay simultaneously — which is obviously absurd and untrue (millions of people use these apps concurrently, constantly).

The correct understanding: synchronized enforces one-thread-at-a-time PER OBJECT (per shared resource instance) — NOT globally across the whole application. If your account is represented by ONE shared object, only ONE thread can execute the synchronized method ON THAT SPECIFIC OBJECT at a time. A completely different account (a different object) with its own synchronized method call is entirely unaffected and can execute at the exact same time, in full parallel, with zero conflict — because it's not sharing any data with the first account.

Multiple Objects, Same Class — No Conflict

Example: if your account has THREE separate linked objects internally (say, one for Google Pay, one for PhonePe, one for ATM) rather than genuinely sharing ONE underlying account object, calling a synchronized method through each of those three DIFFERENT objects could still run in parallel — and could STILL result in a race condition, because synchronization only protects against concurrent access on the same object. This reinforces why the underlying system design (how many objects actually represent your one real account) matters enormously for correctness.

Pedagogical Approach — Problem First, Solution Second

Explicitly stated teaching philosophy for this topic: understand the REAL problem (race conditions) deeply and intuitively FIRST — before jumping to "just add the synchronized keyword and move on." The instructor noted that even many industry professionals don't truly understand synchronization deeply, specifically because they skipped understanding the underlying problem it solves.

💻 Code Snippets / Examples

Creating a thread via Runnable:

class NumberPrinter implements Runnable {

    @Override
    public void run() {
        for (int i = 1; i <= 10; i++) {
            System.out.println(i);
        }
    }
}
class Driver {
    public static void main(String[] args) {
        NumberPrinter task = new NumberPrinter();  // create the Runnable object
        Thread t1 = new Thread(task);              // pass it into a Thread
        t1.start();                                // start it, same as before
    }
}

Why Runnable is more flexible — can still extend another class:

// NOT possible with the Thread-extending approach:
// class NumberPrinter extends Thread, extends SomeOtherClass { } // ILLEGAL — no multiple inheritance

// POSSIBLE with Runnable:
class NumberPrinter extends SomeOtherClass implements Runnable {
    @Override
    public void run() {
        // task logic here
    }
    // ... can still use everything inherited from SomeOtherClass too
}

Thread.sleep() — pausing a thread, with required try-catch:

class EmailTask implements Runnable {

    @Override
    public void run() {
        System.out.println("Preparing to send email...");

        try {
            Thread.sleep(5000); // pause for 5 seconds — moves to TIMED_WAITING
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        // run() has no "throws" clause, so InterruptedException MUST be caught here

        System.out.println("File ready — sending email now.");
    }
}

Demonstrating mixed output — two threads, no synchronization:

class Counter implements Runnable {
    @Override
    public void run() {
        for (int i = 1; i <= 5; i++) {
            System.out.println(Thread.currentThread().getName() + " - " + i);
        }
    }
}
Counter task = new Counter();
Thread t1 = new Thread(task, "Thread-1");
Thread t2 = new Thread(task, "Thread-2");

t1.start();
t2.start();
// Output is MIXED/interleaved — e.g.:
// Thread-1 - 1
// Thread-2 - 1
// Thread-1 - 2
// Thread-2 - 2
// ... unpredictable interleaving

Adding synchronized — forces sequential completion:

class Counter implements Runnable {

    public synchronized void printNumbers() { // synchronized method
        for (int i = 1; i <= 5; i++) {
            System.out.println(Thread.currentThread().getName() + " - " + i);
        }
    }

    @Override
    public void run() {
        printNumbers();
    }
}
Counter task = new Counter();
Thread t1 = new Thread(task, "Thread-1");
Thread t2 = new Thread(task, "Thread-2");

t1.start();
t2.start();
// Output is now SEQUENTIAL — one thread fully completes before the other starts:
// Thread-1 - 1
// Thread-1 - 2
// Thread-1 - 3
// Thread-1 - 4
// Thread-1 - 5
// Thread-2 - 1
// Thread-2 - 2
// ...
// (Which thread goes FIRST is still not guaranteed — but no more MIXING once started)

Conceptual illustration of the bank account race condition:

class Account {
    int balance = 1000;

    // WITHOUT synchronized — vulnerable to race conditions
    public void withdraw(int amount) {
        if (amount <= balance) {          // both threads may read balance=1000 here
            // ... simulate processing delay ...
            balance = balance - amount;    // both threads then subtract independently
            System.out.println("Withdrew: " + amount + ", Balance: " + balance);
        } else {
            System.out.println("Insufficient balance");
        }
    }
}
Account account = new Account();

Thread gpayThread = new Thread(() -> account.withdraw(600));
Thread atmThread = new Thread(() -> account.withdraw(700));

gpayThread.start();
atmThread.start();
// Without synchronized, BOTH may see balance=1000 before either updates it,
// potentially allowing BOTH withdrawals to succeed -> balance goes to -300 (a bug!)

The fix — synchronized on the shared method:

class Account {
    int balance = 1000;

    public synchronized void withdraw(int amount) { // NOW only one thread at a time on THIS object
        if (amount <= balance) {
            balance = balance - amount;
            System.out.println("Withdrew: " + amount + ", Balance: " + balance);
        } else {
            System.out.println("Insufficient balance");
        }
    }
}
// Now: one thread fully completes its check-and-update before the other can even begin —
// the stale-read race condition is eliminated for THIS shared account object

❓ Doubts / Questions Raised in Class

QuestionAnswer
Why is Runnable considered better than extending Thread?A class extending Thread cannot also extend any other class (Java has no multiple class inheritance); a class implementing Runnable remains free to extend a different class if needed — more design flexibility.
Why must Thread.sleep()'s exception be caught inside run()?run() has no "throws" clause in its signature, so the checked InterruptedException thrown by sleep() cannot propagate out — it must be handled with try-catch directly inside run().
Is using synchronized always good practice?No — it depends on context. Critical shared-data operations (like financial transactions) benefit greatly; low-stakes operations (like sending an email) may not need it and could suffer unnecessary overhead.
Does synchronized mean only ONE thread globally can run that method across the entire application?No — this is a common and serious misconception. synchronized enforces one-thread-at-a-time PER OBJECT, not globally. Different objects can still execute the same synchronized method in full parallel with no conflict.
Once synchronized is added, does it guarantee which thread runs FIRST?No — which thread starts first is still determined by the CPU, same as always. What synchronized guarantees is that once a thread DOES start, it will fully complete before another thread can enter that same method on the same object.

📌 Important Points / Common Mistakes

  • Runnable's run() method must return void and cannot declare checked exceptions — handle them internally.
  • Runnable is generally preferred over extending Thread specifically because it preserves the ability to extend another class.
  • Thread.sleep() moves a thread to TIMED_WAITING — it does nothing productive during that time, then becomes eligible to run again.
  • Without synchronization, multiple threads accessing shared logic produce unpredictable, potentially interleaved/mixed results.
  • A race condition occurs when concurrent threads read/modify the same shared data based on stale values, producing an incorrect final result.
  • synchronized fixes this by allowing only one thread at a time to execute the protected method — but ONLY for a given shared object, never globally across the whole system.
  • Don't assume rare-seeming timing coincidences "never happen" — at very large scale (billions of operations), even tiny-probability race conditions occur regularly.
