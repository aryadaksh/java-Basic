🧠 Key Concepts

Quick Recap — Where Does settings.xml Live?

A question from the start of class: is settings.xml specific to a project? No.

  • Whenever you add a JAR (dependency) in pom.xml, your system must connect to a Maven repository — a company-local repository or the Maven global repository.
  • There is only one settings.xml per system. It sits in the common .m2 directory inside your user (home) directory (the transcript says "M2 home").
  • Even if you have 20 projects (possibly talking to 20 different repositories), the settings.xml is that same one, on your local machine.
Build Tools Are Not Optional (Instructor's Emphasis)

The instructor stressed that you cannot avoid Maven (or another build tool) in a Java job, and that from now on, every day's work will be a Maven project. Even if it feels confusing at first, repetition builds the memory.

A Developer's Work — And Where Unit Testing Fits
  • Development is nothing but writing code based on a requirement. Don't try to mug it up — understand the flow.
  • Once code is written, the testing team will check it — but before you give it to them, you must verify it from your side. You cannot hand over junk code.
  • That verification by the developer is unit testing. It sits between development and the testing team.
  • Who performs unit testing? The developer.

Interview angle: "What is your day-to-day activity?" — many people can't justify it. The honest flow is: you get a requirement → you write code → you test it (unit tests) → it goes to the testing team.

Why Test Your Own Code?
  • You only need Core Java to write unit tests (as of now).
  • You may think, "I wrote the code, why should I test it?" — but while writing, you were thinking in one direction only.
  • When you start testing, "100 directions" appear: what if this is negative? what if this is positive? Testing forces you to cover them.
The Product Analogy — Test Scenarios

Imagine a product you have to test (the instructor used a household appliance example — the exact product word is unclear in the transcript; the scenarios he listed — on/off, rotation, speed control, swing, "should not heat up", "should not make noise" — suggest a fan). To test any product you write test case scenarios, e.g. when rotation is turned off, swing should also stop.

In our world, the "product" is our code — specifically methods. To test a method you write different scenarios, and you do it to maintain code quality.

What Is JUnit?

JUnit is the Java unit testing framework. It lets you write and execute test cases.

The advantage: imagine a class with 500 lines of code. If someone else modifies it and you don't know how it works or what the impact is — JUnit captures it.

Setup — Add the JUnit Dependency
  1. Create a Maven project (in class: an e-commerce/order project).
  2. Check pom.xml — the existing JUnit dependency was an old version, so the instructor searched for the latest JUnit Jupiter dependency on the Maven repository website, copied the dependency block and pasted it into pom.xml.
  3. On save, Maven replaces the old one with the new one and downloads it. You only declare one dependency; Maven works out and fetches everything else it needs.

What is a dependency? Nothing but a JAR file containing functionality you want to use. Same idea as the account and payment dependency from the last project: whatever is written in payment can be used in account. Here, the testing functionality is written inside the JUnit JAR, so your project needs it as a dependency.

Which Version? — Instructor's Advice From the Class Fixes
  • When some students had trouble with the newest version, the instructor told them to use 5.x — the highest 5.x version.
  • Copy the dependency from the Maven repository site instead of only editing the version number — the artifact name might change between versions and you wouldn't know.
  • General rule: when you're learning something new, don't use the latest version — use "N minus one". If the latest is 10, start with 9; it will be a little more stable.
The Test Class — Convention and Location
  • Maven already creates a test source folder (src/test/java) in the project.
  • There you write an equivalent class of the class you want to test (e.g. a test class for DiscountCalculator). This is just a convention.
  • This class is used to test the functionality of that class, and holds all the scenarios for it.
Writing a Test Case — Input, Expected, Actual
  • Write a method, e.g. public void testXxx(). The "test…" name is only a convention.
  • Mark it with the @Test annotation — this is what qualifies the method as a test case.
  • Ultimately there's only one way to test: call the method yourself and pass the input. You know the input, so you also know the expected output (like pressing a switch and expecting the fan to turn).
  • To call the method, create an object of the class, then call e.g. calculateDiscount(...).
  • Actual = what the method really returns.
  • Compare with assertEquals(expected, actual) — part of the JUnit framework. It takes two parameters: expected first, then actual, and tells you whether the method's result matches your expectation.
Who Writes the Unit Tests?

The developer who wrote the source code — the owner of the class. Don't think "how would I know it should give 900?" — based on the requirement, the developer knows the functionality: if I pass 1000 and customer type Regular, the discount is 10%, so it should give 900. That's the expected value.

Running the Tests
  • You do not use "Run as Java Application" for this.
  • Right-click the test class → Run As → JUnit Test. It runs the test class and shows a results view.
  • Green = passed. A failing test reports what was expected and what the method actually gave (e.g. "expected 800 but was 1000").

Positive and Negative Scenarios

Scenarios are always both: positive (valid inputs behave as expected) and negative (invalid or unexpected input is handled correctly). The instructor started with positive cases, then moved to negative ones. For this tiny method he said you could write 10 different test cases; even a 10-line piece of code ends up with test cases of its own (in the demo, three).

Why Do We Write Unit Tests? — Two Reasons
  1. Maintain code quality — by giving different inputs you test your code the first time around.
  2. Protect existing code over time — code lives in a company for 20–30 years. The person who wrote it leaves; someone else modifies it, assuming "this part shouldn't be affected". Tests tell you whether the new change breaks the existing implementation.

The instructor's remark: to write 5 lines of code you might write 100 lines of unit tests — because quality matters.

The "GST Story" — What Happens Without Unit Tests
  1. The discount module works. The original developer has left.
  2. Another developer is asked to enhance it — in the story, a new GST-related functionality, plus a change involving the customer type being lower-cased. He adds ~20 lines and thinks: "I'm not touching the base calculation, so nothing will break." (That's how we always assume — until an error shows up.)
  3. Nothing crashes. But a Gold customer no longer gets the discount — there's no failure message anywhere.
  4. The customer calls the call centre → they give a credit of 200 → they report it to the engineering team → engineering explains that the newly introduced GST functionality caused it.
  5. The VP asks: "Why didn't we have unit tests? We could have caught this right before the release."

The rule: whenever you change an existing code base, run the unit tests again. They tell you whether your new changes are breaking the existing implementation. In the demo, re-running showed the Gold test failing: expected 800 but was 1000 — the one-line change had broken a fundamental. With 10,000 lines, you can't know what a change breaks elsewhere — JUnit test cases will catch it.

Standard Practice — Even for One Line of Code
  • Interviewers ask: "How do you maintain code quality?" and "If code is already running and you're doing an enhancement, how do you make sure the existing implementation isn't broken?" The answer: unit test cases.
  • Even a one-line change comes with test cases — part of development.
  • The owner of the class writes them — the developer who knows the class inside out.
  • Nobody in the company will tell you to write JUnit tests — just like nobody tells you to follow Java naming conventions. It's a standard practice.
What About void Methods and Private Methods? (Q&A in Class)
  • Void method: if you call a void method, you get nothing back. But if it changes some state, you can read that state afterwards and check it.
  • Private methods / code you don't control: there are other frameworks — EasyMock and Mockito. You can create a mock, set expectations and run it. They'll be covered when the Spring framework starts; they help test things like server-side code or methods you have no control over.
  • To start with, practise on methods that return something (an integer, etc.).
💡 Added clarification — terms and details the lecture didn't spell out:
  • "Re-run the tests after every change" has a name: regression testing. A regression is when something that used to work stops working after a change. The instructor described the idea but didn't use the term.
  • JUnit versions: "JUnit Jupiter" is JUnit 5. JUnit 4 used org.junit.Test; JUnit 5 uses org.junit.jupiter.api.Test. Importing the wrong @Test (or missing an import) is a very common reason a test doesn't run or assertEquals isn't suggested.
  • mvn test vs the IDE: if tests run in the IDE but not from the command line, an old maven-surefire-plugin version is a frequent cause — JUnit 5 needs a reasonably recent Surefire.
  • Argument order matters: assertEquals(expected, actual). Swapping them still passes/fails correctly, but the failure message becomes misleading.
  • Decimals: comparing double values can hit tiny rounding differences; JUnit offers assertEquals(expected, actual, delta) for that.
  • Name vs annotation: in JUnit 5, it's the @Test annotation — not the "test…" name prefix — that makes a method a test. The prefix is only a readable convention, as the instructor said.
  • Mocking and private methods: mock frameworks replace collaborators; the usual advice for private methods is to test them through the public methods that call them, rather than directly.
  • Developers vs the testing team: unit tests are the developer's first line of checking; the testing team's work happens afterwards and isn't replaced by it.

2. The class under test — Discount Calculator (src/main/java):

public class DiscountCalculator {

    public double calculateDiscount(double amount, String customerType) {
        if ("Regular".equals(customerType)) {
            return amount - (amount * 0.10);   // 10% off
        } else if ("Gold".equals(customerType)) {
            return amount - (amount * 0.20);   // 20% off
        }
        return amount;                         // default: no discount applicable
    }
}

3. The test class — the three scenarios from the demo (src/test/java):

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class DiscountCalculatorTest {

    @Test
    public void testRegularCustomerGets10PercentDiscount() {
        DiscountCalculator calculator = new DiscountCalculator();

        double actual = calculator.calculateDiscount(1000, "Regular");

        assertEquals(900, actual);          // (expected, actual)
    }

    @Test
    public void testGoldCustomerGets20PercentDiscount() {
        DiscountCalculator calculator = new DiscountCalculator();

        double actual = calculator.calculateDiscount(1000, "Gold");

        assertEquals(800, actual);
    }

    @Test
    public void testUnknownCustomerTypeGetsNoDiscount() {      // negative scenario
        DiscountCalculator calculator = new DiscountCalculator();

        double actual = calculator.calculateDiscount(1000, "Premium");

        assertEquals(1000, actual);         // wrongly expecting 800 here would fail
    }
}
// Run: right-click the class -> Run As -> JUnit Test.   All three green = passed.

6. A tidier version using @BeforeEach and a delta (added — not shown in class):

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class DiscountCalculatorTest {

    private DiscountCalculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new DiscountCalculator();    // fresh object before every test
    }

    @Test
    void regularCustomerGets10PercentDiscount() {
        assertEquals(900.0, calculator.calculateDiscount(1000, "Regular"), 0.001);  // delta for decimals
    }
}

7. Testing a void method through its state (the Q&A point — example is mine):

public class Cart {
    private int itemCount;
    public void addItem() { itemCount++; }          // void: returns nothing
    public int getItemCount() { return itemCount; } // ...but changes state we can read
}

@Test
void addItemIncreasesItemCount() {
    Cart cart = new Cart();
    cart.addItem();                                 // call the void method
    assertEquals(1, cart.getItemCount());           // check the state it changed
}
