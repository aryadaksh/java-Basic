🧠 Key Concepts

Recap: The Race Condition Problem

When two threads try to modify the same data of the same object at nearly the same instant (e.g. both reading a balance of ₹1,000 before either updates it), both may proceed based on stale data — resulting in an incorrect final value. This is a race condition.

Recap: What synchronized Guarantees

synchronized ensures that only one thread can execute a given method on a particular shared object at a time — NOT globally across the entire system, only for that specific object.

The Internal Mechanism: Object Lock

Every single object in Java automatically comes with exactly ONE object lock (also commonly called a monitor lock). This is what actually enforces the "one thread at a time per object" rule that synchronized provides.

How a Thread Acquires the Lock

When a thread reaches a call to a synchronized method, it recognizes: "this method is synchronized — I need to acquire this object's lock before I can enter." The thread effectively requests the lock from the object. If the lock is currently available (nobody else is holding it), the object hands it over, and the thread proceeds into the method.

Holding the Lock for the Full Duration

Once a thread acquires the object's lock, it holds onto it for the entire time it's executing that synchronized method — even if that takes several milliseconds. No other thread can acquire that SAME object's lock during this window.

What Happens to a Second Thread Trying to Enter

If a second thread reaches the same synchronized method (on the SAME object) while the lock is already held, it cannot proceed. The object effectively tells it: "I don't have my lock right now — I gave it to someone else. Wait until they return it, and I'll give it to you." This second thread enters a waiting state until the lock becomes available.

Releasing the Lock

Once the first thread finishes executing the synchronized method, it releases the object's lock back to the object. The lock is now available again — whichever thread was waiting for it (if any) can now acquire it and proceed into the method itself.

This is THE Answer to "How Does Synchronization Work Internally?"

Explicitly flagged: if asked in an interview "how does synchronization actually work?" — the correct, complete answer is built entirely around this object lock mechanism: one lock per object, acquired before entering, held during execution, released after completion, and handed to the next waiting thread.

One Object = One Lock, Always

If you have 10 different objects, you have 10 separate, independent locks — one per object. A lock is always tied to a specific object instance, never shared across different objects, even if they're instances of the exact same class.

The Critical Follow-Up Demonstration: Using a DIFFERENT Object

To reinforce the "per object, not global" rule, a second task object was created (a separate instance, same class, same synchronized method). Result: mixed/interleaved output returned — even though the method itself is still marked synchronized. Why? Because each thread was now acquiring the lock of a DIFFERENT object — since the two objects' locks are entirely independent of each other, there's nothing preventing both threads from running concurrently, each holding its OWN object's separate lock at the same time.

⚠️ The Single Most Important Takeaway From This Session

Synchronization ONLY prevents concurrent execution when threads are competing for the SAME object's lock. The moment you introduce a second, independent object, synchronized provides zero protection between operations on the FIRST object and operations on the SECOND — they can run fully in parallel, mixed output and all. Whether a race condition can even occur depends entirely on whether the threads are genuinely sharing the same underlying object.

Thread.join() — Making main Wait

t1.join() tells whichever thread calls it (typically main) to pause and wait until thread t1 has fully completed, before continuing further. Used with multiple threads (t1.join(); t2.join();), this ensures BOTH have finished before execution continues past that point.

Why join() Was Needed in the Demo

Without join(), the main thread might reach a System.out.println(balance) statement before the transaction threads have actually finished their work — printing an incomplete/incorrect intermediate balance. Calling .join() on both worker threads ensures the final balance is only printed after both transactions have genuinely completed, giving an accurate result to observe.

Live Demo: FundTransfer Class — The Race Condition, Reproduced

Setup: a FundTransfer class with a shared sender account (balance ₹1,000), and two separate Thread classes simulating two different payment methods (e.g. PhonePe and Google Pay) both calling transfer() on the SAME sender object — one transferring ₹800, the other also attempting a transfer. Without synchronization: both threads read the balance as ₹1,000 before either updated it, both transfers were incorrectly approved, and the final balance became mathematically incorrect (reflecting an over-withdrawal that should have been rejected).

Live Demo: FundTransfer Class — Fixed With synchronized

Adding synchronized to the transfer() method fixed it: whichever thread arrived first (e.g. PhonePe) acquired the sender object's lock, fully completed its check-and-update sequence (balance correctly dropped from ₹1,000 to ₹200), and only THEN released the lock. The second thread (GPay), which had been waiting, then acquired the lock, checked the balance — now correctly seeing ₹200 — attempted its transfer, and was correctly rejected as insufficient funds.

Reinforced: The Problem Only Exists on a SHARED Object

Directly restated: the race condition specifically arises when multiple threads act concurrently on the SAME sender's account object. If a completely different sender (a different account object) is transacting at the exact same time, there's no conflict at all — that thread works with its own independent data. The problem is fundamentally about object sharing, not about threads or synchronized in isolation.

Threads Maintain Their Own Copy When Objects Are Separate

Clarified: if each thread genuinely operates on its own separate object (e.g. your own account object vs. your friend's own account object), each thread's changes only affect its OWN object's data — there's no interference between them whatsoever, since nothing is being shared.

💻 Code Snippets / Examples

Same object, synchronized method — sequential execution (no mixing):

class Task {
    public synchronized void printNumbers() {
        for (int i = 1; i <= 5; i++) {
            System.out.println(Thread.currentThread().getName() + " - " + i);
        }
    }
}
Task sharedTask = new Task(); // ONE shared object

Thread t1 = new Thread(() -> sharedTask.printNumbers(), "T1");
Thread t2 = new Thread(() -> sharedTask.printNumbers(), "T2");

t1.start();
t2.start();
// Output: T1 fully completes (1-5), THEN T2 fully completes (1-5) — no mixing,
// because both threads compete for the SAME object's lock

DIFFERENT objects, same synchronized method — mixing STILL happens:

Task task1 = new Task(); // object #1 — its own separate lock
Task task2 = new Task(); // object #2 — a DIFFERENT, independent lock

Thread t1 = new Thread(() -> task1.printNumbers(), "T1");
Thread t2 = new Thread(() -> task2.printNumbers(), "T2");

t1.start();
t2.start();
// Output is MIXED/interleaved again! Even though printNumbers() is synchronized,
// t1 and t2 are acquiring DIFFERENT objects' locks — no conflict between them at all

Thread.join() — waiting for threads to finish before continuing:

Thread t1 = new Thread(() -> sharedTask.printNumbers());
Thread t2 = new Thread(() -> sharedTask.printNumbers());

t1.start();
t2.start();

t1.join(); // main thread PAUSES here until t1 fully completes
t2.join(); // then pauses until t2 fully completes too

System.out.println("Both threads are done now."); // guaranteed to print AFTER both finish

Full demo — FundTransfer class, race condition reproduced (no synchronized):

class FundTransfer {
    int balance = 1000;

    public void transfer(int amount) { // NOT synchronized — vulnerable
        if (amount <= balance) {
            balance = balance - amount;
            System.out.println("Transferred: " + amount + ", Balance: " + balance);
        } else {
            System.out.println("Insufficient funds");
        }
    }
}
class PhonePeThread extends Thread {
    FundTransfer account;
    public PhonePeThread(FundTransfer account) { this.account = account; }
    public void run() { account.transfer(800); }
}

class GooglePayThread extends Thread {
    FundTransfer account;
    public GooglePayThread(FundTransfer account) { this.account = account; }
    public void run() { account.transfer(800); }
}
class Driver {
    public static void main(String[] args) throws InterruptedException {
        FundTransfer sharedAccount = new FundTransfer(); // ONE shared account, balance 1000

        Thread t1 = new PhonePeThread(sharedAccount);
        Thread t2 = new GooglePayThread(sharedAccount);

        t1.start();
        t2.start();

        t1.join();
        t2.join();

        System.out.println("Final balance: " + sharedAccount.balance);
        // WITHOUT synchronized: both threads may read balance=1000 before either updates it,
        // BOTH transfers of 800 could incorrectly succeed -> balance becomes WRONG (e.g. -600)
    }
}

The fix — adding synchronized to transfer():

class FundTransfer {
    int balance = 1000;

    public synchronized void transfer(int amount) { // NOW protected by the object lock
        if (amount <= balance) {
            balance = balance - amount;
            System.out.println("Transferred: " + amount + ", Balance: " + balance);
        } else {
            System.out.println("Insufficient funds");
        }
    }
}
// Now: one thread (e.g. PhonePe) fully completes its check-and-update (balance -> 200)
// before the second thread (GooglePay) can even check the balance.
// GooglePay correctly sees 200, tries to transfer 800, and is correctly REJECTED.

📌 Important Points / Common Mistakes

  • Every Java object has exactly ONE object lock (also called a monitor lock) — this is the actual mechanism behind synchronized.
  • A thread must acquire an object's lock before entering any synchronized method called on that object, and holds it for the method's entire execution.
  • Synchronized only prevents concurrent access for threads competing on the SAME object — different objects have entirely independent locks and can run in full parallel, mixed output included.
  • Don't assume "the method is synchronized" alone guarantees no interleaving — it depends entirely on whether the competing threads share the same object instance.
  • Thread.join() pauses the calling thread until the joined thread finishes — commonly used to ensure accurate final-state reporting after concurrent work completes.
  • Race conditions are fundamentally about shared object access, not about threads or synchronized in isolation — always ask "are these threads touching the SAME object's data?"
