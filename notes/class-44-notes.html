Class 44 — Custom (User-Defined) Exceptions

🎯 Topics Covered

  • Why built-in exceptions aren't always enough for business scenarios
  • Creating a custom exception class — extending Exception or RuntimeException
  • Choosing checked vs unchecked for your own custom exception
  • Calling the parent constructor to carry the message (super)
  • Throwing and catching custom exceptions
  • Best practice: meaningful, specific exception class names

🧠 Key Concepts

Why Create Custom Exceptions?

Built-in exceptions (NullPointerException, IOException, etc.) describe technical failures, not business-specific ones. A real application needs to communicate business rule violations clearly — e.g. "InsufficientBalanceException" or "UserAlreadyExistsException" — which don't exist as built-in Java classes. Custom exceptions let you model these scenarios explicitly and meaningfully.

Creating a Custom Exception — extends Exception or RuntimeException

A custom exception is just a regular class that extends either Exception (making it checked — compiler-enforced handling) or RuntimeException (making it unchecked — handling optional).

class InsufficientBalanceException extends Exception {
    public InsufficientBalanceException(String message) {
        super(message); // passes message up to Exception's constructor
    }
}
Choosing Checked vs Unchecked for Your Custom Exception

Extend Exception (checked) when the scenario is serious enough that callers must be forced to handle it — the compiler won't let them ignore it. Extend RuntimeException (unchecked) when handling should be optional — often used for programming errors or validation failures that don't need to be forcibly acknowledged at every call site.

Why Call super(message)

The Exception/RuntimeException classes already have built-in support for storing and retrieving a descriptive message (via getMessage()). Calling super(message) in your custom exception's constructor passes your message up to be stored using that existing mechanism, rather than reinventing message-handling from scratch.

Throwing and Using a Custom Exception

Once defined, a custom exception is thrown just like any other: throw new InsufficientBalanceException("Balance is too low"); — and caught the same way, using its specific type in a catch block.

Best Practice: Meaningful, Specific Names

Name custom exceptions clearly after the exact business scenario they represent (e.g. InvalidOrderQuantityException, not a vague name like MyException) — this makes catch blocks self-documenting and easier to reason about when reading code later.

💻 Code Snippets / Examples

Custom checked exception — InsufficientBalanceException:

class InsufficientBalanceException extends Exception {
    public InsufficientBalanceException(String message) {
        super(message);
    }
}
class Account {
    private int balance;

    public Account(int balance) {
        this.balance = balance;
    }

    public void withdraw(int amount) throws InsufficientBalanceException {
        if (amount > balance) {
            throw new InsufficientBalanceException("Insufficient balance to withdraw " + amount);
        }
        balance -= amount;
        System.out.println("Withdrawal successful, remaining balance: " + balance);
    }
}
class Driver {
    public static void main(String[] args) {
        Account account = new Account(1000);
        try {
            account.withdraw(5000);
        } catch (InsufficientBalanceException e) {
            System.out.println("Transaction failed: " + e.getMessage());
        }
    }
}

Custom unchecked exception — InvalidOrderQuantityException:

class InvalidOrderQuantityException extends RuntimeException {
    public InvalidOrderQuantityException(String message) {
        super(message);
    }
}
class OrderService {
    public void placeOrder(String item, int quantity) {
        if (quantity <= 0) {
            throw new InvalidOrderQuantityException("Quantity must be greater than zero");
        }
        System.out.println("Order placed for " + quantity + " x " + item);
    }
}
class Driver {
    public static void main(String[] args) {
        OrderService service = new OrderService();
        service.placeOrder("Laptop", -2); // throws unchecked — no try-catch required to compile
        // If uncaught, program terminates abnormally with the custom exception's message
    }
}

Custom exception for a duplicate-user scenario:

class UserAlreadyExistsException extends Exception {
    public UserAlreadyExistsException(String message) {
        super(message);
    }
}
class UserService {
    public void createUser(String userId) throws UserAlreadyExistsException {

        }
        System.out.println("User created: " + userId);

❓ Doubts / Questions Raised in Class

QuestionAnswer
Why not just use the built-in Exception class directly with a custom message, instead of creating a whole new class?A dedicated custom exception class gives a specific, self-documenting TYPE that can be caught distinctly from other exceptions — using generic Exception everywhere makes it impossible to differentiate between different failure scenarios in catch blocks.
Should custom exceptions extend Exception or RuntimeException?Depends on whether you want to force callers to handle it (extend Exception, checked) or leave handling optional (extend RuntimeException, unchecked) — a design decision based on how critical the scenario is.
What does super(message) actually do in a custom exception's constructor?It passes the message up to the parent Exception/RuntimeException class's constructor, which already has built-in support for storing and returning it via getMessage().

📌 Important Points / Common Mistakes

  • Custom exceptions are just regular classes extending Exception (checked) or RuntimeException (unchecked).
  • Always call super(message) to properly store the exception's message using the built-in mechanism.
  • Choose checked vs unchecked deliberately based on whether handling should be mandatory or optional for callers.
  • Name custom exceptions specifically and meaningfully — avoid vague names like "MyException" or "CustomException."
  • Custom exceptions are thrown and caught exactly like built-in ones, using their specific class type.
