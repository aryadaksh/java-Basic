🧠 2 · Detailed Concept Explanations

Beginner → advanced, following the instructor's order. All of Part 2 is added.

2.1 · What a bean is — the foundation 🧠 Added

A bean is an ordinary Java object that the Spring IoC container creates and manages — you register a class (XML, @Bean, @Component) and ask the container for the object instead of writing new. The container owns the object's life. Scope is the rule that answers: "how many instances of this bean will exist, and who shares them?"

2.2 · What bean scope is, and why it is needed 🧠 Added
  • Scope = the lifespan and sharing rule of a bean: how many instances, when they are created, who can see them, and when they go away.
  • Without a rule you'd either create objects needlessly (wasting memory and time) or share an object that should be private (leaking one customer's data to another).
  • In a FinTech app: a tax or interest calculator has no per-customer data, so one shared instance is enough. A transfer-in-progress object holds one customer's amount, so each transfer needs its own.
  • The decision is a design decision: "does this object hold state that belongs to one operation, one request, one user, or nobody in particular?"

  • A "singleton" in Spring means one instance per bean definition per container — not "one per JVM" and not the GoF pattern (see 2.4).
2.4 · Singleton scope 🧠 Added
  • The default. If you write no scope, you get a singleton.
  • One instance, shared by everything that asks for the bean — every getBean call and every injection point gets the same object (== is true).
  • Not the GoF Singleton pattern: the class itself isn't restricted to one object. If you define the same class under two names, the container holds two instances.
  • Full life cycle: created at startup, initialised once, destroyed when the container closes.
  • Thread safety is your job. Many request threads call the one instance at the same time, and Spring does not synchronise it. Good singleton beans are stateless (or hold only immutable or thread-safe state).
  • Best for: services, repositories, calculators, clients of external systems.
2.5 · Prototype scope 🧠 Added
  • A new instance every time the bean is requested or injected (== is false).
  • Created lazily — only when someone asks.
  • Partial life cycle: Spring creates it, injects its dependencies and runs the initialisation callbacks — then stops tracking it. Destruction callbacks (@PreDestroy) are never called; cleaning up is the caller's job.
  • Best for: stateful, short-lived, per-operation objects — a transaction context, a statement builder, a one-time challenge.
  • Cost: every request allocates an object; the garbage collector reclaims it later.

2.7 · Request scope 🧠 Added
  • One instance per HTTP request. It is created when the request first needs it and discarded when the request finishes.
  • Ideal for data that belongs to one request only: a correlation ID, the request's start time, the caller's IP.
  • Needs a web application (Spring MVC/Boot, a web-aware context). In a plain console program the container has no "request", and asking for it fails — the reason the instructor said it can't be validated yet (see 3.8).
2.8 · Session scope 🧠 Added
  • One instance per HTTP session — i.e. per logged-in browser session. All of one user's requests share it; another user gets a different instance.
  • Typical use: the logged-in customer's profile, a multi-step loan application draft.
  • Lives until the session ends or times out. Memory use grows with the number of active sessions, and in a cluster sessions must be replicated (and beans made Serializable) or pinned to a server.
  • Also needs a web application.
2.9 · Application scope 🧠 Added
  • One instance for the whole web application (bound to the servlet context): every user, every session, every request sees the same bean — the instructor's "100 users" example.
  • Use it for application-wide read-mostly data: an exchange-rate cache, a bank-holiday calendar, feature flags.
  • It behaves much like a singleton, but it is stored as a servlet-context attribute and only exists in a web application.
  • Careful: shared by many threads, so the same thread-safety rules as a singleton. And "application-wide" means per server instance — three servers in a cluster hold three copies.
2.10 · Multiple users and concurrent requests — who sees what 🧠 Added

Suppose user A sends two requests and user B sends one, all at the same moment:

SingletonInstance #1Instance #1Instance #1All three threads share one object
PrototypeNewNewNewA new object at each lookup / injection
RequestR1R2R3One per request, even for the same user
SessionSASASBShared within a user's session, never across users
ApplicationInstance #1Instance #1Instance #1Shared by all users
  • Shared scopes (singleton, application) are touched by concurrent threads → they need thread-safe design.
  • Per-user or per-request data therefore belongs in session, request or prototype beans — never in a singleton or application field.

2.13 · Advanced: a prototype inside a singleton 🧠 Added

A singleton is built once, so its dependencies are injected once. If one of them is a prototype, the singleton keeps that single instance forever — the "new every time" behaviour is lost. The same trap applies to request- and session-scoped beans injected into a singleton.

  • ObjectProvider<T> — inject the provider and call getObject() each time you need a fresh bean (snippet 5).
  • @Lookup method injection — Spring overrides an abstract/stub method to return a new bean on each call.
  • Scoped proxy (proxyMode = ScopedProxyMode.TARGET_CLASS) — Spring injects a proxy; each call on it is routed to the right instance for the current request/session. The web-scope shortcut annotations already use it.
  • Or ask the context directly (getBean) — it works but ties your class to Spring.
2.14 · Common mistakes 🧠 Added
  • Mutable per-user fields in a singleton — one customer's data appears for another; a serious bug in banking code.
  • Expecting "new every time" from a prototype injected into a singleton — it is injected once.
  • Expecting @PreDestroy on a prototype — Spring never calls it.
  • Using request/session scope in a console program — there is no web scope registered.
  • Treating the Spring singleton as the GoF pattern — Spring only guarantees one per definition per container.
  • Putting sensitive data in session or application scope without thinking about who can reach it and how long it lives.
  • Registering a class twice (@Component on the class and a @Bean method) — you get two beans and possibly a "no unique bean" error.
  • Assuming an application-scoped cache is shared across servers — it is per JVM.
  • Prototype everywhere "to be safe" — wasted objects; use it only where state is per-operation.

2 · A singleton bean (the default) and a prototype bean

package fintech.beanscope;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Component;

@Component                                   // no @Scope -> SINGLETON (the default)
public class InterestCalculator {

    public InterestCalculator() { System.out.println("InterestCalculator created"); }

    @PostConstruct void ready()   { System.out.println("InterestCalculator ready"); }
    @PreDestroy    void cleanup() { System.out.println("InterestCalculator destroyed"); }

    public double simpleInterest(double principal, double ratePercent, int years) {
        return principal * ratePercent * years / 100;      // stateless: no fields that change
    }
}

package fintech.beanscope;

import jakarta.annotation.PreDestroy;
import java.util.UUID;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

@Component
@Scope("prototype")                          // a NEW instance every time it is requested
public class TransactionContext {

    private final String transactionId = UUID.randomUUID().toString().substring(0, 8);
    private double amount;                   // per-operation state: safe because it is not shared

    public TransactionContext() { System.out.println("TransactionContext created: " + transactionId); }

    @PreDestroy void cleanup() { System.out.println("never printed - Spring doesn't destroy prototypes"); }

    public String getTransactionId() { return transactionId; }
    public double getAmount() { return amount; }
    public void setAmount(double amount) { this.amount = amount; }
}

3 · Same object or new object? — the demo and its output

package fintech.beanscope;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class BeanScopeApp {
    public static void main(String[] args) {
        AnnotationConfigApplicationContext ctx = new AnnotationConfigApplicationContext(AppConfig.class);

        InterestCalculator c1 = ctx.getBean(InterestCalculator.class);
        InterestCalculator c2 = ctx.getBean(InterestCalculator.class);
        System.out.println("singleton same object? " + (c1 == c2));              // true

        TransactionContext t1 = ctx.getBean(TransactionContext.class);
        TransactionContext t2 = ctx.getBean(TransactionContext.class);
        System.out.println("prototype same object? " + (t1 == t2));              // false
        System.out.println(t1.getTransactionId() + " vs " + t2.getTransactionId());

        ctx.close();                         // destroys singletons; prototypes are not touched
    }
}

4 · A singleton shared by threads — the bug and the fix

@Component                                   // singleton: ONE instance for ALL request threads
public class FeeCalculator {

    private double amount;                   // BAD: shared mutable state

    public double fee(double amt) {
        this.amount = amt;                   // thread A stores 1000 ...
        // ... thread B stores 50 here, before A reads it back
        return this.amount * 0.01;           // A may now compute the fee on 50 - a wrong result
    }
}

// FIX 1 - keep singletons stateless; use local variables and parameters
public double fee(double amount) { return amount * 0.01; }

// FIX 2 - if state is unavoidable, make it per-operation (prototype, or request scope in a web app)
//         or use thread-safe types (AtomicLong, ConcurrentHashMap).

5 · A prototype inside a singleton — the trap and the fix

// WRONG: TransferService is created once, so it gets ONE TransactionContext for its whole life
@Component
public class TransferService {
    private final TransactionContext context;
    public TransferService(TransactionContext context) { this.context = context; }
}

// RIGHT: ask for a fresh prototype each time through an ObjectProvider
@Component
public class TransferService {

    private final ObjectProvider<TransactionContext> contextProvider;

    public TransferService(ObjectProvider<TransactionContext> contextProvider) {
        this.contextProvider = contextProvider;
    }

    public void transfer(double amount) {
        TransactionContext ctx = contextProvider.getObject();   // a NEW instance on every call
        ctx.setAmount(amount);
        System.out.println("Transferring " + ctx.getAmount() + " under " + ctx.getTransactionId());
    }
}
// import org.springframework.beans.factory.ObjectProvider;

7 · The web scopes — request, session, application (for a Spring MVC / Spring Boot web app — the part the instructor said comes later)

import org.springframework.web.context.annotation.ApplicationScope;
import org.springframework.web.context.annotation.RequestScope;
import org.springframework.web.context.annotation.SessionScope;

@Component
@RequestScope                                 // a new bean for every HTTP request
public class RequestAudit {
    private final String correlationId = UUID.randomUUID().toString();
    private final long startedAt = System.currentTimeMillis();
    // getters ...
}

@Component
@SessionScope                                 // one bean per logged-in user session
public class CustomerSession implements java.io.Serializable {
    private String customerId;                // keep sensitive data out of long-lived beans
    private java.time.Instant loggedInAt;
    // getters/setters ...
}

@Component
@ApplicationScope                             // ONE bean for every user of the web application
public class ExchangeRateCache {
    private final java.util.Map<String, Double> rates = new java.util.concurrent.ConcurrentHashMap<>();
    // shared by all threads, so thread-safe structures are a must
}

// The annotations above are shortcuts for, e.g.:
// @Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)

🏦 5 · Real-World Use Cases

🧠 Added The FinTech picture, and what each choice does to a production system.

ScopeFinTech examplesWhy that scopeWhat can go wrong in production
SingletonInterestCalculator, FeeCalculator, AccountService, repositories, a payment-gateway clientStateless logic: one shared instance is enough and cheapestA mutable field turns it into a data leak between customers and an intermittent wrong-amount bug under load
PrototypeTransactionContext, a statement/receipt builder, a one-time challenge objectEach operation needs its own stateOver-use churns memory; resources inside it are never closed by Spring; injected into a singleton it silently becomes a singleton
RequestRequest audit (correlation ID, start time, caller IP), a per-request risk scoreData that belongs to a single callNot available outside web threads (jobs, schedulers); needs proxies when injected into singletons
SessionLogged-in customer's profile, a multi-step loan-application draftFollows one user across requestsMemory grows with active users; replication or sticky sessions in a cluster; sensitive data lingering until timeout
ApplicationExchange-rate cache, bank-holiday calendar, feature flagsOne read-mostly copy for everybodyConcurrent updates need thread-safe structures; stale data; one copy per server, so servers can disagree
Design rule of thumb
  • Holds nothing that changes → singleton.
  • Holds state for one operation → prototype (fetched through an ObjectProvider if a singleton needs it).
  • Holds state for one HTTP request → request; for one logged-in user → session.
  • Holds read-mostly data for everyone → application (or a singleton) with thread-safe structures.

💼 6 · Interview Questions and Answers

🧠 Added Standard Spring answers, not lecture statements.

Q1What is a Spring bean?
An object created and managed by the Spring IoC container — you define the class and ask the container for the object instead of calling new.
Q2What is bean scope and why do we need it?
Scope defines how many instances of a bean exist, when they are created, who shares them and when they end. Without it you would over-create objects or share objects that should be private to one operation, request or user.
Q3What is the default scope?
Singleton — one instance per bean definition per container. No annotation means singleton.
Q4Singleton vs prototype?
A singleton is created once (at startup by default) and shared by everything; Spring manages its whole life cycle, and it must be stateless or thread-safe. A prototype is created anew on each request for the bean, can hold per-operation state, and Spring runs only its creation and initialisation — never its destruction callbacks.
Q5Is Spring's singleton the same as the GoF Singleton pattern?
No. The GoF pattern restricts the class to one instance per JVM. Spring's singleton is one instance per bean definition per container: define the class under two names and you get two instances, and two containers each have their own.
Q6When is a singleton bean created — startup or first use?
An ApplicationContext creates singletons eagerly at startup, so wiring errors surface immediately; @Lazy postpones creation to first use. Prototypes are always created on demand.
Q7Does Spring call @PreDestroy on prototype beans?
No. The container creates, injects and initialises a prototype, then hands it over and stops tracking it. Releasing resources is the caller's responsibility.
Q8Are singleton beans thread-safe?
Not automatically. All request threads share the one instance and Spring doesn't synchronise it. Keep it stateless (local variables, parameters), or hold only immutable or thread-safe state; put per-operation state in a prototype or per-request state in a request-scoped bean.
Q9What are the request, session and application scopes, and what do they need?
Request: one bean per HTTP request. Session: one per HTTP session (one user). Application: one per web application, shared by every user. All three are web scopes — they need a web-aware context (Spring MVC/Boot); in a console program asking for one fails with "No Scope registered for scope name…".
Q10100 users are connected. What does each scope give them?
Application: all 100 see the same bean (the lecture's example). Session: each user has their own, shared across that user's requests. Request: a fresh one for every request, even from the same user. Singleton: one bean for all of them, shared by concurrent threads. Prototype: a new one at each lookup or injection.
Q11How do you configure a scope?
@Scope("prototype") on a @Component class or a @Bean method; scope="prototype" in XML; or @RequestScope / @SessionScope / @ApplicationScope for the web scopes.
Q12A prototype bean injected into a singleton behaves like a singleton. Why, and how do you fix it?
The singleton is created once, so injection happens once and it keeps that one prototype instance. Inject an ObjectProvider<T> and call getObject() on each use, use @Lookup method injection, use a scoped proxy, or fetch the bean from the context.
Q13What is a scoped proxy and when is it needed?
A proxy injected in place of a shorter-lived bean (request, session) inside a longer-lived one (a singleton). Each call on the proxy is routed to the instance for the current request or session. Without it the singleton would capture one instance at startup — and for request scope there is no request at startup at all. The web-scope shortcut annotations enable it by default.
Q14Which scope would you choose for (a) an interest calculator, (b) a customer's logged-in profile, (c) an exchange-rate cache, (d) a per-transfer context?
(a) Singleton — stateless. (b) Session — follows one user. (c) Application (or a singleton) with a thread-safe map — shared and read-mostly. (d) Prototype — state for one operation, fetched via an ObjectProvider if a singleton uses it.
Q15How do singletons behave in a cluster of servers?
"One instance" means one per JVM. Three servers hold three copies, and an application-scoped cache is likewise per server — so caches can drift apart, and session beans need replication or sticky sessions.
Q16How would you prove a bean's scope in a test?
Fetch it twice from the context and compare with == (singleton true, prototype false), and count constructor calls with a counter or a print statement.
