Recap of the Previous Class

What Is a Dependency? — The E-Commerce Example

When you develop a system you write your own code, but to complete it you need many dependencies. You are not going to develop anything from scratch — you use functionality that somebody else has already developed. Imagine a Java e-commerce backend:

Your system needs…You don't build it — you use…
Payment / encryptionA payment (encryption) JAR
Sending emailAn email-functionality JAR
Sending SMSAn SMS JAR (integration with an SMS gateway)
Database accessThe database's JAR (e.g. to connect your program to MySQL you need the MySQL JAR)
MathematicsA math-functionality JAR
Maps / navigationA Google Maps / navigation JAR

All of these JARs act as dependencies of your backend system. Your program cannot connect to MySQL until you use the MySQL JAR, and cannot send messages until it integrates with the SMS gateway code/JAR.

What Is Inside a Dependency JAR?

Why was the payment service a dependency for the order service? Because the payment service was developed by somebody else and you want to use it in your order service. The bytecode / .class files are part of the JAR, and you give that JAR as a dependency.

One Dependency ≠ One JAR
  • A system might need 20 JARs, 5, 3 or 2.
  • In a typical project the instructor said you'll have hundreds of dependencies (he quoted 500 to 1,000 at one point, and "20–30 different types of JARs" at the end — the numbers were rough).
  • One dependency can bring multiple JARs with it (you'll see this in the demo).
The Biggest Problem — Managing Dependencies and Versions
  • JARs keep evolving. Today you use SMS JAR 1.0; after 6 months it becomes 1.5 with new functionality. Versions keep changing.
  • How do you manage 500 JARs? And what if you have a team of 20 developers?
  • Example from class: the project uses SMS 1.0, but one developer used 1.2. His functionality worked on his side, but failed in production because production expected 1.0.
Why Yesterday's Manual Approach Doesn't Scale

Yesterday we managed the dependency by keeping one JAR file on the local disk. That is not a great idea:

  • It only works for one JAR. What about 1,000 JARs with different versions?
  • The JAR sits on my local disk. With a team of 20 who must all use version 1.3, I cannot control who downloads what — one uses 1.0, another 1.2.
  • If I set up a new machine, I'd have to copy all the JARs over — with 1,000 JARs that's not feasible; you'd waste your time just on setup.
Maven to the Rescue — A Build Tool
  • This problem is solved by Maven — a build tool.
  • If someone asks "Which build tool are you using?" — you say Maven. Others exist, such as Gradle (and SBT). If you have experience with Maven, you can work with any of them.
  • Maven isn't something technical to memorise — it's part of the process. The instructor's view: "Without Maven you cannot even work one day in a company."
What Does "Build" Mean?
  • Build = compile + package. Compile the code, then bundle the classes into a JAR (package).
  • Don't think that pressing Ctrl+S (the IDE compiling) is the build — that's only local. When you give a release to QA, they need only JAR files, so someone must compile the code and create them.
  • For a real product — 20,000 class files, hundreds of JARs — compilation can take 10, 20, even 30 minutes.
What Maven Does
  1. Builds your code (compiles it).
  2. Creates the package — puts your classes inside the JAR file.
  3. Manages your project structure overall.
  4. Manages your dependencies — you don't supply JARs from your local system. You just say "I want the SMS JAR, version 1.3" and Maven gets it for you. Dependencies are nothing but JAR files.
  5. Plus other features related to your build and deployment.
pom.xml — The Brain of Maven

pom.xml (the instructor guessed it stands for "project object model") is the brain of the entire Maven. Whatever your requirements are, write them in pom.xml: "I want to compile; my JAR should be named X.jar; to create it I need these dependencies" — and Maven automatically gets all the dependencies.

  • You don't have to remember everything from day one. From today, pom.xml will come up every day.
  • After 10–15 days you won't worry about it — adding a dependency becomes part of your day-to-day activity: just add it inside pom.xml.
  • It's an interesting topic with no heavy technicality — you just need to understand the system.

Creating a Maven Project in Eclipse

So far we created projects with New → Java Project. Now use the Maven Project option:

  1. New → Maven Project, then Next.
  2. Choose the archetype catalog: Internal. (If Internal doesn't work, use Central.) The list takes some time to load.
  3. For a core Java standalone project, choose the quickstart archetype (whatever version is shown). It creates the basic project structure.
  4. Fill in Group ID, Artifact ID, Version and Package (see the table below), then Finish.
  5. Maven needs internet while doing this — a log scrolls by as it generates the project.

You get a basic structure with a "Hello World" app — no code to write yet; this was just for exploring.

SNAPSHOT — What Does It Mean?

SNAPSHOT is a naming convention meaning "work in progress". The JAR will change later as well, so people should be careful while using a snapshot JAR. When you know a version is final, remove the word SNAPSHOT — which is what the instructor did while creating his project.

What the Generated Project Gives You
  • A Hello World app in the main code folder, and a separate test folder meant for unit testing ("we'll understand why they write tests" — covered in later classes).
  • A Maven Dependencies entry showing the JARs the project uses.
  • The system assumes you'll write test cases, so it gives you JUnit by default.
  • In pom.xml, a <dependencies> tag; under it each <dependency> is one JAR addition.
  • If you remove a dependency and save, it disappears from the project's Maven Dependencies too.
Adding a Dependency — Step by Step

Say Infosys Finance wants email-related functionality. Downloading the JAR and asking everybody to download it is not the right way — Maven manages it instead; you just give Maven an instruction.

  1. In Google, type the keyword of the JAR you want + "maven dependency".
  2. Open the Maven repository website result (the mvnrepository.com style page).
  3. Pick your version — multiple versions are listed, so choose by your requirement.
  4. The page shows copy-ready snippets for different build tools (Gradle, SBT and others). Since we use Maven, copy the Maven snippet.
  5. Paste it inside <dependencies> in pom.xml.
  6. Save. Maven downloads the JAR from the Maven Central repository over the internet.
  7. The JAR appears under Maven Dependencies and is on your class path — you can use its classes in your code.

You never download anything yourself: whatever JAR you need, find it, copy the dependency, paste, and the JAR comes.

The Demo — One Dependency Brought Many JARs

When the instructor added a second library, the Maven Dependencies list grew by several JARs. That is not your worry: you only told Maven "bring this functionality/JAR"; the library uses other JARs internally, and Maven fetched all of them. This is what makes JAR management easy.

The exact libraries used in the instructor's demo were garbled in the transcript (an SMS library and a Google library), so I don't name them here.

Maven Central Repository
  • A central repository over the internet that holds all the possible JARs, in categorised locations.
  • It is open source and free to use.
  • The instructor quoted about 64 million artifacts ("six and a half crore"; he later said "66 million"). Treat it as approximate — the number changes. His point: if you can't find a JAR with your keyword, you're probably searching in the wrong direction.
  • It is saying, in effect: "your build tool can connect to our central repository and download the JAR file."
  • You can even upload your own JAR to it; once approved, people start using it.
How It All Works — End to End
  1. Your project uses Maven, and you tell Maven what you need through pom.xml ("I need these two dependencies").
  2. Maven knows where to connect — by default the Maven Central repository on the internet, and it knows where those artifacts live.
  3. Maven says "give me these JARs", connects, and downloads them.
  4. They're stored on your local machine — your system runs locally.
  5. From the local system, Eclipse / your code refers to those JARs.

Why internet? Because Maven must fetch the JARs from the public repository the first time. Without internet you can't get new JARs; once they're downloaded, you can work without it.

The Local Repository — the .m2 Folder

Where do the downloaded JARs go? A student shared their screen to show it:

  • Open your user folder (e.g. C drive → Users → your user). Maven creates a .m2 folder there; inside it, a repository folder.
  • When you tell Maven "give me these JARs", it connects to the central repo, gets them, and drops them under .m2/repository.
  • Package-style folders appear inside — e.g. a student's JSON library from Google landed under com / google / code / gson.
  • You can verify it in Eclipse: expand Maven Dependencies, right-click a JAR → Properties, and look at its path — it points into your .m2/repository.
Local-First Rule
  • Whenever you give an instruction to Maven, it first checks whether the JAR is already in the local machine's .m2. If yes, it uses it.
  • Otherwise it goes to the remote repository, downloads the file, drops it into .m2, and then uses it.
  • So if nothing changes, internet isn't required; it's needed only the first time you ask for a JAR/version.
  • Q (student): a second project needs the same JSON dependency — central repo or local? A: Local only. The .m2 path is not specific to any project — it's the user's .m2 home, so on one system you might use the same JAR in 500 projects without downloading it again (same version).
How Companies Really Do It — Local (Private) Repository and the Security Team
  • Imagine someone uploads a fake JAR with a virus to the public repository and it somehow gets approved. A bank that blindly uses it could be in trouble. With so many JARs, nobody knows how many are corrupted.
  • So a company does not connect to Maven Central directly. Instead it has a local repository (also called the company/private repo) — inside the company network, not on your own computer.
  • That repo holds only a subset of the ~66 million JARs, because no company needs them all.
  • How JARs get in: your manager/director gives a list of required JARs to the (information) security team. They download from the public repo, scan for viruses, mark them approved, and drop them into the local repo.
  • When you join a team and use Maven, it points to this local repo, so your JARs come from there.
  • If a JAR you need isn't in the local repo: raise a ticket to the security team — "this JAR isn't available in our company; please get it from the public repo". They fetch, scan, and add it.
  • It can take days (the instructor joked about "10 days") — the point being that real work is largely about process, and people can use blockers as an excuse.
settings.xml — Which Repository Does Maven Talk To?
  • How does Maven decide whether to connect to the public repo or the company's local repo? Through settings.xml.
  • The configuration of your company's local repository is kept here — including username and password if needed.
  • If nothing is configured, Maven connects by default to the central/public repo — not advisable in a company.
  • It lives in your .m2 home directory. In practice: when your setup isn't working on day one, an expert will ask for the settings.xml; a colleague may send you the file with no explanation — drop it into your .m2 directory.
  • Distinguish: pom.xml says what your project needs; settings.xml says which repository Maven should talk to.
Packaging the Project into a JAR (Build Demo)
  • The project's target folder is empty to begin with.
  • To build: right-click the project → Run As → Maven build (the transcript doesn't capture the goal that was typed).

Other Build Tools — Does the Choice Matter?
  • The same way there are 50+ programming languages, there are several build tools — different people built them with different implementations; it's also a market competition ("I'm giving you Gradle, slightly better in this area").
  • Most common: Maven and Gradle; SBT is used in places. The instructor estimated 70–80% of people use Maven.
  • Some tools use Groovy scripts internally; people comfortable with Groovy may prefer Gradle (the instructor also mentioned Kotlin-style scripts for Gradle).
  • All do the same work: dependency management, connecting to the central repo, giving you dependencies, building your project, managing project structure.
  • Difference he showed: in Gradle a dependency is a single line, whereas Maven's is an XML block — in some cases dependency management is easier, in others you write more script.
  • For you it doesn't matter: you know there's a central repo, a local repo, and a build file where you keep pasting the dependency snippet for your tool. The company decides which tool to use.

💡 Added clarification — terms and details the lecture didn't spell out:
  • Maven coordinates (GAV): GroupId + ArtifactId + Version uniquely identify an artifact. Every dependency snippet you paste is exactly these three values.
  • Transitive dependencies: the "extra JARs that came along" are called transitive dependencies — a dependency's own dependencies, resolved automatically by Maven. You can inspect them with mvn dependency:tree.
  • How the folder path is built: the Group ID's dots become folders — com.google.code.gson → com/google/code/gson/<artifactId>/<version>/<artifactId>-<version>.jar — which is exactly why the student saw com / google / code / gson. Different versions of the same library sit side by side in separate version folders.
  • .m2 is created on first use: it appears in your user directory the first time Maven runs/downloads something (the lecture said "whenever you install Maven").
  • Build phases, not just "build": Maven's lifecycle includes clean, compile, test, package, install and deploy. The demo created a JAR, which is the package phase (typically mvn clean package); install additionally copies the JAR into your .m2; deploy pushes it to a remote repository. The lecture didn't name these.
  • Dependency scope: the default JUnit dependency in a quickstart project normally has <scope>test</scope>, meaning it's only available for tests, not packaged into your app's runtime.
  • SNAPSHOT behaviour: Maven treats -SNAPSHOT versions as changing, so it may re-fetch them; fixed release versions are not expected to change.
  • Repository managers: companies typically run tools such as Nexus or Artifactory as the local/private repository. The instructor didn't name them.
  • Mirrors: in settings.xml a company usually declares a <mirror> that redirects requests for the public repository to the internal one.
  • Eclipse refresh: after editing pom.xml, if the IDE doesn't pick it up, use right-click project → Maven → Update Project.
  • Maven needs a JDK (a compiler), not just a JRE — a likely explanation for the JDK/JRE confusion in the demo, though the transcript doesn't confirm it.

import com.google.gson.Gson;

public class App {

    static class Customer {
        String name;
        String type;
        Customer(String name, String type) { this.name = name; this.type = type; }
    }

    public static void main(String[] args) {
        Gson gson = new Gson();                                  // class from the downloaded JAR

        System.out.println(json);                                // {"name":"Asha","type":"Gold"}
    }
}

Which build tool do you use? Are there others?Maven; others are Gradle and SBT. They do the same work — dependency management, building, structure; Maven is the most common.
What is pom.xml?The brain of Maven — you write your build requirements and dependencies there.
How do you add a dependency in Maven?Find it on the Maven repository website, pick the version, copy the Maven snippet, paste it inside <dependencies> in pom.xml, and save.
What is the Maven Central repository?A public, free, internet-based repository holding all possible JARs (millions); Maven downloads from it by default.
Where does Maven store downloaded JARs? Does it download every time?In the local .m2 repository under the user directory. It checks there first and uses the local copy; it downloads only if the JAR/version isn't present.
Why does Maven need internet?To fetch JARs from the public repository the first time; afterwards, with JARs cached locally, it isn't needed.
Why don't companies connect directly to Maven Central?Security — public JARs could be corrupted or carry viruses. Companies use a private repository with JARs approved and scanned by the security team.
What if a JAR you need isn't in the company repo?Raise a ticket to the security team to fetch it from the public repo, scan it, and add it.
What is settings.xml and where does it go?It decides which repository Maven connects to (and holds credentials). It lives in the .m2 directory. With nothing configured, Maven uses the public Central repo.
pom.xml vs settings.xml?pom.xml is per project and says what the project needs; settings.xml is per machine and says where Maven gets things from.
What are Group ID and Artifact ID? What is SNAPSHOT?Group ID = group/business area; Artifact ID = project name; SNAPSHOT = work-in-progress version that can change.
How do you create the JAR with Maven? Where does it appear?Run a Maven build (compile then package); the JAR appears in the project's target folder, named from artifact ID and version.

What are Maven coordinates (GAV)?groupId, artifactId and version — together they uniquely identify an artifact.
What are transitive dependencies?Dependencies of your dependencies; Maven resolves and downloads them automatically. Inspect with mvn dependency:tree.
What are the main Maven build phases?clean, compile, test, package, install, deploy — each phase runs the earlier ones in its lifecycle first.
Difference between package, install and deploy?package creates the JAR in target; install also copies it to your local .m2; deploy publishes it to a remote repository.
What does <scope>test</scope> mean?The dependency (e.g. JUnit) is available only for compiling/running tests, not in the packaged application.
Two projects need different versions of the same library — what happens?Both versions can sit in .m2 in separate version folders; each project uses what its own pom.xml declares.

📌 Lecture Takeaways

  • Real systems depend on many JARs (email, SMS, database, payment, maps…) — you reuse, not rebuild.
  • Manual JAR handling breaks down: version mismatches, team inconsistency, painful machine setup.
  • Maven is the build tool that solves this; build = compile + package.
  • Maven builds, packages, manages project structure and dependencies.
  • pom.xml is the brain — you declare your dependencies there.
  • Create projects with New → Maven Project (quickstart archetype); know Group ID, Artifact ID, version, SNAPSHOT.
  • To add a dependency: search "jar name + maven dependency" → copy the snippet → paste inside <dependencies> → save.
  • Maven Central is the public repo with millions of JARs; Maven needs internet to fetch from it the first time.
  • Downloaded JARs go to .m2; Maven checks local first; .m2 is not project-specific.
  • Companies use a private repo filled with security-scanned JARs; missing JAR → ticket to security team.
  • settings.xml (in .m2) decides which repository Maven talks to.
  • A Maven build creates the JAR in target; refresh to see it; target can be deleted and regenerated.
  • Gradle/SBT do the same job; most companies use Maven; the company decides.

🚧 Common Interview Traps

  • "One dependency = one JAR." A single dependency can bring several JARs along.
  • "Build is just pressing Ctrl+S / compiling in the IDE." Build means compile and package into JARs.
  • "Maven always needs internet." Only the first time for a new JAR/version; afterwards it uses the local .m2.
  • "The .m2 folder belongs to a project." It's per user and shared by all projects on the machine.
  • "Companies download from Maven Central directly." They use a private repo of security-approved JARs.
  • Mixing up pom.xml and settings.xml. Project needs vs repository location/credentials.
  • Using a SNAPSHOT as if it were final. It can change; be careful.
  • Not refreshing the project and concluding "the JAR wasn't created".
  • Thinking the build-tool brand matters. They do the same job; the company chooses — but be able to explain Maven.
