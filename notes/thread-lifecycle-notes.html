🧠 Key Concepts

Recap: Creating and Starting a Custom Thread 
class EmailSender extends Thread {
    @Override
    public void run() {
        System.out.println("Sending email");
    }
}
EmailSender emailSender = new EmailSender();
emailSender.start(); // launches a NEW thread
Why You Can't Meaningfully "Debug" Multi-threaded Code the Normal Way

Normal (single-threaded) debugging works because execution is synchronous — you know exactly what happens next, one line at a time. Multi-threaded execution is asynchronous — you don't know WHEN the CPU will grant time to which thread. Attempting to step through a thread in a debugger often causes you to "lose control," since the CPU's scheduling decisions don't wait for your debugger's pace.

Two Threads Running "in Parallel" — Recap

In a basic custom-thread program, you actually have TWO threads: the main thread (created automatically by JVM, responsible for executing main()) and your custom thread (created by calling .start()). Both run independently/concurrently once the custom thread has started.

The Thread Lifecycle — Compared to the Human Life Cycle

The instructor drew a direct parallel: a human is born, works, and eventually dies — with no "rebirth." A Java thread follows the exact same one-way pattern: it's created, it performs its task, and once done, it terminates — permanently, with no possibility of restarting it afterward.

The Six Thread States
StateMeaning
NEWA Thread object has been created, but .start() has NOT been called yet
RUNNABLE.start() has been called — the thread is eligible/ready to run, but the CPU hasn't given it execution time yet
RUNNINGThe CPU has granted time, and the thread is actively executing its run() method
WAITING / BLOCKEDThe thread has been paused/interrupted mid-execution due to some condition, and is temporarily set aside
TIMED_WAITINGA more specific variant of waiting (distinguished from plain blocked/waiting) — exact distinction flagged as a topic for later
TERMINATEDThe run() method has fully completed — the thread has died and can never run again
NEW → RUNNABLE: Triggered by .start()

The moment a Thread object is created, its state is NEW. Calling .start() on it immediately changes the state to RUNNABLE — meaning the thread is now ready and requesting CPU time, but hasn't necessarily received it yet.

RUNNABLE → RUNNING: Only When the CPU Grants Time

Example given: launch 100 threads on a single-core CPU. At any given moment, only 1 thread can actually be in the RUNNING state (genuinely executing) — the other 99 remain in RUNNABLE, waiting their turn. This switching happens at the scale of fractions of a millisecond/microsecond/nanosecond.

RUNNING → WAITING/BLOCKED — The "Study Break" Analogy

Analogy: imagine you're studying (RUNNING) at a shared table, and something interrupts you — you step outside for a while (WAITING/BLOCKED). Critically: while you're away, someone else can take your spot. When your break ends, you don't magically resume exactly where you left off — you go back to being RUNNABLE (ready, requesting a spot again), and must wait for the CPU to grant you RUNNING status once more, just like any other waiting thread.

RUNNING → TERMINATED: Once run() Fully Completes

Once a thread's run() method finishes executing completely (whether it was one line or hundreds), the thread's state becomes TERMINATED — its lifecycle is over.

The Golden Rule: TERMINATED is Final — No "Rebirth"

Once a thread reaches TERMINATED, it is permanently done. You cannot call .start() on it again to bring it back to life.

What Actually Happens If You Try to Restart a Terminated Thread

Calling .start() on an already-TERMINATED thread throws an IllegalThreadStateException. The underlying rule: .start() can only be called successfully when a thread's current state is NEW — calling it from any other state (including TERMINATED) fails.

🔥 Classic Interview Trap — Flagged Explicitly

Interviewers commonly present code that starts a thread, lets it finish, then calls .start() on the SAME thread object again — asking "what will this print? Will 'Sending email' print twice?" Candidates who answer "yes, it prints twice" are giving themselves away as not understanding the thread lifecycle — this is described as an immediate, high-confidence rejection signal for interviewers, not a minor point deduction. The correct answer: it throws IllegalThreadStateException — a terminated thread can never be restarted.

Checking Thread State Programmatically — getState()

Java provides thread.getState() to inspect a thread's current lifecycle state directly — useful for understanding NEW vs RUNNABLE vs TERMINATED transitions while learning.

Important Practical Caveat: Don't Rely on Printed States for Verification

Explicitly warned: don't structure real learning/testing around printing a thread's state to "prove" what state it's in at a given moment. Because state transitions happen at such extreme speed (fractions of a nano/micro/millisecond), the exact moment you print might not accurately capture the state you intended to observe — the print statement itself can be "too slow" relative to how fast the actual state is changing.

Calling run() Directly — Why It Stays Single-Threaded

Demonstrated directly: if you skip .start() and call .run() directly on your thread object, the ENTIRE program remains a single-threaded program — only ONE thread exists in total (the main thread). This is because .start() is specifically what registers a new thread with the thread scheduler and allows it to actually execute independently; calling .run() directly just treats it as an ordinary method call, executed by whichever thread called it (main).

Practical Exercise: Two Threads Printing Numbers 1–20

Exercise given: write a program using 2 threads, each printing numbers from a loop (up to ~20), while also printing the executing thread's name/ID alongside each number. Running this repeatedly showed the CPU granting varying, unpredictable amounts of consecutive execution time to each thread — sometimes Thread 0 printed 3 numbers before switching to Thread 1, other times Thread 1 got a longer uninterrupted stretch. The key takeaway, reinforced yet again: you cannot predict this pattern — it depends entirely on the CPU's scheduling decisions at runtime.

On Feeling Confused While Learning This

A piece of encouragement offered directly: "If you're getting confused, that means you're learning. If you say you already understand everything immediately, that's not actually true." Multithreading is explicitly framed as a topic where genuine understanding comes gradually, through repeated hands-on practice — not instant clarity.

💻 Code Snippets / Examples

Checking thread state at each stage:

class EmailSender extends Thread {
    @Override
    public void run() {
        System.out.println("Sending email");
    }
}
EmailSender t1 = new EmailSender();
System.out.println(t1.getState()); // NEW — object created, start() not called yet

t1.start();
System.out.println(t1.getState()); // Likely RUNNABLE (or possibly already TERMINATED,
                                    // since this simple task completes almost instantly —
                                    // remember: don't rely on this print for precise verification!)

The classic interview trap — restarting a terminated thread:

EmailSender t1 = new EmailSender();
t1.start(); // prints "Sending email" — thread completes, moves to TERMINATED

t1.start(); // throws java.lang.IllegalThreadStateException
            // A terminated thread can NEVER be started again

Calling run() directly — stays single-threaded:

EmailSender t1 = new EmailSender();
t1.run(); // NOT t1.start() — just an ordinary method call

System.out.println(Thread.currentThread().getName());
// Output: main (both "Sending email" AND this line were executed by the SAME main thread)
// Only ONE thread exists in this entire program

Practical exercise — two threads printing numbers, observing unpredictable switching:

class NumberPrinter extends Thread {
    public NumberPrinter(String name) {
        super(name); // set a custom thread name
    }

    @Override
    public void run() {
        for (int i = 1; i <= 20; i++) {
            System.out.println(Thread.currentThread().getName() + " - " + i);
        }
    }
}
NumberPrinter t1 = new NumberPrinter("Thread-A");
NumberPrinter t2 = new NumberPrinter("Thread-B");

t1.start();
t2.start();

// Run this multiple times — you'll see DIFFERENT interleaving patterns each time:
// Thread-A - 1
// Thread-A - 2
// Thread-A - 3
// Thread-B - 1
// Thread-B - 2
// Thread-A - 4
// ... (completely unpredictable, CPU-dependent switching)

❓ Doubts / Questions Raised in Class

QuestionAnswer
Can a terminated thread be restarted?No — this is a permanent, one-way transition. Attempting to call start() again throws IllegalThreadStateException.
What exactly triggers IllegalThreadStateException?Calling .start() when the thread's current state is anything OTHER than NEW (most commonly, calling it again after the thread has already reached TERMINATED).
If a thread goes from RUNNING to WAITING and then resumes, does it go directly back to RUNNING?No — it goes back to RUNNABLE first, and must wait for the CPU to grant it execution time again, exactly like any other thread requesting a turn.
Why does calling run() directly (instead of start()) result in a single-threaded program?Because .start() is specifically what registers a new thread with the thread scheduler and launches independent execution; calling run() directly just executes it as a normal method call on whichever thread called it.
Should I print a thread's state in my code to verify its current lifecycle stage?Be cautious — state transitions happen extremely fast, and a print statement may not accurately capture the exact state at the intended moment.

📌 Important Points / Common Mistakes

  • The six thread states: NEW, RUNNABLE, RUNNING, WAITING/BLOCKED, TIMED_WAITING, TERMINATED.
  • NEW → RUNNABLE happens via .start(). RUNNABLE → RUNNING happens only when the CPU grants execution time.
  • A thread interrupted mid-execution goes to WAITING/BLOCKED, then back to RUNNABLE (NOT directly back to RUNNING) once ready to resume.
  • TERMINATED is final — a thread can NEVER be restarted once it reaches this state. This is a guaranteed interview question.
  • Calling .start() on a non-NEW thread (especially a TERMINATED one) throws IllegalThreadStateException.
  • Calling .run() directly instead of .start() does NOT create a new thread — it just runs as a normal method call on the current thread.
  • Don't rely on printing getState() output for precise verification — timing is too fast and unpredictable for reliable observation this way.
  • Thread execution order/interleaving remains fundamentally unpredictable — entirely dependent on CPU scheduling decisions.
