🧠 Key Concepts

Critical Clarification: All Exceptions Occur at Runtime

A common point of confusion: "checked" and "unchecked" do NOT refer to when the exception is thrown — every exception, without exception, is thrown at runtime. The distinction is about whether the compiler forces you to provide handling (try-catch or throws) before it will even let the code compile.

Unchecked (Runtime) Exceptions

Exceptions like NullPointerException, ArrayIndexOutOfBoundsException, and ArithmeticException — the compiler does not force you to handle these. Code compiles fine even without try-catch; if the exception occurs at runtime and isn't handled, the program terminates abnormally, but there's no compile-time obligation.

Checked (Compile-Time-Enforced) Exceptions

Exceptions like FileNotFoundException, IOException, SQLException, and ClassNotFoundException — the compiler forces you to provide a handling mechanism (try-catch, or declaring throws) before it will compile the code at all. These are considered serious enough (often representing scenarios where the operation fundamentally cannot proceed — e.g. the file/class simply doesn't exist) that Java mandates explicit acknowledgment.

Real-World Analogy — Amazon COD Restriction

Just as Amazon proactively blocks Cash-on-Delivery for certain PIN codes before you even place the order (because it already "knows" this won't work), the compiler proactively blocks compilation for checked exceptions it "knows about" — forcing you to address the risk upfront rather than letting it fail silently at runtime.

The Class Class and Dynamic Class Loading

Java has a built-in Class class with a method Class.forName("ClassName") used to dynamically load a class by name at runtime (commonly used with database drivers). If the specified class doesn't exist (e.g. due to a typo), it throws ClassNotFoundException — a checked exception, so the compiler requires it to be handled.

Static vs Dynamic Class Loading

Static loading — a class is loaded into memory automatically whenever you create an object of it directly (e.g. new SomeClass()). Dynamic loading — a class name is supplied at runtime (e.g. as a String) and loaded via Class.forName(), allowing flexibility in which class gets loaded without hardcoding it.

Exception Hierarchy — How to Tell Checked from Unchecked
Throwable
/    \
Error    Exception
        /    \
RuntimeException   (everything else under Exception)
   (UNCHECKED)      (CHECKED)

Any class that is a direct or indirect child of RuntimeException is an unchecked exception (e.g. NullPointerException, ArrayIndexOutOfBoundsException, ArithmeticException). Any class that's a child of Exception but NOT under RuntimeException is a checked exception (e.g. IOException, FileNotFoundException, SQLException, ClassNotFoundException).

throws Keyword — Declaring a Method May Throw

Written in a method's signature, throws tells the caller: "this method may throw this exception — you must handle it." It doesn't itself create or throw anything — it's a declaration/warning to whoever calls the method.

public String createUser(String username) throws NullPointerException {
    // ...
}
throw Keyword — Actually Creating and Throwing

throw is used inside a method's body to create a new exception object and throw it immediately: throw new SomeException("message");. This is how you communicate a meaningful, business-specific exception to the caller instead of letting a generic/technical one (like NullPointerException) leak through untranslated.

Why Translate Technical Exceptions into Meaningful Ones

A caller (and eventually an end user) usually doesn't care about "NullPointerException" — they need meaningful context like "Username is already taken" or "Insufficient balance." Catching a low-level technical exception and re-throwing a business-meaningful one lets the caller (and ultimately the UI) respond appropriately, instead of showing cryptic technical errors to end users.

Handle vs Throw — Two Valid Strategies

You don't always have to handle an exception yourself — you can also choose to simply declare throws and let the caller handle it, if that's more appropriate. Alternatively, you can catch a technical exception and throw a new, more meaningful one — combining both handling and throwing together.

What Happens If an Exception is Never Handled Anywhere?

If no method in the call chain handles it, the exception ultimately propagates all the way up to the JVM, which terminates the program abnormally — though in well-designed real systems, exceptions are meant to be handled or meaningfully translated well before reaching that point.

💻 Code Snippets / Examples

Unchecked exception — compiles without any handling:

String name = null;
int len = name.length(); // NullPointerException — compiles fine, no handling required

Checked exception — compiler REFUSES to compile without handling:

// This does NOT compile without try-catch or throws:
ObjectOutputStream os = new ObjectOutputStream(new FileOutputStream("file.txt"));
// ERROR: unhandled exception type FileNotFoundException
// Fixed with try-catch:
try {
    ObjectOutputStream os = new ObjectOutputStream(new FileOutputStream("file.txt"));
} catch (FileNotFoundException e) {
    System.out.println("File not found");
} catch (IOException e) {
    System.out.println("IO error occurred");
}

ClassNotFoundException — dynamic class loading:

try {
    Class.forName("com.example.SomeDriver"); // may not exist -> ClassNotFoundException
} catch (ClassNotFoundException e) {
    System.out.println("Class not found: " + e.getMessage());
}

throws — declaring a method may throw, letting the caller handle it:

class UserService {

    public String createUser(String username) throws NullPointerException {
        int length = username.length(); // may throw if username is null
        return "USR" + length;
    }

}
class Driver {
    public static void main(String[] args) {
        UserService service = new UserService();
        try {
            String userId = service.createUser(null);
        } catch (NullPointerException e) {
            System.out.println("Failed to create user: " + e.getMessage());
        }
    }
}

throw — translating a technical exception into a meaningful one:

class UserService {

    public String createUser(String username) throws Exception {
        try {
            int length = username.length();
            return "USR" + length;
        } catch (NullPointerException e) {
            throw new Exception("Username is not provided"); // meaningful message for the caller
        }
    }

}
class Driver {
    public static void main(String[] args) {
        UserService service = new UserService();
        try {
            String userId = service.createUser(null);
        } catch (Exception e) {
            System.out.println(e.getMessage()); // "Username is not provided"
            // caller can now take meaningful action, e.g. assign a default user ID
        }
    }
}

Business-meaningful exception example — user already exists:

public void createUser(String userId) throws Exception {
    boolean exists = checkIfUserExistsInDB(userId);
    if (exists) {
        throw new Exception("User already exists");
    }
    // proceed with creation...
}

Practice exercise — negative quantity validation:

class OrderService {

    public void placeOrder(String item, int quantity) throws Exception {
        if (quantity < 0) {
            throw new Exception("Quantity cannot be negative");
        }
        System.out.println("Order placed for " + quantity + " x " + item);
    }

}
class Driver {
    public static void main(String[] args) {
        OrderService service = new OrderService();
        try {
            service.placeOrder("Laptop", -5);
        } catch (Exception e) {
            System.out.println("Order failed: " + e.getMessage());
        }
    }
}

❓ Doubts / Questions Raised in Class

QuestionAnswer
Do checked exceptions get thrown at compile time?No — the exception is always thrown at runtime; only the requirement to HANDLE it is enforced at compile time.
What's the difference between throw and throws?throws (in the method signature) declares that a method may throw a given exception, informing callers they must handle it. throw (inside the method body) actually creates and throws a specific exception object at that point in the code.
If a method declares "throws SomeException" and also has a try-catch handling that exact exception internally, is that a conflict?Not a conflict, but redundant — if the method already fully handles the exception internally, there's no need to also declare throws for it, since the caller would never actually receive it.
Can a method throw multiple different exceptions?Yes — a method can declare multiple exception types in throws (comma-separated), and internally throw different specific exception objects depending on the scenario (e.g. "user already exists" vs "invalid input").
What happens if an exception is thrown all the way up without any catch anywhere?It eventually reaches the JVM, which terminates the program abnormally.

📌 Important Points / Common Mistakes

  • All exceptions occur at runtime — checked/unchecked only describes whether handling is compiler-enforced.
  • Checked exceptions (FileNotFoundException, IOException, SQLException, ClassNotFoundException) must be handled or declared with throws, or the code won't compile.
  • Unchecked exceptions (children of RuntimeException) don't require any compile-time handling.
  • throws goes in the method signature (declaration); throw is used inside the method body to actually create and throw an exception.
  • Translate low-level/technical exceptions into meaningful, business-specific ones before they reach the end user.
  • You can choose to handle an exception yourself, or declare throws and let the caller handle it — both are valid strategies depending on context.
