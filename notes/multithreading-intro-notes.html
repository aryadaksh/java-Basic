🧠 Key Concepts

What is Multi-threading?

Multi-threading means a piece of work is done by multiple threads at the same time, instead of one. Analogy: 50 chairs need to be moved out of a classroom. Scenario 1 (single-threaded): one person moves all 50 chairs alone. Scenario 2 (multi-threaded): 10 students each move a portion of the chairs simultaneously — roughly 5 chairs each, though the exact split varies (someone faster might do 6, someone slower does 4). The second approach is faster — that's the core advantage of multi-threading.

The Immediate Catch: You Cannot Predict Completion Order

With 10 people moving chairs, you cannot know in advance who finishes first. One student might be moving fast, then get an emergency phone call and pause for 20 seconds. The same happens with threads — a thread's execution can be paused/delayed unpredictably. Core rule introduced here, repeated throughout the entire class: in multithreading, you cannot predict the order of execution. Even if you observe the same order many times in a row, that does NOT mean it's guaranteed or fixed.

Process — A Running Application With Its Own Memory

A process is any running application that has been allocated its own memory. Examples: the JVM itself is a process; your web browser is a process; Eclipse is a process. Opening Task Manager (Ctrl+Shift+Delete on Windows) and viewing the process list shows exactly these — independent running applications, each with dedicated memory.

Thread — The Unit of Execution Inside a Process

A thread is the unit that actually performs work within a process. A process does not directly "do" anything by itself — the actual work is carried out by threads running inside it.

Task — The Actual Work Being Done

Whatever work a thread performs is called a task. Real-world example: a Payment process might need to (1) process the transaction, (2) update the account balance, (3) send a notification/SMS. Each of these is a task, and each task is carried out by a thread.

The Full Hierarchy
Process (e.g. JVM) — has its own memory
    └── Thread — unit of execution, does the work
        └── Task — the actual work performed
Even "Hello World" Requires a Thread

A direct, important point: without a thread, Java cannot function at all — not even printing "Hello World." When you run any Java program, the JVM (the process) automatically creates a thread to actually execute your code. There's no such thing as code running with "zero threads" in Java.

The Main Thread — Created Automatically by JVM

When you run a Java class, the JVM: (1) loads the class's bytecode into memory, (2) creates one thread, conventionally named "main." (3) That main thread's ONLY job is to execute the main() method. This happens automatically — you never explicitly create this thread yourself.

Finding Out Which Thread Executes Your Code

Thread.currentThread().getName() returns the name of whichever thread is currently executing that line of code. Running this inside a plain main() method (with no custom threads created) will always print "main" — confirming that even basic, single-threaded-looking code is still being run BY a thread.

Class Loading + Main Thread Creation — The Full Startup Sequence

When you tell Java to execute a class: the class's bytecode is loaded into memory (method area) → JVM creates a thread → that thread calls ClassName.main() as its assigned task. If no main() method exists, Java complains that the entry point is missing — because the automatically-created main thread has nothing to execute.

"Basics" in Software Includes Threads Too

A philosophical aside worth remembering: there's no clean separation between "basic" and "advanced" topics in software — if you claim your Java fundamentals are solid, that should include understanding threads too, since even the simplest program relies on one.

Two Ways to Create a Custom Thread

Java offers two approaches: (1) extending the Thread class (covered in this session), or (2) implementing the Runnable interface (mentioned as a separate topic for later). Today's focus is exclusively the Thread class approach.

Steps to Create a Custom Thread (Thread Class Approach)
  1. Create a class that extends Thread.
  2. Override the run() method — standard signature: public void run(), no parameters. This is fixed syntax that "hasn't changed in 30 years and won't change in the next 30."
  3. Write whatever logic/task you want the thread to perform inside run().
  4. Create an object of your custom thread class.
  5. Call .start() on that object — NOT .run() directly.
Why .start() and Not .run() Directly?

Calling .run() directly would just execute that method like any normal method call — on the SAME thread that called it (e.g. the main thread), with no actual new thread involved. Calling .start() is what actually creates a genuinely new thread of execution, which then internally invokes run() on ITS OWN separate execution path — going through the thread scheduler and CPU negotiation process.

Multiple Custom Threads — Demonstrating Unpredictable Order

Creating multiple thread objects (T1, T2, T3) from the same custom class and starting all of them live in class produced different output orderings on different runs — sometimes 0-1-2, sometimes 1-0-2, sometimes 2-0-1, and so on. This directly demonstrated, hands-on, that execution order is genuinely not fixed or predictable, even for the exact same code run repeatedly.

Why Order is Unpredictable — Thread Scheduler and CPU

Each thread, once started, must request permission from the CPU (via a JVM component called the Thread Scheduler) before it can actually run. The Thread Scheduler negotiates with the CPU on the thread's behalf. The CPU decides which thread gets to run and when — this decision is not first-come-first-served. A thread that requests first may still be denied if the CPU is currently busy with something else (even unrelated system-level work), while a thread that requests later might get approved sooner.

The Thread Scheduler Only Manages YOUR Threads

Clarified explicitly: the Thread Scheduler (part of the JVM) only negotiates for the small number of threads belonging to YOUR Java program — it has no involvement with threads from unrelated processes like your browser, YouTube, or Eclipse. Those are managed independently by the operating system/CPU alongside everything else.

CPU Context Switching — Why Things "Feel" Parallel

Even a single-core CPU can only genuinely execute one thread at a time — true simultaneous execution requires multiple cores. However, the CPU switches between different threads/tasks so incredibly fast (fractions of a nanosecond) that humans cannot perceive the switching at all — it FEELS like everything (music, browser, typing) is happening in parallel, even though, strictly at the CPU level, it's actually rapid switching between one task at a time.

When Context Switching Becomes Visible — Heavy Software

Real-world evidence of this switching: running a heavy game can cause background music or YouTube to visibly stutter/lag. This happens because the CPU must dedicate MORE time to the demanding software, leaving less switching capacity for everything else — you start to actually notice the previously-invisible switching overhead. Modern high-end, multi-core CPUs reduce (but don't eliminate) this effect by genuinely running more threads in true parallel.

The "Janta Darbar" Analogy for CPU Scheduling Priority

A vivid analogy for how the CPU decides thread order: in a "Janta Darbar" (a public grievance-hearing session held by a Chief Minister), people register in a queue with sequence numbers. But when an emergency arises (e.g. a flood requiring urgent resource deployment), the CM (playing the role of the CPU) skips ahead to handle that higher-priority matter — regardless of registration order. Similarly, requesting CPU time first (starting a thread first) does NOT guarantee getting executed first — the CPU is the central authority, weighing its own priorities (which may include totally unrelated system tasks) before deciding what runs next.

Parent Thread / Independently Running Threads

Clarified in response to a student question: the main thread's only responsibility is executing the main() method. Any custom thread YOU create and start from inside main() then runs independently — there's no enforced "parent-child" relationship controlling their execution relative to each other. Once started, a custom thread follows its own separate execution path, unrelated to whether the main thread has finished or not.

Threading Requires Practice, Not Just Theory

Directly emphasized: mastering multithreading requires a lot of hands-on practice PLUS a degree of "out-of-the-box" thinking — it's fundamentally different from most topics covered so far, precisely because the usual assumption of predictable, top-to-bottom code execution no longer fully holds.

Foreshadowed for the next session: while default thread order is unpredictable, Java DOES provide synchronization mechanisms to control/fix the order when your application genuinely requires it. 💻 Code Snippets / Examples

Finding which thread executes your code:

public class Driver {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName());
        // Output: main
    }
}

Creating a custom thread by extending the Thread class:

class MyThread extends Thread {

    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName() + " is executing");
    }

}

Starting the custom thread:

public class Driver {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName()); // main

        MyThread t1 = new MyThread();
        t1.start(); // launches a NEW thread — do NOT call t1.run() directly

        System.out.println(Thread.currentThread().getName()); // main (again)
    }
}
// Output order between the two "main" prints and the new thread's print
// is NOT guaranteed — could vary between runs

Multiple custom threads — demonstrating unpredictable order:

class NumberThread extends Thread {
    int id;

    public NumberThread(int id) {
        this.id = id;
    }

    @Override
    public void run() {
        System.out.println(id);
    }
}
public class Driver {
    public static void main(String[] args) {
        NumberThread t0 = new NumberThread(0);
        NumberThread t1 = new NumberThread(1);
        NumberThread t2 = new NumberThread(2);

        t0.start();
        t1.start();
        t2.start();

        // Possible outputs across different runs: 0 1 2 | 1 0 2 | 2 0 1 | 1 2 0 | ...
        // Order is genuinely NOT guaranteed — this is expected, not a bug
    }
}

Calling run() directly — the WRONG way (no actual new thread):

MyThread t1 = new MyThread();
t1.run(); // WRONG — just a normal method call on the CURRENT thread (e.g. main)
          // No new thread is actually created; defeats the purpose entirely

t1.start(); // RIGHT — actually creates and launches a new thread

📌 Important Points / Common Mistakes

  • A process has its own memory (JVM, browser, Eclipse); a thread is the unit of execution INSIDE a process; a task is the actual work a thread performs.
  • Even the simplest Java program requires a thread (the automatically-created "main" thread) — there's no such thing as threadless Java execution.
  • Always call .start() to launch a new thread — calling .run() directly just executes it as a normal method on the current thread, with no actual concurrency.
  • Thread execution order can NEVER be reliably predicted by default — don't design logic that assumes a specific order without proper synchronization.
  • Observing the same order repeatedly does NOT mean the order is guaranteed or fixed.
  • The CPU (not the order requests arrive in) has final authority over which thread executes when.
  • On a single core, true parallelism doesn't exist — extremely fast context switching just makes it appear that way to humans.
