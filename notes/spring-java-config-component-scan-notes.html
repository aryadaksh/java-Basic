🧠 Key Concepts

Recap From Yesterday
  • A bean is an object managed by the Spring Framework; the IoC container manages it — IoC means the responsibility for the object's life cycle shifted from your application to the container.
  • Two container types: BeanFactory (lightweight, for small or limited use) and ApplicationContext (production-grade, large applications).
  • Yesterday's flow: a POJO class plus an XML file were given to the container, which created the Employee bean for anyone to request and use.
  • Today the XML is replaced — the configuration, initialisation and value-setting are done in Java. "XML will not be used."
Three Ways to Create Beans — and When to Use Each
ApproachHowWhen (instructor's guidance)
1. XMLBean definitions in an XML file (done yesterday)If your project is already XML-based, or you do a lot of customisation.
2. Java configuration@Configuration class with @Bean methodsWhen you want better control over the beans and how values are set.
3. Annotations@Component on the class + @ComponentScan on a config classWhen you just want the beans created as soon as possible and don't need control over how they're set up.
  • In a real project you mix all three — some parts XML, some Java config, some annotations.
  • He added that the annotation approach is "hard to test" — the explanation in the recording is unclear, so don't quote it as a rule.
  • Most of the time, the service, repository and controller layers are created with component-style annotations.
🔥 Interview angle: "XML vs Java config vs annotation-based configuration — which and when?" — and "what is the difference between @Bean and @Component?" (method level vs class level; see the table below).
The Four Annotations — One-Line Meanings

The instructor's closing recap. Where each is used appears in the demos below.

AnnotationLevelWhat it tells Spring
@ConfigurationClassThis class is responsible for bean definitions — "the source for all the beans".
@BeanMethodThis method defines a bean: "please manage this object" — the returned object becomes Spring-managed.
@ComponentClassThe bean of this class can be managed by Spring — "please manage the bean of this class".
@ComponentScanClass (on the config class)Scan this package; wherever you find @Component, create the bean and keep it in memory.
Approach 2 — Java Configuration: the Demo
  • Setup: a new Maven project, the same spring-context dependency as yesterday, and the Employee POJO (fields, getters/setters, a way to print the details).
  • The config class: instead of the XML, a class marked @Configuration holds a @Bean method that returns a new Employee — Spring is being asked to manage that employee bean. One config class can define multiple beans — "this can have multiple beans" — by adding more @Bean methods.
  • The container: for Java configuration use AnnotationConfigApplicationContext and pass the config class — AppConfig.class — so the container knows where the bean definitions are.
  • Requesting beans: without a name, ask by class — getBean(Employee.class) — and you get an Employee. Using a name (employee1, the method's name) returns an Object, so downcast. For a second bean, add another @Bean method and ask for its name.
  • What was printed: the fields showed null because no values were set.

Difference from yesterday: same idea, but the bean definition now lives in Java instead of in the XML file.

Approach 3 — Annotations and Component Scan: the Demo
  • Mark the class: put @Component on Employee — no @Bean method is needed. Usually, with a component you're not interested in the fields.
  • The config class carries @Configuration plus @ComponentScan naming a package: Spring scans that package and creates beans for the annotated classes, keeping them ready. The config class does nothing else — "the annotation will do the job".
  • Why a package: an application may have 1,000 component classes; this config class is responsible only for the ones under the package it scans.
  • The container is the same AnnotationConfigApplicationContext; ask with getBean(Employee.class). Fields are null again, since no values were set.
  • Proof that the scan matters: he changed the package in the scan to one without the component and got a "no such bean" exception — the bean wasn't available because the scan never looked where it was.
💡 Added clarification:
  • Bean names: by default an @Bean method's name is the bean's name; a @Component class gets its class name with a lowercase first letter (employee).
  • By type with two beans: if two @Bean methods return Employee, getBean(Employee.class) can't choose and fails (NoUniqueBeanDefinitionException) — use the name. The class demo asked by type with a single bean.
  • Setting values: inside a @Bean method you can call the setters before returning the object, so the fields aren't null — that is the extra control Java config gives over annotations (snippet 1).
  • Component-style variants: @Service, @Repository and @Controller are specialised forms of @Component — presumably the "component-style" annotations he meant for the service/repository/controller layers; the recording doesn't name them.
  • Scan from the right place: @ComponentScan("com.example.emp") also covers sub-packages; if no package is given it scans the config class's own package.

1. Approach 2 — Java configuration (@Configuration + @Bean):

package com.example.emp;

public class Employee {                       // plain POJO
    private String name;
    private String id;
    // getters and setters ...
    @Override
    public String toString() { return "Employee[id=" + id + ", name=" + name + "]"; }
}

@Configuration                                // this class is the source of bean definitions
public class AppConfig {

    @Bean                                     // "Spring, please manage this employee object"
    public Employee employee1() {
        Employee e = new Employee();          // (added) set values here so the fields aren't null
        e.setName("Ravi");
        e.setId("101");
        return e;
    }

    @Bean                                     // a second bean of the same class
    public Employee employee2() {
        return new Employee();                // values not set -> printed as null, as in class
    }
}

public class App {
    public static void main(String[] args) {
        ApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);

        Employee emp1 = (Employee) context.getBean("employee1");   // by name -> Object, so downcast
        System.out.println(emp1);                                  // Employee[id=101, name=Ravi]

        // by class works when there is exactly ONE bean of that type:
        // Employee e = context.getBean(Employee.class);
    }
}

2. Approach 3 — annotations (@Component + @ComponentScan):

package com.example.emp;

@Component                                    // "Spring, please manage a bean of this class"
public class Employee {
    private String name;
    private String id;
    // getters, setters, toString ...
}

@Configuration
@ComponentScan("com.example.emp")             // scan this package for @Component classes
public class ScanConfig { }                   // nothing else needed inside

public class App2 {
    public static void main(String[] args) {
        ApplicationContext context = new AnnotationConfigApplicationContext(ScanConfig.class);

        Employee emp = context.getBean(Employee.class);   // no cast when asking by class
        System.out.println(emp);                          // Employee[id=null, name=null] - no values set
    }
}
// Change the scan to a package that has no component, e.g. @ComponentScan("com.example.nothere"):
// getBean(Employee.class) -> NoSuchBeanDefinitionException (no bean of that type is available)
