🧠 Key Concepts

Recap: Garbage Collection & Reachability

An object becomes eligible for garbage collection only when it is completely unreachable — no active reference points to it anymore. The garbage collector periodically reclaims memory from such unreachable objects.

What is a Memory Leak in Java?

Even though Java has automatic garbage collection, a memory leak can still occur — it happens when objects that are no longer actually needed remain reachable (something still references them), so the garbage collector can never reclaim them. Over time, these unreleased objects accumulate, consuming more and more heap memory, eventually leading to OutOfMemoryError.

Why This Matters — It's Not a "Java Bug"

A memory leak isn't caused by garbage collection failing to work — GC works exactly as designed, only cleaning up truly unreachable objects. The leak happens because of how the application code is written — objects are unintentionally kept reachable (e.g. via a reference that's never cleared) long after they're actually needed.

Common Cause 1: Static Fields Holding References

A static field lives for the entire lifetime of the class (as long as the class is loaded) — if a static collection or field keeps accumulating object references (e.g. adding to a static List but never removing), those objects can never become unreachable, even if the rest of the application no longer needs them.

Common Cause 2: Unclosed Resources

Database connections, file streams, and similar resources that are opened but never explicitly closed can hold onto memory and system resources indefinitely, even though the "user-facing" object referencing them may seem done with its work.

Common Cause 3: Listeners / Callbacks Not Removed

If an object registers itself as a listener/callback with another long-lived object, and is never explicitly deregistered, the long-lived object continues to hold a reference to it — preventing garbage collection even after the listener is logically no longer needed.

Common Cause 4: Caches Without Eviction

A cache that keeps adding entries without ever removing old/unused ones effectively becomes an ever-growing reachable structure — a very common real-world source of memory leaks in long-running applications.

Transition to Collections — Why Arrays Aren't Always Enough

A plain array has a fixed size, decided at creation time — you cannot grow or shrink it afterward. In real applications, the number of elements needed is often not known in advance (e.g. how many items a user adds to a cart) — this limitation motivates Java's Collections Framework, which provides flexible, resizable data structures.

ArrayList — A Resizable, Array-Backed List

ArrayList (from java.util) is one of the most commonly used Collection classes — internally backed by an array, but it automatically resizes itself as elements are added or removed, so you never need to know the final size in advance.

ArrayList vs Array — Key Differences
ArrayArrayList
Fixed size, set at creationDynamically resizable
Can hold primitives directlyOnly holds objects (uses wrapper classes for primitives, e.g. Integer instead of int)

💻 Code Snippets / Examples

Memory leak example — static list that never shrinks:

class SessionCache {
    static List activeSessions = new ArrayList<>();

    public static void addSession(String sessionId) {
        activeSessions.add(sessionId); // keeps growing, never removed
    }
    // If sessions are never removed after logout, this list grows forever,
    // and every session object it references can never be garbage collected.
}

Fixed-size limitation of arrays:

int[] scores = new int[3]; // fixed at 3 — cannot add a 4th element without creating a new array
scores[0] = 90;
scores[1] = 85;
scores[2] = 70;
// scores[3] = 60; // ArrayIndexOutOfBoundsException — no room to grow

Creating and using an ArrayList:

import java.util.ArrayList;
import java.util.List;

class CartDemo {
    public static void main(String[] args) {
        List cartItems = new ArrayList<>();

        cartItems.add("Laptop");
        cartItems.add("Mouse");
        cartItems.add("Keyboard");

        System.out.println(cartItems);        // [Laptop, Mouse, Keyboard]
        System.out.println(cartItems.size());  // 3

        cartItems.remove("Mouse");
        System.out.println(cartItems);        // [Laptop, Keyboard]

        System.out.println(cartItems.get(0)); // Laptop
        System.out.println(cartItems.contains("Keyboard")); // true
    }
}

ArrayList grows automatically — no fixed size needed:

List numbers = new ArrayList<>();
for (int i = 0; i < 100; i++) {
    numbers.add(i); // no size limit issues — ArrayList resizes internally as needed
}
System.out.println(numbers.size()); // 100

❓ Doubts / Questions Raised in Class

QuestionAnswer
If Java has garbage collection, how can a memory leak still happen?GC only reclaims UNREACHABLE objects. A leak happens when application code unintentionally keeps objects reachable (e.g. via a static collection that's never cleared) even though they're no longer actually needed.
Why use ArrayList instead of a plain array?Arrays have a fixed size decided at creation; ArrayList grows and shrinks dynamically as elements are added/removed, which fits most real-world scenarios where the final size isn't known upfront.
Can an ArrayList store primitive types directly like an array can?No — ArrayList only stores objects, so primitives are automatically wrapped using their corresponding wrapper classes (e.g. int becomes Integer) when added.

📌 Important Points / Common Mistakes

  • Memory leaks in Java happen due to objects being unintentionally kept REACHABLE, not because GC fails.
  • Watch out for static collections, unclosed resources, unregistered listeners, and unbounded caches as common leak sources.
  • Arrays have a fixed size; ArrayList resizes automatically as needed.
  • ArrayList only stores objects — primitives are auto-boxed into their wrapper types.
  • Import ArrayList from java.util before using it.
