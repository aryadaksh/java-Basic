🧠 Key Concepts

Why Do We Need the Executor Framework?

Creating threads manually causes two major problems:

  1. For a particular task, it is difficult to estimate how many threads are required.
  2. After a manually created thread finishes its task, the thread terminates instead of being reused.

Java introduced the Executor Framework in Java 5 (Java 1.5) to address exactly these two problems.

The Main Idea — Submit Tasks, Don't Manage Threads
  • The programmer submits tasks instead of manually managing every thread.
  • A thread pool manages the worker threads.
  • Worker threads can be reused for multiple tasks.
  • Tasks that cannot execute immediately wait in a queue.
  • The framework manages much of the thread lifecycle and task scheduling.
ExecutorService — The Interface You Use

ExecutorService is the interface commonly used to submit and manage tasks. Typical code:

ExecutorService service = Executors.newFixedThreadPool(5);

When the work is finished, call service.shutdown();. If the ExecutorService is not shut down when it is no longer needed, its worker threads can keep the executor alive.

Example: 5 Worker Threads, 10 Tasks

A fixed thread pool has 5 worker threads and 10 tasks are submitted:

  • Up to 5 tasks can execute concurrently.
  • The remaining tasks wait in the queue.
  • When a worker finishes, it takes another waiting task.
  • The same worker thread is reused.
The Practical Example: 2 Worker Threads + 4 Tasks

Create a fixed pool with 2 worker threads and submit 4 tasks.

  • Task 1 and Task 2 execute using the two workers.
  • Task 3 and Task 4 wait in the work queue while both workers are busy.
  • When a worker finishes, it takes another queued task.
  • The worker does not terminate after every task — it is reused.

The executor therefore provides thread reuse and automatic task distribution. (See the diagram in the visual section below.)

💡 Added clarification — why the queue exists, and why workers are reused (not stated this way in class):
  • Why tasks wait in a queue: a fixed pool has only N workers, so at most N tasks can run at once. The queue is the holding area for the extra tasks — the caller of submit() doesn't have to be blocked, the pool doesn't have to spawn an unlimited number of threads, and no task is lost. As soon as a worker frees up, it pulls the next task from the queue.
  • Why workers are reused: a worker isn't "one thread per task" — it is a thread that runs in a loop: run a task → ask the queue for the next one → run it…. Creating and destroying a thread for every task is wasteful work; reusing a small set of threads avoids it.
  • Why a finished manual thread can't just be reused: once a Thread object has finished, it is dead — calling start() on it again throws IllegalThreadStateException. A pool avoids this by keeping the thread alive and feeding it new tasks.

The Problem: The "10-Second Calculation"

The main thread starts another thread to perform a calculation. The calculation takes 10 seconds. The main thread carries on independently. If the calculation lives inside Runnable.run(), there is no return value the caller can directly receive from run().

The fundamental question: "How does the caller know what result the asynchronous task produced?"

The Older / Manual Answer: Task ID + External Storage
  1. Generate a unique task ID.
  2. Store the task's status/result somewhere — such as a database.
  3. Update the database when the task completes.
  4. Later, query the task ID to discover the status/result.

This works as an external status-tracking mechanism — but Java already provides a standard concurrency abstraction for asynchronous task results: Future.

🔥 Interview Trap — Thread.sleep() Is Not an Answer

Thread.sleep() is not a proper general solution for asynchronous result handling. It only delays execution and does not reliably coordinate task completion. (Guessing "the task will surely be done in 10 seconds" is fragile — it may take 9 or 12.)

Why join() Is Not the Same Solution

Thread.join() makes one thread wait for another thread to finish. It is appropriate when you explicitly need to wait for completion. But if the goal is asynchronous execution where the caller should continue doing other work, joining immediately defeats much of the asynchronous behaviour.

ApproachMeaning
join()Wait for another thread to finish
Asynchronous task submissionLet the task run independently and obtain its result later
Why Was Callable Needed When Runnable Already Existed?

Because Runnable.run() returns void — it has no channel through which an asynchronous task can hand a result back to the caller. Without it you're pushed into workarounds (task IDs, databases, shared variables). Callable fixes this at the source: call() returns a value (and may throw checked exceptions), and when you submit a Callable to an ExecutorService you get a Future — the handle for that result.

Callable + Future — The Standard Solution

When a Callable is submitted to an ExecutorService, submission returns a Future:

Future<Integer> future = executor.submit(callable);

Why "Future"? Because the result may become available in the future.

Conceptual flow:

  1. The main thread creates a Callable.
  2. The main thread submits it to the ExecutorService.
  3. The ExecutorService assigns the task to a worker thread.
  4. The worker thread executes call().
  5. call() returns a value.
  6. Future represents the pending/available result.
  7. The caller can retrieve the result later.
Future Is Generic

The type parameter depends on the result type of the Callable: Future<Integer>, Future<String>, Future<Void>. Example:

Callable<Integer> task = () -> { return 20; };
Future<Integer> future = executor.submit(task);
Integer result = future.get();

Future.get() — And Its Blocking Behaviour

The result is retrieved with future.get(). Future.get() can block if the result is not available yet. So Future does not automatically mean "never wait" — it is a handle through which the caller can obtain the asynchronous result. The benefit is that you choose when to wait: submit first, do other work, and call get() only when you actually need the value.

execute() → Runnable → no Future returned.
submit() → Runnable or Callable → Future returned.

Practical Mental Model — ExecutorService Is a Manager

You give the manager tasks. The manager maintains worker threads, assigns tasks to available workers, queues tasks when workers are busy, reuses workers, and manages task execution. You focus on WHAT needs to run — not on creating and destroying a Thread for every task.

⚠️ Technical Nuances Worth Verifying (Not Stated This Way in Class)
  • shutdown() is graceful: it stops the pool from accepting new tasks, but tasks already submitted (running and queued) still complete, after which the workers exit. shutdownNow() is the forceful variant — it tries to interrupt running tasks and returns the tasks that never started. shutdown() does not wait for completion; use awaitTermination() if you need to.
  • Why unshutdown pools "keep the executor alive": workers created by the default factory are non-daemon threads, and in a fixed pool they stay alive waiting for work — so the JVM can't exit while they exist.
  • Which worker gets which task is not guaranteed: in the 2 + 4 example, Task 1 and Task 2 start first, but whichever worker finishes first takes Task 3 — you can't predict which. Don't rely on "Worker 1 runs Task 1 and Task 3".
  • submit(Runnable) also returns a Future — but it carries no result, so get() returns null (it still tells you when the task is done).
  • Callable exceptions: a checked (or unchecked) exception thrown inside call() doesn't surface at submit() — it is captured in the Future and re-thrown from get() wrapped in an ExecutionException.
  • Future<Void>: for a Callable<Void> you must still write return null;.
  • Sleep in demos vs sleep as a solution: the lecture warns against using Thread.sleep() to wait for a result. Using it inside a task to simulate a 10-second calculation (as in the code samples below) is fine — it just mimics slow work.
  • Other pool types exist (single-thread, cached, scheduled), but the lecture covers only the fixed thread pool, so these notes do too.

⚙️ Internal Working (Added Clarification)

Note: the lecture stayed at the conceptual level ("the manager assigns tasks to workers"). This section is my addition — a simplified picture of how the standard JDK implementation behaves. Exact details can differ between JDK versions, so treat it as a mental model and verify against your JDK's ThreadPoolExecutor source/docs.
What Executors.newFixedThreadPool(n) Builds

In the standard JDK it returns a ThreadPoolExecutor with n core threads, n maximum threads, and an unbounded queue (a LinkedBlockingQueue). That combination is exactly the "fixed workers + waiting queue" behaviour from the lecture.

What Happens When You Submit a Task
  1. submit(callable) wraps your Callable in a FutureTask (which is both a Runnable and a Future), then passes it to execute().
  2. If fewer than n workers exist, the pool starts a new worker thread with this task as its first job (workers are created lazily as tasks arrive, not all n upfront).
  3. If all n workers already exist, the task is put in the queue.
  4. Each worker runs a loop: run its task → take the next task from the queue (blocking while the queue is empty) → run it… That loop is the thread reuse.
  5. When the FutureTask runs, it calls your call(), stores the return value (or the exception), and wakes anyone blocked in future.get().
  6. shutdown() stops new submissions; workers drain the queue, then exit.

💻 Code Snippets / Examples

Note on this code: the lecture source contains only the short fragments quoted above (newFixedThreadPool, shutdown, submit, Callable returning 20, future.get()). The complete, runnable programs below are my reconstructions built around those fragments and the instructor's examples.

1. Fixed thread pool — 2 workers, 4 tasks (Runnable via execute):

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class FixedPoolDemo {
    public static void main(String[] args) {
        ExecutorService service = Executors.newFixedThreadPool(2);   // 2 worker threads

        for (int i = 1; i <= 4; i++) {
            final int taskId = i;
            service.execute(() -> {                                  // Runnable, no result
                String worker = Thread.currentThread().getName();
                System.out.println("Task " + taskId + " started  by " + worker);
                try {
                    Thread.sleep(2000);                              // simulate 2 seconds of work
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                System.out.println("Task " + taskId + " finished by " + worker);
            });
        }

        service.shutdown();   // no more tasks will be submitted
    }
}
// Sample output (interleaving and worker names for Task 3/4 may vary):
// Task 1 started  by pool-1-thread-1
// Task 2 started  by pool-1-thread-2
// ... 2 seconds pass ...
// Task 1 finished by pool-1-thread-1
// Task 2 finished by pool-1-thread-2
// Task 3 started  by pool-1-thread-1   <-- same worker reused
// Task 4 started  by pool-1-thread-2   <-- same worker reused
// ...
// Only TWO distinct thread names ever appear: the workers are reused.

2. Runnable vs Callable — side by side:

import java.util.concurrent.Callable;

// Runnable — void run(), no result
Runnable r = () -> System.out.println("I return nothing");

// Callable — call() returns a value and may throw checked exceptions
Callable<Integer> c = () -> {
    return 20;
};

// The same thing as a classic class:
class Calculation implements Callable<Integer> {
    @Override
    public Integer call() throws Exception {   // "throws Exception" is allowed here
        return 20;
    }
}

3. The 10-second calculation with Callable + Future:

import java.util.concurrent.*;

public class CallableFutureDemo {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(1);

        Callable<Integer> task = () -> {
            System.out.println("Calculating in " + Thread.currentThread().getName());
            Thread.sleep(10_000);          // sleep here only SIMULATES a 10-second calculation
            return 20;                     // the result of the asynchronous work
        };

        Future<Integer> future = executor.submit(task);   // returns IMMEDIATELY

        System.out.println("main: free to do other work...");

        Integer result = future.get();     // BLOCKS here until the result is ready
        System.out.println("Result = " + result);

        executor.shutdown();
    }
}

4. Future is generic — String result, and submit(Runnable):

Future<String> greeting = executor.submit(() -> "Hello");        // Callable<String>
System.out.println(greeting.get());                               // Hello

Future<?> done = executor.submit(() -> System.out.println("hi")); // Runnable
done.get();                                                       // returns null — but confirms the task finished

Callable<Void> noResult = () -> {
    System.out.println("side effect only");
    return null;                                                  // Callable<Void> must return null
};
Future<Void> v = executor.submit(noResult);

5. execute() vs submit() — same task, different handling:

Runnable task = () -> System.out.println("working...");

executor.execute(task);                    // returns void — no way to check status or result

Future<?> f = executor.submit(task);       // returns a Future
System.out.println(f.isDone());            // can ask: has it finished?

6. Robust Future usage — timeout, polling, exceptions (added):

Future<Integer> future = executor.submit(task);

// (a) Don't wait forever: give up after 2 seconds
try {
    Integer result = future.get(2, TimeUnit.SECONDS);
    System.out.println("Got " + result);
} catch (TimeoutException e) {
    System.out.println("Not ready yet — do something else");
    // future.cancel(true);              // optionally attempt to cancel
} catch (ExecutionException e) {
    System.out.println("Task itself failed: " + e.getCause());   // real exception from call()
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

// (b) Poll without blocking, do useful work in between
while (!future.isDone()) {
    // doOtherWork();
}
Integer result = future.get();             // returns immediately now

7. Exceptions: execute() vs submit() — a classic trap (added):

Runnable failing = () -> { throw new RuntimeException("boom"); };

executor.execute(failing);
// -> the worker thread dies with an uncaught exception; a stack trace is printed
//    ("Exception in thread pool-1-thread-1 ...") and the pool replaces the worker.

Future<?> f = executor.submit(failing);
// -> NOTHING is printed. The exception is captured inside the Future.

try {
    f.get();                               // the exception only appears here
} catch (ExecutionException e) {
    System.out.println("Failed: " + e.getCause());   // java.lang.RuntimeException: boom
}
// If you submit() and never call get(), the failure is silently swallowed.

8. Proper shutdown (added):

ExecutorService service = Executors.newFixedThreadPool(5);
try {
    // submit tasks ...
} finally {
    service.shutdown();                    // stop accepting new tasks; queued tasks still run
}

try {
    if (!service.awaitTermination(30, TimeUnit.SECONDS)) {
        service.shutdownNow();             // force-stop: interrupt running tasks
    }
} catch (InterruptedException e) {
    service.shutdownNow();
    Thread.currentThread().interrupt();
}

9. join() — waits, but hands back no result:

Thread t = new Thread(() -> compute());   // compute() is void — nothing to return
t.start();
t.join();      // main WAITS here until t finishes, so it can't carry on with other work meanwhile.
               // join() also gives no result back — you would still need a shared variable/DB to fetch one.

10. The older task-ID approach — illustration only (a Map stands in for the database):

import java.util.Map;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;

Map<String, String> statusStore = new ConcurrentHashMap<>();   // stands in for the DB

String taskId = UUID.randomUUID().toString();       // 1. unique task ID
statusStore.put(taskId, "RUNNING");                 // 2. store status

new Thread(() -> {
    int result = heavyCalculation();                // ~10 seconds
    statusStore.put(taskId, "DONE: " + result);     // 3. update when complete
}).start();

// 4. later, from anywhere: query by task ID
String status = statusStore.get(taskId);
// Future gives you this "handle to the result" as a standard Java object instead.

11. What newFixedThreadPool(n) roughly builds (added — JDK implementation detail):

// Roughly equivalent to Executors.newFixedThreadPool(n):
ExecutorService service = new ThreadPoolExecutor(
        n, n,                                  // core = max = n worker threads
        0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>());  // unbounded queue for waiting tasks

🎤 Likely Interviewer Follow-Up Questions (Added)

These go beyond what the lecture said — expect them in Java backend interviews.

Follow-upShort answer
What if the task throws an exception — how does execute() differ from submit()?With execute(), the exception kills the worker thread and prints a stack trace (the pool replaces the worker). With submit(), the exception is captured in the Future and only thrown from get() as an ExecutionException — if you never call get(), it's silently lost.
What happens if you never call shutdown()?Non-daemon worker threads stay alive, so the JVM typically doesn't exit.
shutdown() vs shutdownNow()?shutdown(): no new tasks, already-submitted tasks (including queued) still finish. shutdownNow(): tries to interrupt running tasks and drains the queue.
How do I avoid blocking forever on get()?Use get(timeout, unit) (throws TimeoutException), or poll isDone().
Can you cancel a task?future.cancel(true) attempts to; it's best-effort and only works well if the task responds to interruption.
What kind of queue does a fixed pool use? Any risk?An unbounded LinkedBlockingQueue in the standard JDK — if tasks arrive faster than workers finish them, the queue keeps growing and memory can run out.
How many threads should a pool have?It depends on the workload — the lecture itself notes this is hard to estimate. A common rule of thumb: about the number of CPU cores for CPU-bound tasks, more for I/O-bound tasks; measure and tune.
Is the result of submit(Runnable) useful?The Future's get() returns null, but you can still use it to wait for completion and detect failure.
What are the limits of Future?get() blocks, and there's no built-in way to say "run this when it's done" — which is one reason later APIs such as CompletableFuture exist (not covered in this lecture).
Difference between Executor and ExecutorService?Executor has only execute(Runnable). ExecutorService extends it with submit(), Futures, and lifecycle methods like shutdown().

📌 Lecture Takeaways

  • The Executor Framework was introduced in Java 5.
  • ExecutorService abstracts much of manual thread management.
  • Thread pools reuse worker threads.
  • Tasks that can't execute immediately wait in a queue.
  • A fixed thread pool has a fixed number of worker threads.
  • shutdown() should be called when the executor is no longer needed.
  • Runnable.run() returns void; Callable.call() can return a value.
  • Callable is useful for asynchronous work that produces a result.
  • Future represents a result that may become available later.
  • submit() returns a Future and supports Callable; execute() is for Runnable and returns no Future.
  • join() causes waiting — it is not equivalent to asynchronous result handling.
  • An external task-ID/database mechanism can track long-running async work, while Future is the standard Java way to represent a submitted task's result.

🚧 Common Interview Traps

  • "Future means non-blocking." Wrong — get() can block. Future is a handle; blocking depends on when you call get() and whether the task is finished.
  • "Use Thread.sleep() until the result is ready." Wrong — it only delays and doesn't coordinate completion.
  • "Just join() the thread." join() waits; if you join immediately you lose the asynchronous benefit, and you still get no return value.
  • "execute() and submit() are the same." They differ in accepted task types and in the Future return.
  • "The pool creates a new thread per task." The opposite — 5 workers, 10 tasks means 5 threads run and 5 tasks queue.
  • Forgetting shutdown() — the worker threads can keep the executor (and program) alive.
  • Assuming a fixed worker–task mapping — which worker runs which queued task isn't predictable.
  • Treating garbled transcript words as APIs — stick to real names: Executors, ExecutorService, Runnable, Callable, Future, submit, execute, shutdown, get.
