🧠 Key Concepts

Recap: Why Callable Was Introduced

Runnable doesn't give anything back to the caller. When a Runnable launches a new thread, the caller has no idea when it will get CPU time or what happened to its work. Callable fixes this: its call() method returns a value, wrapped in a Future object — Future of String, Future of Integer, Future of Person, Future of Account — and once call() has executed, the caller can read the result and find out whether the work went as expected.

The Live Demo: Sending Emails With a Callable

The instructor wrote a class implementing Callable<Boolean>. Its call() uses an EmailSender to send an email and returns true (only the positive case was handled). In the driver: create an ExecutorService from the Executors class (fixed thread pool), call submit(...) with the task (submit accepts both Runnable and Callable; execute accepts only Runnable), and receive a Future<Boolean>. Then the task is repeated for 10 different email addresses (in real life these would come from customers; in the demo the ID is appended to build different addresses).

Reading the Status

Printing future.get() for each task shows the status — that means we are getting the result. To make the timing visible, the instructor added a sleep of 2 seconds inside the email sending (assuming each email takes 2 seconds). Tip from class: whenever you're understanding a concept, put maximum print statements — you understand the flow.

🔥 The Key Observation: Future.get() Is a Blocking Call

With 10 tasks performed by 2 threads, calling future.get() made the calling thread (main) wait until that task's result arrived before it moved on. A "Main started" / "Main ended" print confirmed it: "Main ended" only appeared after all the results were read — main was stuck waiting the whole time. That is the meaning of blocking: future.get() blocks your current thread until it gets the response from the other thread. The instructor noted it's "the current thread" — here it's main, but it could be any thread that executes this call.

The Contrast: Without get(), Main Is Free

When the instructor commented out the status reading (no future.get()), "Main ended" printed immediately — main was not blocked at all, even though the email tasks were still running in the background. Reading the result is the thing that makes the caller wait.

Runnable vs Callable — The Trade-Off in One Line

Runnable doesn't give you a result. Callable gives you a result via future.get() — "but all beautiful features come with some problem." The problem: it is blocking. You get the result, but if you're waiting for it, your other work is held up — it's slow. Java introduced another feature, CompletableFuture, to solve this — covered next. The instructor's advice: first understand Future properly before learning CompletableFuture.

🔥 Interview Alert

"What is Future?" is a definite interview question — the instructor said your answer to it can decide how the interview goes. A strong answer covers: Future represents the result of an asynchronous task submitted to an executor; it's what submit() returns; you read it with get(); and get() blocks the calling thread until the result is ready — which is exactly the limitation CompletableFuture addresses.

⚠️ Clarification Added (Not Stated in Class)
  • In the demo, get() was called inside the submission loop — i.e. submit task 1, wait for its result, then submit task 2. That's why the 2-thread pool couldn't overlap the work. A common improvement is to submit all tasks first, store the Futures in a list, and only then call get() on each — the tasks then run concurrently and you only wait for whatever hasn't finished yet. This wasn't shown in class; it's offered as a standard technique.
  • Future also has a timed overload, get(timeout, unit), which gives up waiting after a limit. Not covered in this class.
  • shutdown() is described in class as needed so the service doesn't stay "up and running." In standard Java it stops accepting new tasks but lets already-submitted tasks finish.
The Three Famous Thread Pools

All created through the Executors class. As summarized in class: Fixed, Single, and Cached (dynamic) — "these three are very famous."

PoolFactory methodBehavior (as taught)
FixedExecutors.newFixedThreadPool(n)You decide the number of worker threads. With 5 workers and 10 tasks, each worker averages 2 tasks — workers are reused.
Cached ("dynamic")Executors.newCachedThreadPool()Based on the work, it decides how many threads to launch. If load is more, it keeps creating new threads.
SingleExecutors.newSingleThreadExecutor()Only one thread is created, and that one thread does all the work.
Cached Pool Experiments — What the Instructor Observed

He submitted increasing numbers of tasks to a cached pool and counted the distinct thread IDs:

  • 10 tasks → 10 threads launched.
  • 100 / 200 / 500 / 1,000+ tasks → it kept creating new threads; the IDs climbed into the thousands. His first reaction: "it should reuse threads — it's always creating new ones."
  • Then the realization: the demo tasks contained sleep. A sleeping thread is busy, so it can't be reused — the pool has no choice but to launch another thread for each new task that arrives while the others are still sleeping.
  • With the sleep removed (tiny tasks that finish almost instantly), the thread count dropped sharply — idle threads were reused instead.

Lesson (instructor's words): "It's creating threads based on the work. If the first thread is taking time, we cannot reuse it, so it definitely creates another." With sleep, the work effectively became heavy work, and the pool launched more threads than necessary.

When the Cached Pool Fits

It suits small work in large volume — each task is quick, but there are lots of them and you don't know how many threads you'd need. Example: sending an email takes very little time, but you're sending it to 10,000 customers (or one lakh, or 5 million). You can't pre-decide the thread count, so you let the pool decide dynamically. With a Fixed pool, you decide the number — "similar to you creating threads yourself."

When the Single Thread Pool Fits

When you need only one thread — sometimes that's exactly the requirement. One worker thread does all the submitted work.

⚠️ Technical Nuances Worth Knowing (Not Stated This Way in Class)
  • The cached pool is unbounded in standard Java: if tasks are slow and arrive faster than they finish, it can keep creating threads without limit — which is the real-world risk behind what the instructor's sleep experiment showed. Idle cached threads are also removed after a period of inactivity (60 seconds by default). Neither detail was mentioned in class.
  • A single-thread executor also guarantees tasks run one after another in submission order — a useful property when order matters. Not mentioned in class.
  • Printing thread names (e.g. pool-1-thread-3) is the easiest way to see which worker ran which task — the instructor's counting method was essentially this.
"How Do I Decide the Number of Threads in a Fixed Pool?"

A student asked this; the instructor called it a valid question. His answer: there is no fixed formula — you have to do an effort estimate using logic. Factors he listed:

  1. Limits of your system — current CPU requirement, how many cores are available, how many threads are allowed.
  2. Criticality of the task.
  3. How soon you need it done — "quickly, or are 2–3 minutes okay?"
The Chairs Analogy

Task: move 20 chairs out of the classroom. How many people do you need? You factor in the situation — only so many people can physically work in the room at once (limitation), and whether you need it done quickly or can take a few minutes (urgency). Thread-pool sizing works the same way.

A Worked Estimate From Class

Suppose 1,000 customers place orders every second, and each order needs an email. Assume one thread takes 100 ms per email — so one thread can send roughly 10 emails per second. "Roughly, you calculate" — the instructor stopped here and moved on to the approach below.

Added arithmetic: 1,000 emails/sec ÷ 10 emails/sec per thread ≈ 100 threads in theory, if the work were purely waiting on email sending and your system could support that many. The instructor did not state this final number, and he stressed the figure is a starting estimate, not a formula.
Tiny Approach vs Fat Approach
  • Tiny approach: start with a small number (e.g. 100 threads), observe system behavior; if emails are still delayed, fine-tune and increase (say, to 150); if some threads sit idle, reduce the count. You converge on an average number that works.
  • Fat approach: blindly give a big number (e.g. 1,000). It may work — but if only ~150 threads were really needed, then ~850 threads are running idle and "not contributing much."

"Whenever you're deciding any resource, start with the basics. Start small, observe, then increase or decrease."

The email Callable — returns true when the email is sent:

import java.util.concurrent.Callable;

class EmailSender {
    public boolean sendEmail(String to) {
        System.out.println(Thread.currentThread().getName() + " sending email to " + to);
        try {
            Thread.sleep(2000); // assume each email takes 2 seconds
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        return true; // positive case only, as in class
    }
}

class EmailTask implements Callable<Boolean> {
    private final String to;

    EmailTask(String to) {
        this.to = to;
    }

    @Override
    public Boolean call() {
        return new EmailSender().sendEmail(to);
    }
}

The blocking version — get() inside the loop (what the demo showed):

import java.util.concurrent.*;

public class Driver {
    public static void main(String[] args) throws Exception {
        System.out.println("Main started");
        ExecutorService executor = Executors.newFixedThreadPool(2);

        for (int i = 1; i <= 10; i++) {
            Future<Boolean> future = executor.submit(new EmailTask("user_" + i + "@example.com"));
            System.out.println("Status: " + future.get()); // BLOCKS main until this email is done
        }

        System.out.println("Main ended"); // only prints after ALL results have been read
        executor.shutdown();
    }
}

Without reading the status — main is NOT blocked:

for (int i = 1; i <= 10; i++) {
    executor.submit(new EmailTask("user_" + i + "@example.com")); // no future.get()
}
System.out.println("Main ended"); // prints immediately; emails keep running in the background
executor.shutdown();

Added improvement — submit everything first, then collect (not shown in class):

import java.util.ArrayList;
import java.util.List;

List<Future<Boolean>> futures = new ArrayList<>();

for (int i = 1; i <= 10; i++) {
    futures.add(executor.submit(new EmailTask("user_" + i + "@example.com")));
}
// All 10 tasks are now queued/running across the 2 workers.

for (Future<Boolean> f : futures) {
    System.out.println("Status: " + f.get()); // main only waits for whatever isn't finished yet
}
executor.shutdown();

📌 Important Points / Common Mistakes

  • Callable returns a result (via Future); Runnable doesn't give the caller anything.
  • Future.get() blocks the calling thread until the result arrives — getting a result isn't free.
  • Reading the result is what blocks; submitting alone does not (main ended immediately without get()).
  • Calling get() inside the submission loop serializes your work — consider submitting everything first, then collecting results.
  • Fixed = you pick the count; Cached = dynamic, grows with load; Single = exactly one thread.
  • A cached pool reuses idle threads; busy (e.g. sleeping) threads can't be reused, so it launches more.
  • Sizing a pool is an estimate-and-observe exercise, not a formula — start tiny, don't go fat.
  • Print thread names and put plenty of print statements when learning concurrency — it makes the flow visible.
