🧠 Key Concepts

Recap: ArrayList vs LinkedList Complexity

For reading: ArrayList is O(1) (direct index access), LinkedList is O(N) (must traverse). For inserting into the middle of a LinkedList: you first need to traverse to the desired location (O(N)), then the actual insertion itself is O(1) — so overall it's described as O(N) + O(1), commonly summarized as O(N) once traversal is required.

What is a Set?

A Set is a Collection interface where the defining rule is uniqueness — no duplicates allowed. Unlike List (which allows duplicates and maintains order), Set specifically exists for when your requirement is: unique elements, and order doesn't matter.

List vs Set — Choosing Based on Requirement

If you want an ordered collection where duplicates are allowed → use List (ArrayList/LinkedList). If you want uniqueness (no duplicates) → use a class under Set. Classes under Set: HashSet, LinkedHashSet, TreeSet (this class focuses on HashSet).

Why NOT Just Brute-Force Check for Duplicates?

A naive approach: before adding any element, check it against every existing element to see if it's already present. But if a Set already has 10,000 elements, adding ONE more element would require checking it against all 10,000 — this is slow and doesn't scale. The real question: is there a mechanism where all duplicate elements automatically go to the SAME location, so you never need to search the whole set?

hashCode() — A Unique(ish) Number Per Object

Every object in Java gets a number assigned by the JVM — its hashCode. This number can be positive or negative. For practical purposes, assume it's unique per object — though in rare corner cases, JVM MAY assign the same hashCode to two genuinely different objects (this limitation is not something developers or even the JVM can fully control). hashCode() is defined in the Object class, so every object inherits it.

The Bucket Mechanism — How HashSet Decides WHERE to Store

When you create a HashSet, it internally creates a set of buckets (a table), with a default capacity of 16 (indices 0 to 15). When adding an element, its hashCode() is calculated, and a formula is applied to convert that hashCode into a specific bucket index — so the element always lands in a predictable, calculable position, without ever needing to scan the whole set.

The Formula: hashCode & (capacity − 1)

The classic mechanism uses the bitwise AND operator (&): hashCode & (n - 1), where n is the total capacity (e.g. 16). This always produces a number between 0 and n−1 (e.g. 0 to 15) — guaranteeing the result always maps to a valid bucket index. Note: the exact formula has been refined in newer Java versions, but the core idea (hashCode → deterministic bucket index) is what matters — you don't need to memorize the exact bitwise formula.

Same Input → Same Output (Key Insight)

Since hashCode is deterministic for a given object's state, and the formula is fixed, the same element will always compute to the same bucket index. So if you try to add "Chennai" five times, it always lands in the exact same bucket — no searching required, just recomputing the formula and checking that ONE location.

Why HashSet Appears "Unordered"

This is the single concept the instructor called out as the mark of really understanding Java: elements are placed based on their calculated bucket index, which has nothing to do with insertion order. You might insert "Bangalore" first, but its hashCode-derived bucket might be far down the list, while a later-inserted element lands in an earlier bucket. When you iterate/print the set, you get bucket order — NOT insertion order — which is why it looks "unordered" and unpredictable.

Checking for Duplicates — hashCode First, Then equals()

When adding an element: (1) compute its hashCode → determine the target bucket. (2) If that bucket is EMPTY, add the element there. (3) If something already exists at that bucket, call .equals() to check if it's a TRUE duplicate. If equals() returns true → ignore (don't add). If false → this is a hash collision (different object, same bucket) → add it as an additional node.

Hash Collision — Two Different Objects, Same hashCode

In rare cases, JVM may assign the same hashCode to two genuinely different objects — this is a known limitation, not something JVM or developers fully control. When this happens, both objects compute to the same bucket, but equals() correctly identifies they are NOT duplicates, so both get stored — this scenario is called a hash collision.

Buckets Are Internally Linked Lists

To handle hash collisions, each bucket isn't just a single slot — it's implemented as a linked list. Normally each bucket holds just one node (one element). If a collision occurs, a second node is attached to the existing one at that bucket, forming a short linked list at that specific index.

The hashCode()/equals() Contract — Classic Interview Question
Rule 1: If two objects are equal (via equals()) → their hashCode() must be the same.

Rule 2: If two objects have the same hashCode() → they may or may not be equal.

Rule 1 is a hard requirement — equal objects MUST produce the same hashCode, or the hashing mechanism breaks. Rule 2 is the reverse case — matching hashCodes don't guarantee equality (this is exactly the hash collision scenario), so equals() must always be used as the final confirmation.

Live Demo: Forcing a Hash Collision

To deliberately demonstrate this (not standard practice, purely for learning), the instructor overrode hashCode() in an Employee class to always return a fixed number. Two different Employee objects were then created — both computed to the same bucket (e.g. bucket 13). Since equals() correctly determined they were different objects, BOTH were stored — as two separate nodes within that bucket's linked list.

HashSet is Internally Backed by HashMap

HashSet has no independent storage implementation of its own — internally, it creates and delegates to a HashMap object. When you call hashSet.add(element), it internally calls map.put(element, someValue). This is why the instructor emphasized: "whoever learns Set is also learning Map" — since the internal mechanics are shared. Inside HashMap, each bucket entry is technically a Node (an inner class holding key, value, and a reference to the next node) — this Node IS the linked list structure used to handle collisions.

Rehashing — Flagged for a Future Class

Just like ArrayList grows when it runs out of space, HashSet's internal bucket table also grows (commonly doubling) as more elements are added — this process is called rehashing, and what happens to existing elements during rehashing was explicitly deferred to a future session.

💻 Code Snippets / Examples

Creating a HashSet and observing "unordered" behavior:

import java.util.HashSet;
import java.util.Set;

class Driver {
    public static void main(String[] args) {
        Set cities = new HashSet<>();

        cities.add("Bangalore");
        cities.add("Jaipur");
        cities.add("Mysore");
        cities.add("Hyderabad");
        cities.add("Chennai");
        cities.add("Chennai"); // duplicate — will be ignored

        for (String city : cities) {
            System.out.println(city);
        }
        // Output order does NOT match insertion order —
        // it reflects bucket order based on each city's hashCode
        // "Chennai" appears only once — duplicate was silently ignored
    }
}

Forcing a hash collision — demonstration purposes only:

class Employee {
    String name;

    public Employee(String name) {
        this.name = name;
    }

    @Override
    public int hashCode() {
        return 100; // forced — NOT normal practice, purely to demonstrate collision handling
    }
}
class Driver {
    public static void main(String[] args) {
        Set employees = new HashSet<>();

        Employee e1 = new Employee("Kodewala");
        Employee e2 = new Employee("Devwin");

        employees.add(e1); // computes to some bucket, e.g. bucket 13
        employees.add(e2); // SAME hashCode -> same bucket 13

        // equals() (default, from Object class) says e1 != e2 (different objects)
        // Both are added as SEPARATE nodes within bucket 13's linked list

        System.out.println(employees.size()); // 2 — both stored, since they aren't truly equal
    }
}

The bucket index formula (conceptual):

int hashCode = someObject.hashCode();
int capacity = 16; // default HashSet capacity
int bucketIndex = hashCode & (capacity - 1); // bitwise AND -> always between 0 and 15

📌 Important Points / Common Mistakes

  • Set guarantees uniqueness (no duplicates) but does NOT guarantee order — this is the key trade-off vs List.
  • HashSet uses each element's hashCode() + a formula to determine a deterministic bucket, avoiding the need to scan the whole collection for duplicates.
  • "Unordered" specifically means: iteration order reflects bucket placement (based on hashCode), NOT insertion order.
  • hashCode()/equals() contract: equal objects MUST have the same hashCode; same hashCode does NOT guarantee the objects are equal.
  • A hash collision (two different objects, same hashCode) is a rare JVM-level limitation — handled gracefully via linked lists within buckets, not a bug in your code.
  • HashSet has no independent implementation — it's built entirely on top of HashMap internally.
  • Never manually force a hashCode override like the demo unless you're deliberately studying collision behavior — this was for learning purposes only, not real-world practice.
