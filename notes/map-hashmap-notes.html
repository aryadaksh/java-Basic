🧠 Key Concepts

Recap: List and Set

ArrayList — dynamically growing, index-based, best for random/index access; not ideal for frequent middle insertion/deletion (shifting required). LinkedList — dynamically growing, good for frequent insertion/deletion, but reading by index requires traversal. Set — used when uniqueness is required: HashSet (unique + unordered), LinkedHashSet (unique + insertion order), TreeSet (unique + sorted order, via Comparable/compareTo(), O(log n) search).

Why Move From Set to Map?

The course explicitly connects these topics: HashSet internally uses HashMap. LinkedHashSet internally uses LinkedHashMap. TreeSet internally uses TreeMap. Since every Set implementation is actually built on top of the corresponding Map implementation, truly understanding Set internals requires first understanding how Map works.

What is a Map?

A Map stores data as key-value pairs. The key must be unique; values may repeat. Whenever a requirement naturally looks like "unique identifier → associated data," Map is the right structure. Typical examples: student → marks, product → price, state → capital, country → capital.

HashMap Basics

HashMap<String, String> stores key-value pairs. Default initial capacity: 16 (same as HashSet). HashMap is unordered — never assume insertion order will be preserved. Values CAN be duplicated — but keys cannot exist as separate mappings if duplicated. If you insert the same key again, its associated value is simply replaced/overwritten, not added as a new entry.

Only the Key Matters for Bucket Placement

Hashing and equality checks are performed on the key — the value has no role in determining which bucket an entry goes to. Two entries with completely different values but the same key are still treated as the same mapping (the newer value simply replaces the older one).

How HashSet Uses HashMap Internally — The Dummy Value Trick

HashSet conceptually stores only elements (no key-value concept) — but HashMap requires both a key and a value to function. To bridge this gap: HashSet internally stores each Set element as the HashMap's key, and supplies a constant placeholder/dummy object as the value for every entry. This dummy value has no meaning to the HashSet user — it exists purely so HashMap can be reused as HashSet's backing implementation, without needing a completely separate, duplicate implementation. This connects to the backward compatibility principle covered earlier — changing HOW something is implemented internally shouldn't break the existing public API/behavior.

HashMap.put() — Behavior and Return Value

put(key, value) adds or updates a mapping. Its return type is V (the value type) — specifically, it returns the PREVIOUS value associated with that key. If the key is new, put() returns null (nothing existed before). If the key already existed, put() returns the old value and stores the new one in its place.

Example: put("Gujarat", "Gandhinagar") → returns null (first time this key is used). put("Gujarat", "Ahmedabad") → returns "Gandhinagar" (the previous value), and now stores "Ahmedabad" for that key.

Why This Matters — Read the Documentation

The instructor specifically stressed: don't guess what a method returns — read Java's method documentation/comments to understand return values properly (like put()'s "returns previous value" behavior, which isn't obvious from the method name alone).

HashMap Internal Working — Full Flow
  1. A key is supplied to put().
  2. HashMap computes the key's hash via hashCode().
  3. That hash is processed to determine the target bucket/index (classically via a bitwise AND with capacity - 1).
  4. If the bucket is empty, a new entry/node is created there.
  5. If the bucket already has an entry, HashMap compares keys using equals().
  6. If the existing key and new key are equal → the mapping's value is replaced.
  7. If the keys are NOT equal → this is a hash collision; HashMap finds an appropriate place within that bucket's structure and adds the new mapping alongside the existing one.
  8. Treeification applies here too, once collisions in a bucket become high enough (same threshold/capacity conditions as HashSet).
Hash Collision vs Duplicate Key — The Critical Distinction

A hash collision does NOT automatically mean two keys are equal — it just means they landed in the same bucket. HashMap always uses equals() AFTER locating the bucket to determine the TRUE relationship: if equals() returns true → it's the same logical key → value is replaced. If equals() returns false → it's a collision involving a genuinely different key → the new mapping is stored alongside the existing one (not replacing it).

LinkedHashMap and TreeMap

LinkedHashMap maintains insertion-order behavior via its internal linked structure — mirroring LinkedHashSet. TreeMap keeps mappings sorted according to the key — mirroring TreeSet. Important: TreeMap's sorting is based purely on the key, never the value. Hashing (for HashMap) is likewise applied only to keys — values never participate in bucket selection.

Map is NOT Part of the Collection Interface

Map is part of the Java Collections Framework overall, but it is NOT a child of the Collection interface. List and Set are both Collection types (they hold individual elements). Map has a fundamentally different structure — it stores key-value pairs, not standalone elements — so it maintains its own separate interface hierarchy rather than extending Collection.

Iterating Over a Map — entrySet()

Since Map doesn't directly provide the same Iterator mechanism that Collection types do, you iterate using entrySet() — which returns a Set of Map.Entry objects. Because the result IS a Set, you can obtain a standard Iterator from it. Each Map.Entry represents one key-value pair, exposing entry.getKey() and entry.getValue().

get() vs contains() — Map vs Set

map.get(key) returns the value associated with that key. For a Set, there's no meaningful "value" to retrieve — its whole purpose is membership/uniqueness checking, so it exposes contains(element) (returning boolean) instead of a get()-style method.

Null Handling — Don't Generalize

Null behavior varies across Map implementations, and this must NOT be generalized. Specifically noted: TreeMap does not allow a null key in the relevant comparison-based scenario (since it needs to compare keys to maintain sorted order — same reasoning as TreeSet). Always check the specific implementation and Java version/documentation rather than assuming a blanket rule.

💻 Code Snippets / Examples

Basic HashMap usage — put(), duplicate key behavior:

import java.util.HashMap;
import java.util.Map;

class Driver {
    public static void main(String[] args) {
        Map stateCapitals = new HashMap<>();

        String r1 = stateCapitals.put("Gujarat", "Gandhinagar");
        System.out.println(r1); // null — key is new

        String r2 = stateCapitals.put("Gujarat", "Ahmedabad"); // same key again
        System.out.println(r2); // "Gandhinagar" — the PREVIOUS value

        System.out.println(stateCapitals.get("Gujarat")); // "Ahmedabad" — replaced
        System.out.println(stateCapitals.size()); // 1 — NOT 2, key wasn't duplicated
    }
}

Values CAN repeat, even though keys can't:

Map productCategory = new HashMap<>();
productCategory.put("iPhone", "Electronics");
productCategory.put("Laptop", "Electronics"); // same VALUE, different key — totally fine
productCategory.put("Shirt", "Clothing");

System.out.println(productCategory.size()); // 3 — all distinct keys allowed

Conceptual illustration — how HashSet uses HashMap with a dummy value internally:

// Conceptual illustration of HashSet's internal delegation (not literal JDK source)
class MyHashSet {
    private static final Object DUMMY = new Object(); // constant placeholder
    private HashMap backingMap = new HashMap<>();

    public boolean add(E element) {
        return backingMap.put(element, DUMMY) == null;
        // if put() returns null, it was a NEW key -> successfully added
        // if put() returns the dummy (non-null), it already existed -> duplicate
    }

    public boolean contains(E element) {
        return backingMap.containsKey(element);
    }
}

Iterating a Map using entrySet():

Map countryCapital = new HashMap<>();
countryCapital.put("India", "New Delhi");
countryCapital.put("Japan", "Tokyo");
countryCapital.put("France", "Paris");

for (Map.Entry entry : countryCapital.entrySet()) {
    String key = entry.getKey();
    String value = entry.getValue();
    System.out.println(key + " -> " + value);
}

Manually obtaining an Iterator via entrySet():

import java.util.Iterator;
import java.util.Set;

Set> entries = countryCapital.entrySet();
Iterator> it = entries.iterator();

while (it.hasNext()) {
    Map.Entry entry = it.next();
    System.out.println(entry.getKey() + " : " + entry.getValue());
}

get() vs contains() — Map vs Set:

Map marks = new HashMap<>();
marks.put("Rahul", 85);

int value = marks.get("Rahul");        // 85 — returns the associated VALUE
boolean exists = marks.containsKey("Rahul"); // true — Map also has containsKey/containsValue

Set names = new HashSet<>();
names.add("Rahul");
boolean present = names.contains("Rahul"); // true — Set only checks MEMBERSHIP, no value to fetch

TreeMap — sorted by key, not value:

import java.util.TreeMap;

Map scores = new TreeMap<>();
scores.put("Charlie", 60);
scores.put("Alice", 95);
scores.put("Bob", 80);

for (Map.Entry entry : scores.entrySet()) {
    System.out.println(entry.getKey() + " -> " + entry.getValue());
}
// Output sorted by KEY (alphabetically): Alice, Bob, Charlie
// — regardless of insertion order or the VALUES

LinkedHashMap — preserves insertion order:

import java.util.LinkedHashMap;

Map visits = new LinkedHashMap<>();
visits.put("Page3", "10:15");
visits.put("Page1", "10:10");
visits.put("Page2", "10:12");

for (String page : visits.keySet()) {
    System.out.println(page);
}
// Output: Page3, Page1, Page2 — exact insertion order preserved

📌 Important Points / Common Mistakes

  • Map keys are unique; values can repeat freely.
  • Inserting the same key again REPLACES the value — it does not create a duplicate mapping.
  • Only the KEY participates in hashing/bucket placement — the value has no role in this.
  • put() returns the PREVIOUS value (or null if new) — not the newly inserted value, and not a boolean.
  • HashSet has no independent implementation — it's built entirely on HashMap, using a dummy value trick.
  • A hash collision (same bucket) is NOT the same as a duplicate key (same key via equals()) — always distinguish these clearly.
  • Map is NOT part of the Collection interface hierarchy — a common point of confusion.
  • Use entrySet() (not keySet() alone, unless you only need keys) to iterate both keys and values efficiently together.
  • TreeMap sorts by key only, never by value.
  • Don't assume null-handling rules apply uniformly across all Map implementations — check the specific type (e.g. TreeMap disallows null keys).
