His reason: "in the company you won't feel awkward when somebody asks you to review your code." The demos showed admin and customer roles, search by name / brand / price range / category, add to cart, place and cancel order, order history, profile/address update and seller flows.

The same feedback came up in demo after demo, so the notes are grouped by theme instead of by day, with tags showing when it was said: Oct 26 Oct 27. Student names are left out, and the recordings are noisy, so student-specific details are summarised only where the transcript is clear.

📋 Quick Review Checklist

Short items, each listed once. The longer topics have their own cards below.

ThemeWhat the instructor flaggedFix
One giant class
Oct 26Oct 27		 Everything written in one class ("you should have 20 to 30 classes"). On Oct 27 he contrasted a 50-class project with one finished in 3 classes: "which approach is modular?" Split by responsibility — product, cart, order history, place order, login, invoice, delivery — plus service / repository / exception layers.
main in every class
Oct 26		 Several classes had their own main only to call a method while testing. "Do we need a main method in every class?" One entry point per project. Remove the rest and test through test classes.
Class naming & empty classes
Oct 26		 A class named with the word "logic" was questioned (the exact name is unclear in the recording); a product service class sat empty. Name classes by responsibility (customer service / management); give every class a purpose or delete it.
Private constructors
Oct 26Oct 27		 Asked repeatedly: why private? Answer: nobody can create an object outside the class. Removing it changed nothing in behaviour. On Oct 27 it was on a static-method utility class (invoice printing); he accepted it if the class will always stay a pure utility, but asked where the idea came from — it also blocks creating objects later. Use it deliberately for utility classes, not out of habit.
Connection never closed
Oct 26		 "You're opening the connection — where are you closing it?" A student's DB-helper class on Oct 27 used try-with-resources, so resources close automatically — he approved. Close the ResultSet, Statement and Connection every time (snippet 3).
Guest cart in memory
Oct 27		 A guest repository kept guest users and their carts in RAM. Good idea, but a restart wipes it, whereas a real cart is still there a month later. Store the guest cart in the database.
Stock check too late
Oct 26		 A customer added 12 units to the cart although only 10 existed; the order failed only at "place order". The product page should show the available quantity. Check and show stock at add-to-cart; consider a maximum order quantity per customer.
Validation
Oct 27		 Praised: product validation (brand not null/empty, price above zero, valid quantity, category, email/mobile format). Criticised: addresses accepted like "XYZ". Keep checks in one place; set a minimum address length (about 25–50 characters).
Unique constraints
Oct 27		 A second registration with the same email was rejected — email is a unique constraint. Good. Keep unique constraints in the table design (the CSV upload below needs the same).
Parent / child delete
Oct 27		 A customer with orders can't be deleted — the orders (child rows) reference the customer. Delete the child records first, then the parent.
Generated order ID
Oct 26Oct 27		 He asked what return-generated-keys is, and questioned a "select last insert ID" approach used to fetch the new order's ID (the details are unclear in the recording). Ask JDBC for the generated key when you insert (snippet 3).
Java comments
Oct 27		 Nobody had written any. People won't have time to read line by line, and complicated logic stays unclear even then. Write what each class is responsible for and what the critical methods do — "that's what industry expects".

🧠 Detailed Feedback

Keep Configuration Outside the Code Oct 26Oct 27
  • What was hard-coded: database name, URL, port, username, password — and also the SQL queries and table names, and values like a GST rate. Port 3306 isn't guaranteed on other systems either.
  • Why move it out: when the project goes to QA and later production, the database name differs. Changing Java code means recompile, redeploy and a fresh test cycle — risky. A property file lives outside the code, so you change it without rebuilding, and only minimal (end-to-end) testing is needed.
  • A property file is just key = value — e.g. query1 = select * from … — and you read the keys into variables. You can keep separate property files for the database and for the SQL.
  • Passing credentials from the environment was accepted. Later in the course database credentials move to a secure wallet; storing them in a property file is only for now.
  • Don't copy-paste settings around — use a utility to read them. Several students had hard-coded values and fixed them overnight.
🔥 Interview line: asked "what best practice do you follow?" — "We separate code and configuration." Researching "code plus configuration" was suggested homework.
Statement vs PreparedStatement — The Instructor's Correction Oct 26
  • He first checked the class knew a DAO is a Data Access Object, then asked why PreparedStatement was used.
  • Students answered in terms of hitting the database once or many times. He corrected that: it isn't about how many times you hit the database — it's about query compilation.
  • Statement: run it 100 times and the query is compiled 100 times. PreparedStatement: with ? placeholders the query is static — compiled once and reused 100 times. Compilation takes time, so it is faster, and it is also more secure.
Transactions in Place-Order Oct 26Oct 27
  • Oct 26: he asked who had turned off auto-commit for flows with several queries (updating the cart, then the stock, then marking the order paid). No clear taker; he stressed it isn't only about rollback — related updates should be one unit.
  • Oct 27: a student's place-order method — "the main complex method of this project" — used a single connection for the whole order, set auto-commit to false before the transaction, and set it back to true once the order completed so other transactions don't interfere. That makes rollback possible if something fails. The instructor moved on with approval.
Bulk CSV Upload — Batching and Duplicates Oct 26Oct 27
  • Product import from a CSV file: "are you using JDBC batch?" He later explained why big uploads on real sites say the data will be available "after 5 minutes" — it is batching and updating in the background.
  • The duplicate problem: the project used the file's own key as the product ID, so uploading the same CSV a second time added every product again. Who decides the product ID? Define what makes a product unique — he called for a composite key (or unique constraint) — otherwise a repeated upload duplicates the data.
Who Gets the Last Items? — Optimistic Locking Oct 26Oct 27

Scenario: 15 items in stock, 20 customers ordering (think "only 3 donuts left, 100 people trying"). Class answers: whoever clicked first; a SQL lock (he called that "a little bit correct"). His point: it doesn't matter who clicked first — whoever completes the transaction first gets the product.

StepWhat happens
1Every buyer reads the record: version 1, with the stock.
2Everyone goes off to pay. The first to pay comes back, finds the version still 1 → updates the stock; the record becomes version 2.
3The others come back expecting version 1 but find 2 → optimistic locking exception: someone else got the product.
4They are refunded — within 24 hours, or "3 to 5 business working days" — with an email, or credited to a wallet, depending on the requirement.
  • Holding the stock in case someone cancels adds complexity and a bad experience ("waiting for other customers to cancel"), so it isn't done.
  • A stock check before payment still belongs in the cart flow.
  • Spring Data JPA/Hibernate have a built-in version concept — covered later; he told them now because the question is famous.
🔥 Interview question: "15 in stock, 20 buyers — who gets it?" He said it "will be asked to each and every one".
Audit Columns — A Minimum Requirement Oct 26Oct 27
  • Every table needs: created by, created date, updated by, updated date, deleted by, deleted date — "that's the minimum requirement".
  • Why: a user says "I did not place this order" — check who placed it: if it shows his username, he did; if the system placed it, the column says system; if someone else deleted a record, that person is recorded. Without these columns you can't tell whether a record was deleted by the system, a user or a developer — whether you delete or update, record who did it.
  • Audit means the data is used to audit reports and activity.
Code Coverage and Test Structure Oct 26Oct 27
  • Numbers seen in the demos ranged from the teens to the mid-70s (for example 16%, 25%, 62% for source only, 73%, 74%, 76%, 80%). The target is a minimum of 85%; below it the pipeline rejects the build and emails the whole engineering team, so you can't hand it to testing.
  • Measure the source only: close the test folder — only src matters. One project showed 62% for source against a higher figure overall.
  • Keep tests out of the source code: test classes placed inside the main source drag coverage down (one project was at about 25%). Tests live in the test folder.
  • Too few tests: a project with 9 source classes and only a handful of tests — "this is a standard process, you cannot ignore it".
  • Test exceptions too — he reminded students to write tests that expect an exception class.
  • Private methods: students made methods public so they could test them. Don't. Design classes with focused methods so they're easy to test, but don't cut required functionality just to make tests easy.
  • Real-world cost: a small use case already has hundreds of tests, and a test run can take about an hour in a company — which is why there is an option to skip tests/coverage temporarily while you experiment.
🔥 Interview line: asked about coverage, one student said 84%; his advice: "85 is our requirement." To reach it, write all the possible test cases — and stop treating this exercise as optional.
Exceptions — Know Where Each One Is Thrown Oct 26Oct 27
  • He asked students to explain why a custom exception exists and to reproduce the scenario that throws it — including where an invalid-order exception was used in a project (one student first answered "when stock is exceeded", which is not what the code did).
  • Product not found: a product that isn't in the database never appears in search, so the exception belongs where a product is looked up directly (get product by ID). One project had only two custom exceptions and used built-in ones (SQLException, IllegalArgumentException) elsewhere.
  • Find usages fast: right-click the class → References → Workspace shows every place it is used — "this is how you want to track your code".
🔥 Interview line: "What custom exceptions did you define in your product?" Anyone with real project experience can list them — remember 10 to 20 exceptions of your own product.
What If the Database Goes Down? Oct 27
  • The demo: he had a student stop the MySQL service from Windows Services and run the application again. The JDBC connection failed with the message that the last packet was sent successfully but the driver received nothing back from the server. Restarting the service fixed it (it is a Windows service and starts with the computer).
  • Real systems: a database is software too, so it will go down. The application should send a notification and fall back to a secondary server. This is advanced — "just make a note": what happens to your application when the primary server goes down?
Using AI Wisely Oct 26
  • Think first: use your own thought process, then tell the AI "I have this idea, help me — what's the best approach?" instead of just asking it to write the project. He asked students how much AI they had used and told them to be honest.
  • Don't upload documents. He said that when he searched, AI handed back a document someone had uploaded.
  • Don't give AI your whole project. A student asked AI to generate tests for the data-access code and the AI kept dropping the database/tables. Be explicit: "write tests for this code only — do not delete anything without my permission."
  • It shows: when copied or AI-generated code breaks and a student can't say why, it's obvious. His upside: "at least you learned how to check the code."
The Instructor's Expectations (Non-Technical) and the Next Class
  • The purpose of the project was process — Maven, the database connection, test cases, coverage — not clever logic.
  • Students were given 5–6 days; the instructor said placement will be better if the project is done seriously, and that anyone who did it properly "can get a job easily". He urged students to come every day and present whatever they have: "you are not losing anything."
  • Next session: the logging framework (the recording says "Log 40. J", read here as Log4j — unclear).
💡 Added clarification:
  • Optimistic vs pessimistic locking: pessimistic locks the row while someone works on it (e.g. select … for update), blocking others; optimistic lets everyone proceed and detects the conflict at update time with a version check — snippet 2. The student's "SQL lock" answer was the pessimistic kind.
  • Credentials: a plain property file is fine for learning; real projects keep passwords in environment variables or a secrets manager, consistent with the "secure wallet" he mentioned.
  • Skipping tests: in Maven that is -DskipTests, and your coverage plugin has its own skip switch — only for experiments, since the pipeline will still enforce 85%.

💻 Code Snippets / Examples

Note on this code: the instructor reviewed students' code on screen and the transcript doesn't contain it, so these are my illustrations of the ideas he described — the names, tables and values are mine. Nothing was run against a database.

1. Configuration outside the code (property file + loader):

# db.properties — outside the Java code; change values without recompiling
db.url=jdbc:mysql://localhost:3306/ecommerce
db.user=app_user
db.password=change_me
query.getProduct=select * from product where id = ?
query.updateStock=update product set stock = ? where id = ?
Properties props = new Properties();
try (InputStream in = getClass().getClassLoader().getResourceAsStream("db.properties")) {
    props.load(in);
}
String url = props.getProperty("db.url");
String sql = props.getProperty("query.getProduct");     // change the query without touching Java code

2. Optimistic locking — the version check decides who gets the product:

-- the product table has a version column; 'version' below is the value the buyer read earlier
update product
   set stock = stock - ?, version = version + 1
 where id = ? and version = ?;
int rows = ps.executeUpdate();
if (rows == 0) {
    // someone else updated the row first: this buyer lost -> roll back, refund, notify
    throw new ProductAlreadySoldException("Product was bought by someone else");   // your own exception
}

3. try-with-resources and the generated order ID in one insert:

String sql = "insert into orders (customer_id, status) values (?, ?)";

try (Connection con = DriverManager.getConnection(url, user, password);
     PreparedStatement ps = con.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {

    ps.setInt(1, customerId);
    ps.setString(2, "CREATED");
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            long orderId = keys.getLong(1);       // the new order's ID, needed by later queries
        }
    }
}   // ResultSet, PreparedStatement and Connection are closed automatically

4. Testing that an exception is thrown:

@Test
void getProduct_unknownId_throwsProductNotFound() {
    assertThrows(ProductNotFoundException.class, () -> productService.getProductById(999));
}
// JUnit 4 style: @Test(expected = ProductNotFoundException.class)

5. Audit columns on a table:

create table orders (
