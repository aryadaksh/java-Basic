🧠 Key Concepts

Recap: Future Gives the Result — But Blocks

The advantage of Future is that we were able to get the result. The problem: we were blocking the thread. If you call get(), the current thread waits until the result arrives.

CompletableFuture — Java 8's Answer

CompletableFuture is a class introduced in Java 1.8. With it you can:

  • Create a chain of operations — combine many operations together.
  • Let those operations run independently — you don't have to wait.
  • Work asynchronously.
  • Still call get() whenever the result is ready, if you want to.

The class provides a lot of built-in methods (more than 50, per the instructor) from which you assemble a chain that fits your requirement.

supplyAsync() — Start Work That Returns Something

Simplest usage: CompletableFuture.supplyAsync(...). "Supply" means it just returns something and takes no input. His example: supply the value 20, getting back a CompletableFuture<Integer>. get() on it is still blocking (he threw the checked exception out of main for the demo) and returned 20. Writing a lambda body lets you put more code inside, e.g. printing the current thread's name.

Who Executes It? The ForkJoinPool Common Pool

Printing the thread name showed the task ran on a worker thread that was automatically picked from the existing ForkJoin common pool (the name showed a worker number — "worker 9" in his run). You don't have to decide how many threads you need. If you have your own pool, you can supply it as well.

thenApply() — Transform the Result

To perform an operation on the output of the first operation, chain thenApply(...). Example: the first stage yields 20; thenApply multiplies it. The output shows the transformed value — and no blocking was done here. In the old Future style, to run another operation on a result you would get the result of one thread (blocked), then launch another operation, and so on.

thenApply vs thenApplyAsync — Same Thread or Worker Thread?

He captured the current thread inside each stage:

MethodObserved behavior
thenApplyThe same worker thread did the job — "only a single thread did the job"; effectively single-threaded for that chain (the only other thread printed was main).
thenApplyAsyncA worker thread from the pool does the job — it may be a new worker or a reused one, but it is not guaranteed to be the same thread.

His summary: "There is no difference between sync versus async — sync uses the current thread, async uses a separate worker thread." Another thenApply (e.g. multiply by 5) keeps the chain going, and the results come out correctly — it will decide which thread to use.

The stages are chained and run asynchronously; nothing in between blocks the calling thread.

🔥 The Fundamental Difference: Future vs CompletableFuture

Many people get confused: "Sir, get() is blocking here and blocking there — so what's the difference?" His answer:

FutureCompletableFuture
Gives you the result, but blockingAsynchronous — you can create a chain of operations, so it is effectively non-blocking
Limited options — you can basically just getA rich set of methods to chain, combine, transform and handle errors
To run a second step: launch a thread, get (block), pass the result to another thread, get againChain the steps; "you don't have to wait"

You only need get() if you actually want the final value at the end.

thenCombine() — Merge Two Independent Results

Scenario: two separate CompletableFutures (CF1 and CF2), each producing an Integer, and you want to combine the result of this as well as the result of that. You call cf1.thenCombine(cf2, ...), passing the second future and a function that takes both results; it returns a new CompletableFuture<Integer> holding the combined result. In his demo the two chains produced 200 and 300, and the combined result was 500. The same sync/async split applies: the plain version uses the current thread, the Async version a worker thread.

get() vs join()

To read the combined result you can use get() or join(). They do the same work — the only difference is the exception part: join() doesn't throw the checked exception, so you don't need the extra exception handling that get() requires.

thenRun() — Nothing to Return

thenRun is void — it doesn't return anything. His demo: supplyAsync of 20, then thenRun printing something like a test message. Since nothing comes back, there's no point in printing a result; it simply runs after the previous stage completes.

The Consumer Style — Take the Result, Return Nothing

He also described another family of method that takes a Consumer — it consumes the value (the accept method, or andThen) and returns nothing: "this will just consume it."

Functional Interfaces Under the Hood — A Definite Interview Topic

supplyAsync takes a Supplier — a functional interface. Read functional interfaces and you'll see Supplier, Consumer, Function, BiFunction used internally throughout CompletableFuture's methods.

InterfaceWhat it doesUsed by
SupplierTakes no input, just supplies/returns a valuesupplyAsync
Function (A → B)Takes an input of type A, applies some logic / transforms it, gives back type BthenApply
BiFunctionTakes two inputs and performs some operationthenCombine
ConsumerTakes an input and consumes it — returns nothing (accept method)the "consume the result" method

In the interview they will ask: "What functional interfaces do you know? What is a Supplier, a Consumer, a Function, a BiFunction?" — and then the common CompletableFuture operations you did in class.

thenCompose(), exceptionally(), handle() — and the Other 50+
  • thenCompose — he described it as making sure the existing task completes first, then performing the next.
  • exceptionally — handles the exception: if you want to handle an exception in CompletableFuture, you use exceptionally.
  • handle — lets you handle both scenarios, error versus success.
  • Others he named in passing: run-after / run-before style methods, "complete any of," cancel, complete.

⚠️ Clarifications Added (Not Stated This Way in Class)
  • thenApply's thread, precisely: plain thenApply runs on the thread that completed the previous stage — or on the calling thread if that stage had already finished. In his demo that was the same pool worker. thenApplyAsync submits the step to the pool (the common ForkJoinPool by default, or an Executor you pass in).
  • join() exception: join() skips the checked exceptions (InterruptedException, ExecutionException) that get() declares; if a stage failed, join() throws an unchecked CompletionException instead.
  • thenCompose is normally used when the next step itself returns a CompletableFuture (a dependent async call) — it flattens the nesting, much like flatMap. His description ("make sure the existing task completes, then perform the next") is a loose version of that.
  • Consumer-style method name: the transcript doesn't name it; the standard one is thenAccept.
  • Keep the program alive: common-pool worker threads are daemon threads, so if main finishes before the async work does, the JVM may exit first. In demos, that's why main calls get()/join() (or waits some other way) before ending.

💻 Code Snippets / Examples

Note on this code: the instructor typed the demos live and the audio is garbled, so the code below is reconstructed from his spoken walkthrough. The numbers 200 / 300 / 500 are the results he stated; the exact multipliers in each stage are my illustration.

supplyAsync — and which thread ran it:

import java.util.concurrent.CompletableFuture;

public class Driver {
    public static void main(String[] args) throws Exception {
        CompletableFuture<Integer> cf = CompletableFuture.supplyAsync(() -> {
            System.out.println(Thread.currentThread().getName());
            // prints something like: ForkJoinPool.commonPool-worker-9
            return 20;
        });

        System.out.println(cf.get());   // 20 — get() is still a blocking call
    }
}

Supplying your own pool:

ExecutorService pool = Executors.newFixedThreadPool(3);

CompletableFuture<Integer> cf =
        CompletableFuture.supplyAsync(() -> 20, pool);   // runs on YOUR pool, not the common pool

A chain with thenApply — no blocking between steps:

CompletableFuture<Integer> result = CompletableFuture
        .supplyAsync(() -> 20)          // Supplier: no input, returns 20
        .thenApply(n -> n * 10)         // Function: transform the result
        .thenApply(n -> n * 5);         // another transformation, chained

System.out.println(result.get());       // only block here, because we want the final value

thenApply vs thenApplyAsync — compare the thread names:

CompletableFuture.supplyAsync(() -> {
        System.out.println("supply  : " + Thread.currentThread().getName());
        return 20;
    })
    .thenApply(n -> {
        System.out.println("apply   : " + Thread.currentThread().getName()); // same worker, as seen in class
        return n * 10;
    })
    .thenApplyAsync(n -> {
        System.out.println("applyAsync: " + Thread.currentThread().getName()); // a pool worker (may differ)
        return n * 5;
    })
    .join();

thenCombine — merge two independent async results (200 + 300 = 500):

CompletableFuture<Integer> cf1 = CompletableFuture
        .supplyAsync(() -> 20)
        .thenApply(n -> n * 10);        // 200

CompletableFuture<Integer> cf2 = CompletableFuture
        .supplyAsync(() -> 30)
        .thenApply(n -> n * 10);        // 300

CompletableFuture<Integer> combined =
        cf1.thenCombine(cf2, (a, b) -> a + b);   // BiFunction: two inputs

System.out.println(combined.get());     // 500
System.out.println(combined.join());    // 500 — join() doesn't force you to handle checked exceptions

thenRun and the Consumer style — nothing to return:

// thenRun: no input, returns void — just runs after the previous stage completes
CompletableFuture.supplyAsync(() -> 20)
        .thenRun(() -> System.out.println("Completed"))
        .join();

// Consumer-style (thenAccept): receives the result, returns nothing
CompletableFuture.supplyAsync(() -> 20)
        .thenAccept(n -> System.out.println("Got " + n))
        .join();

Error handling — exceptionally and handle:

// exceptionally: only runs if something failed
CompletableFuture<Integer> safe = CompletableFuture
        .supplyAsync(() -> {
            if (true) throw new RuntimeException("boom");
            return 20;
        })
        .exceptionally(ex -> -1);        // fallback value

// handle: runs for BOTH success and failure
CompletableFuture<Integer> either = CompletableFuture
        .supplyAsync(() -> 20)
        .handle((value, ex) -> ex == null ? value : -1);

The functional interfaces, written out by hand:

Supplier<Integer>           supplier = () -> 20;                  // no input → output
Function<Integer, Integer>  function = n -> n * 10;               // A → B
BiFunction<Integer, Integer, Integer> bi = (a, b) -> a + b;       // (A, B) → C
Consumer<Integer>           consumer = n -> System.out.println(n); // input → nothing

📌 Important Points / Common Mistakes

  • Future: result, but blocking and limited. CompletableFuture: chained, asynchronous, many methods.
  • supplyAsync = no input, returns something; thenApply = transform; thenCombine = two results in; thenRun = void.
  • Default executor is the ForkJoin common pool; you don't pick the number of threads, but you can supply your own pool.
  • Plain (sync) variants use the current thread; Async variants use a pool worker.
  • Calling get()/join() at the end blocks — fine when you need the final value, but don't call it between every step.
  • join() avoids the checked-exception handling get() requires; behavior is otherwise the same.
  • Know Supplier, Consumer, Function, BiFunction cold — interviewers ask them with these operations.
  • Don't memorize 50+ methods; practice 5–10 and read the Javadoc for others.
