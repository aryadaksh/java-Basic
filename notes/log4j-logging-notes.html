🧠 Key Concepts

What Are We Using System.out.println For Today?

The instructor opened by asking why we write System.out.println (SOP). The answer: to trace. With no debugging mechanism you print lines so you can follow the flow of the program in the console. SOP does no business work — the logic runs regardless; the printing exists only for the developer, so they can look later.

That tracing is still needed in production, but in a different form. When a customer complains "I placed an order three days back and didn't get it", the developer goes to the log file and checks what happened — without those details you can't tell whether the order was placed or rejected. Example from class: a customer in Delhi places an order, the product name arrives as null, the system logs it, and the next day you read the line and know the problem. Class demo: an OrderManagement flow — receive the order, validate the customer and quantity, check stock — logging each step so that later you can see, say, "your order got rejected because…".

Why Logs Must Be Controlled — Volume and Cost
  • Imagine 10,000 classes, each full of SOP lines on every decision ("this is true, this is false, got this ID"). The output is huge — the instructor's figures were terabytes every day, and he mentioned a company that cleaned up petabytes of logs. His estimates were rough, but the point is storage costs money and copying logs to your local system from the server (say 20 TB) takes a long time.
  • You don't need all of it all the time — maybe once in 30 days you look at a log, and the other 29 days it is unnecessary printing that slows the application down. So: print only when needed, turn it on and off when you want.
  • Analogy: a phone keeps a call history for a limited period (he said about a month on his phone) — you can't check what happened six months back. Recording everything forever costs space and slows things, and you only look at it when something goes wrong.
  • Everything has a limit, and logs are no exception.
What SOP Can't Do — and What a Logging Framework Does

The instructor's verdict: SOP is not the right approach — you won't write it in a company. The alternative is a logging framework — Log4j.

Log Levels
  • From lowest to highest: TRACE → DEBUG → INFO → WARN → ERROR → FATAL. The low levels mean "everything, in detail".
  • Whatever level you configure, you get that level and everything above it. TRACE prints all of it (like SOP did); INFO skips trace (and debug); ERROR prints only error and above.
  • Production normally runs in ERROR mode — only errors are captured, so logs stay small. That is why it is the developer's responsibility to write the right log statements.
  • When a problem comes, you switch to debug (or trace) to get meaningful, detailed information.

The Developer's Mindset — Find One Line in Lakhs
  • Think like an Amazon developer: one customer says their order failed, while lakhs of customers placed orders at the same time. How much log does the system generate, and how do you find the one line for that customer? That is why logging matters — don't think "hello world".
  • The instructor's recurring message: logic isn't the critical part — understand the process. Logic comes once you join a company; "before logic, you should know the right process".
  • Logging is compulsory, even for one line of code. It is standard practice, and nobody will give it to you as a requirement — "develop the application, write logs". Every system writes logs; they are heavy and necessary.
Setting Up Log4j — Three Steps
  1. Dependencies in pom.xml: the Log4j API and Log4j Core.
  2. A configuration file in the project's resources — the instructor called it a log4j properties file. It holds the settings for logging:
    • the pattern of each log line (time, package name, class name, message…),
    • the destination: the console and/or a file location,
    • the level you want (trace and above, error and above…).
  3. In the code: create a logger with LogManager.getLogger(…) and call methods such as logger.info(…), logger.error(…) where you used to print.

The big advantage: the configuration file sits outside your code, so changing the level means no code change. This is the only code you write; "there's not much coding here". To convert an existing class, the SOP lines are replaced by logger calls — the recording suggests a tool did the replacement for him, with no change to the business logic.

The Demo — Changing the Level Without Touching the Code
  • He logged at several levels: normal flow as info, problems as errors. Then only the configuration changed:
  • Error → only the error line (and fatal) appeared. Info → trace was gone, info and above remained. Trace → every line appeared, with all the details.
  • The same code, different output — "now you'll see the magic". That is the difference between SOP and logging: you control the level.
  • Where it goes: with a file appender the lines are written to the log file; if you also keep the console appender they show on the console too. In production you run on a Linux box with no Eclipse, so the console is turned off and only the file is written — you go and read the file on the server.
Rolling Files — Don't Let One File Grow Forever
  • Logs are usually retained for a couple of months (depending on the project). A single file would keep growing until nobody could open it — "let's say 200 GB: can you open that file? No."
  • So use a rolling file appender: change the file by time or size. Typically every hour or every day — at midnight the current file is renamed with the date (for example the 28th of October) and a new file starts a second later.
  • Size-based rolling also works: "don't wait for an hour — at 100 MB, write a new one".
  • For the demo he rolled every minute, because he couldn't wait an hour: when the minute changed, the old file moved aside and a fresh one started. You set the rolling pattern in the configuration.
  • Whether it is hours or days depends on the nature of the application and how much it logs.

💡 Added clarification:
  • Log4j 2: the LogManager.getLogger style belongs to Log4j 2 (packages org.apache.logging.log4j). Early 2.x versions had a serious security hole (Log4Shell, CVE-2021-44228), so copy a current version from the Maven repository site rather than an old one from an example.
  • Level names: the recording garbles some of them; I used the standard Log4j order. FATAL sits above ERROR; OFF and ALL also exist.
  • Applying a level change: Log4j 2 can re-read its configuration periodically (the monitorInterval setting), so a level change can take effect without a restart. After investigating, set the level back to ERROR so the logs stay small.
  • Write messages with placeholders — logger.info("Order {} placed", orderId) — and pass an exception as the last argument (logger.error("…", e)) so the stack trace is logged.
  • Singleton: the instructor described the logger as the singleton pattern. More precisely, LogManager hands out one cached logger per name, so the usual practice is one static final logger per class.
  • Never log secrets — passwords, card numbers, tokens.

    </dependency>
</dependencies>

2. The configuration file — src/main/resources/log4j2.properties (outside your Java code):

status = error
name = AppConfig

# --- console output (turn this off in production) ---
appender.console.type = Console
appender.console.name = ConsoleAppender
appender.console.layout.type = PatternLayout
appender.console.layout.pattern = %d{yyyy-MM-dd HH:mm:ss} %-5level %c{1} - %msg%n

# --- file output that rolls over ---
appender.rolling.type = RollingFile
appender.rolling.name = FileAppender
appender.rolling.fileName = logs/application.log
appender.rolling.filePattern = logs/application-%d{yyyy-MM-dd}.log
#   for the every-minute experiment use: logs/application-%d{yyyy-MM-dd-HH-mm}.log
appender.rolling.layout.type = PatternLayout
appender.rolling.layout.pattern = %d{yyyy-MM-dd HH:mm:ss} %-5level %c - %msg%n
appender.rolling.policies.type = Policies
appender.rolling.policies.time.type = TimeBasedTriggeringPolicy
appender.rolling.policies.time.interval = 1
appender.rolling.policies.size.type = SizeBasedTriggeringPolicy
appender.rolling.policies.size.size = 100MB

# --- THE level: change error -> info -> trace here, no code change ---
rootLogger.level = error
rootLogger.appenderRef.console.ref = ConsoleAppender
rootLogger.appenderRef.file.ref = FileAppender

3. Using the logger instead of System.out.println (the order flow from class):

import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public class OrderManagement {

    private static final Logger logger = LogManager.getLogger(OrderManagement.class);

    public void placeOrder(String customerId, String productName, int quantity) {
        logger.trace("placeOrder() entered");
        logger.info("Order received for customer {}", customerId);

        if (productName == null) {
            logger.error("Order failed for customer {}: product name came as null", customerId);
            return;
        }
        if (quantity <= 0) {
            logger.warn("Customer {} sent an invalid quantity {}", customerId, quantity);
            return;
        }

        logger.debug("Validated order: product={}, quantity={}", productName, quantity);
        // ... business logic -- unchanged ...
        logger.info("Order placed for customer {}", customerId);
    }
}
// rootLogger.level = error  -> only the "Order failed ..." line is printed
// rootLogger.level = info   -> the info, warn and error lines
// rootLogger.level = trace  -> everything, including placeOrder() entered
