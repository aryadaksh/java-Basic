🧠 Key Concepts

Recap of the Previous Class
  • We did development, then unit testing using JUnit — the Java unit testing framework.
  • The purpose of unit testing: to maintain code quality.
  • The person who wrote the code writes the JUnit tests. Because you wrote the code, you must know the scenarios — without knowing the scenarios, you wouldn't be able to write the code in the first place.
The Problem — How Do They Know You Really Tested?

For a whole project, a developer could write test methods that are empty — just add the @Test annotation, leave the body blank, and tell the boss: "All my test cases are working fine — all green." That's possible, but it's not right. You have to actually test your code.

This is where code coverage comes in.

What Is Code Coverage?
  • Code coverage tells you how much of your code has been tested by your unit tests.
  • Example: a class has 1000 lines of code; the tests exercise 900 of them → 90% coverage.
  • 100% can't be achieved — some corner scenarios cannot be tested.
  • A code-coverage tool (the instructor said "Emma, or something") runs along with your JUnit tests and catches which source code lines were actually called by them, then gives you a report.
  • The report is per class, e.g. "in this class you tested 80%; in that class 90%; in this other class only 50%."
Per-Class Coverage — The Instructor's Example
ClassTested by unit testsMeaning
Class A80%Most code exercised; some lines never called by a test
Class B90%Very good coverage
Class C50%Half of the code is untested

Coverage = lines tested ÷ total lines × 100. If a class has 100 lines and tests reach 70 of them, coverage is 70% and 30% of the code is untested.

Why Is Code Coverage Required?
  • It is part of the process. The system gets to know how much unit testing you have really written.
  • Otherwise you could write an empty method and claim "my JUnit is 100% done". No — you must write a unit test for each and every scenario.
  • The instructor's point: without meeting the coverage requirement you won't be able to check in your code — the process stops you.
Why 100% Coverage Is Not Achievable
  • One class might be 100%, another 70%. Across 10,000–20,000 classes the average will never be 100%.
  • Example: your program talks to a database and throws an exception — but that exception comes only if the database is down or crashes. You cannot produce that situation in your unit tests, so those lines stay uncovered.
  • Considering such cases, industry says ~85% is good (some say 80%, some say 90%).
🔥 Interview Line — Code Coverage Requirement

The CI/CD Pipeline — What Happens After You Push Code

If a project requires 85% minimum coverage and you don't maintain it, the system will catch you. The flow:

  1. You write the code and push it (to Git / GitHub).
  2. Jenkins (a CI/CD tool) automatically triggers the build: it compiles the code, builds the packages and creates the JAR, using Maven.
  3. It executes the JUnit test cases.
  4. It checks the code coverage.
  5. If coverage is above 85% → it builds the JAR and deploys it ("deploy" = copy the JAR to a target system).

Why automatic? You don't have one or two classes — you might have 20,000. Somebody must compile and package them automatically. Even for a small change you go through this pipeline, and it is already configured.

The instructor's message: don't just say "I know Java" — everybody does. Explaining this structure shows how you're different and what value you add. You'll do CI/CD hands-on when the time comes.

Second Scenario — Coverage Is Only 80%
  • Your code is right, but coverage is 80%, below the 85% minimum.
  • The pipeline fails the build: it says your code is right, but you aren't following the process — 85% is the minimum requirement, not matched.
  • It sends an email to your entire engineering team.
  • You cannot bypass or play with the system. You must sit down, write more JUnit tests, and improve the coverage.

Where Does the QA Team Fit? — Build, Deploy, Environments
  • "My build is ready" means: I've tested it from my side and the JAR has been created, so it can be moved to another system. (Last time you created a JAR in the project's target folder — that's the build.)
  • Deploy = copy the JAR to a target system: QA, SIT, pre-prod or prod.
  • If you move it to the QA system, the testing team starts testing. If testing is already done, it moves on to SIT, pre-prod, or prod.
  • The testing is done on your build only — whatever JAR you create.
  • All of this happens through the Jenkins pipeline.

Code Review — The Step After Unit Testing

After developing and finishing the unit tests, you go through code review. There are two types: static code review and peer code review.

Static Code Review — Done by a Tool
  • Done by some tool, based on configured rules.
  • It catches small mistakes, for example:
    • A global (instance) variable that you only use locally → should be a local variable.
    • A 500-line method → "can you break this into 3 methods?"
    • A variable that is declared but never used.
    • Creating objects inside a loop.
  • Rules are configurable — your company or project decides, e.g. a method must not exceed 200 lines (a 210-line method gives an error), a class must not exceed 1,000 lines.
Peer Code Review — Done by Humans
  • Done by your team members and team lead (experts and architects may join).
  • You share your screen and present the code; the entire team reviews.
  • They check the business requirement too — what you're trying to do. A static tool can't do that; it only runs the configured rules and gives a checklist.
  • They give feedback; you fix it; then re-review.
  • Take it positively. The instructor makes people present in class so that you feel comfortable when you join a company.
What a Peer Review Can Look Like — The Instructor's Examples
  • Naming: "Why did you choose this class name? It doesn't convey anything." A badly named class (e.g. starting in lower case) can even derail the meeting.
  • Static vs instance: "Why is this calculation method non-static? It doesn't depend on any object — amount and type are just inputs — so it should be static." And the reviewer is right. Note the knock-on effect: making it static changes your test cases, because you no longer create an object to call it.
  • Extensibility: "What if a new customer category comes — will you change code each time? Make it pick the customer type dynamically, and then you won't need this switch." Maybe on closer thought your approach is right — but in front of the manager and the manager's manager, the impression is already formed.
  • Defend your approach: if you believe your design is the right one, explain and defend it right there, in the meeting.

1. The Discount Calculator after the instructor's changes (reconstruction):

public class DiscountCalculator {

    public double calculateDiscount(double amount, String customerType) {
        String type = customerType.toUpperCase();          // NullPointerException if customerType is null

        if (type.equals("REGULAR")) {
            return amount - (amount * 0.10);               // tested
        } else if (type.equals("GOLD")) {
            return amount - (amount * 0.20);               // tested
        } else if (type.equals("PLATINUM")) {
            return amount - 150;                           // NEW branch -- no test yet = uncovered
        }
        return amount;                                     // default: no discount (tested via "Premium")
    }
}

@Test void testPremium()  { assertEquals(1000, calculator.calculateDiscount(1000, "Premium")); }   // covers the default

8. A pipeline sketch as a Jenkinsfile (added — illustration only; the lecture's real pipeline also had Docker steps):

pipeline {
    agent any
    stages {
        stage('Checkout') {
            steps { git branch: 'main', url: 'https://github.com/your-org/your-repo.git' }
        }
        stage('Build, Test & Coverage Gate') {
            steps { sh 'mvn clean verify' }        // compile + JUnit + coverage rule; fails below 85%
        }
        stage('Deploy') {
            steps { echo 'Copy the JAR to the target system (QA / SIT / pre-prod / prod)' }
        }
    }
    post {
        failure { echo 'Build failed -- notify the engineering team (e.g. by email)' }
    }
}
// A failed stage stops the pipeline, so Deploy never runs for a build that missed the coverage rule.

📌 Lecture Takeaways

  • Developers write JUnit tests to maintain code quality; the person who wrote the code writes them.
  • Empty test methods can fake "all green" — code coverage exposes that.
  • Code coverage = how much of the code your unit tests execute; reported per class.
  • A coverage tool runs with the tests and highlights tested vs untested lines; new untested branches and exception paths lower the percentage.
  • 100% is not achievable (e.g. exceptions only when the database is down); industry standard is about 85%.
  • To improve coverage, write tests for corner scenarios.
  • The pipeline: push → Jenkins build → compile → JUnit → coverage check → (≥ 85%) JAR → deploy.
  • Below the minimum, the build fails and the team is emailed — you can't bypass the system.
  • Deploy = copy the JAR to a target system (QA, SIT, pre-prod, prod); the QA team tests your build.
  • Code review has two kinds: static (tool, rules) and peer (humans, business and design).
  • Write your own script about your day-to-day work for interviews.

🚧 Common Interview Traps

  • "All my tests are green, so my code is covered." Empty or weak tests are green too — coverage is what measures how much code ran.
  • "We target 100% coverage." Unrealistic — say you maintain about 85%, and explain why 100% isn't practical.
  • Saying "I know Java" and stopping there. The instructor wants you to explain the process — tests, coverage, pipeline, reviews.
  • Confusing build with deploy. Build creates the JAR; deploy copies it to a target system.
  • Thinking you can bypass the coverage rule. The pipeline enforces it and informs the whole team.
  • Thinking a tool can replace peer review. Static tools check rules, not business requirements.
  • Getting defensive in a review. Take feedback positively — but defend a design you can justify.
  • Treating coverage as proof of quality. Added A test that asserts nothing still counts as "covered".
