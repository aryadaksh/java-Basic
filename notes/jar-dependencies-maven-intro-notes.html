🧠 Key Concepts

The Starting Point: Source Code → .class Files

As developers we write code to requirements, and the source is kept in a repository (GitHub, Bitbucket, CVS, SVN, or another source-control system). After development the source is compiled into .class files. A real application, module, or service can have hundreds or even thousands of compiled class files.

The Need: Services Depend on Each Other

The class discussed an architecture with an Order Service, a Payment Service, and a Delivery Service — developed by different developers or teams, but interconnected. The Order Service places an order, the Payment Service confirms payment, the Delivery Service handles delivery, and the Order Service may need functionality from the other two.

A service cannot simply ask another developer for the entire source code and copy everything into its project. Instead, the service compiles its code and bundles the compiled classes into a JAR.

What Is a JAR?

JAR = Java Archive — a bundle containing compiled Java classes plus related metadata/resources. If a module has 1,000 class files, managing 1,000 separate files is inconvenient; bundle them into one JAR and hand over that single file.

The ZIP Analogy

If you need to send 20–25 documents, you don't send each separately — you put them in one ZIP file. Likewise: compile the source → bundle the classes into a JAR → distribute the JAR. The consumer uses the single JAR and accesses the classes inside it. A JAR can hold a few classes, hundreds, or thousands.

Versioning JAR Files

Version numbers track changes to the packaged code: clothing-1.0.jar; after a code change, clothing-1.1.jar. The same idea applies to services: payment-1.2.jar, payment-1.3.jar. When a service's implementation changes, a new JAR version is generated and the consuming project updates its dependency.

Looking Inside a JAR From the Command Line
CommandWhat it does

Handy for checking whether a particular class is really present in a JAR.

The Class-Not-Found Problem

A common failure, including NoClassDefFoundError. Example: a project tries to use an Employee Management class, but that class isn't in the JAR being used — the application fails with a class-not-found-related error. The key lesson: a dependency JAR must actually contain the classes the consuming application needs.

Troubleshooting approach from class:

  1. Check which JAR is being used.
  2. Inspect the JAR's contents.
  3. Use jar -tvf to see whether the required class is present.
  4. Check whether it's the latest version of the JAR.
  5. Check with the developer/team that supplied the JAR.
  6. Verify whether the class was removed, renamed, or changed between versions.

Order Management needs Payment Service functionality. Instead of copying Payment Service's source into Order Management, Payment Service is packaged as a JAR and the JAR is added as a dependency. Order Management can then create Payment Service objects and call its methods. Because Payment Service is a separate project, its classes are not automatically visible inside Order Management.

  1. Customer places an order.
  2. Order Management processes it.
  3. Order Management needs to confirm payment.
  4. Payment Service provides the payment functionality.
  5. Order Management calls Payment Service.

The Payment Service class in the demo was deliberately simple — the goal was to show JAR creation and dependency management, not real payment logic.

Real-World Dependencies

Developers don't implement every feature from scratch: sending email, JSON parsing, converting objects to JSON and back, other reusable functionality. Someone has probably already built it and packaged it as a library/JAR — so you use it as a dependency instead of rewriting it. A project may depend on a payment service, mail APIs, JSON libraries, database libraries, logging libraries, other internal services, and other third-party libraries — in companies, hundreds of JARs.

The Problem With Manually Managed JARs
  • Manually managing hundreds of JAR files becomes difficult.
  • Suppose payment.jar sits at a specific location on your laptop — the project works on your machine because the JAR is at that local path.
  • You push the source to GitHub. The local external-JAR path does not travel with the source code.
  • Another developer clones the project: the code is there, but the JAR may not exist at the same path — the dependency breaks.

This is one of the problems Maven is meant to solve.

When a Service Changes — a New JAR Is Required

Question from class: if Payment Service changes, do we need a new JAR? Yes — if the consumer uses the packaged JAR, the changed code must be packaged again into a new version.

Example: if a new method checkStatus() exists only in payment-1.3.jar, Order Management won't see it while it still uses payment-1.2.jar. The consumer must use the correct version of the provider's packaged artifact.

Deployment — The Simplified Idea

Source code → compile → create/package a JAR → copy/deploy the JAR to the server. The instructor gave this as a simplified view; real production deployment is much more involved.

Maven — Introduced, Not Yet Taught

Maven was introduced as the answer to dependency management: instead of arbitrary local JAR paths, it provides a standard way to declare and manage dependencies so the required libraries can be resolved. The detailed mechanics were reserved for the next session.

⚠️ Standard Details Added (Not Taught in This Class)
  • Creating a JAR by command: besides Eclipse's Export, the JDK's jar tool can create one, e.g. jar cvf payment-1.2.jar -C bin . (c = create). The class only showed Export and the -tvf / -xvf commands.
  • Runnable JAR specifics: a runnable JAR's manifest names the entry point (Main-Class), and it's launched with java -jar app.jar. The class only said a runnable JAR needs an entry point like main().
  • JARs are ZIP-format files — that's why the ZIP comparison fits, and why zip tools can open them. (The class used ZIP purely as a bundling analogy.)
  • NoClassDefFoundError vs ClassNotFoundException: NoClassDefFoundError usually means a class was available when the code was compiled but is missing at runtime; ClassNotFoundException occurs when a class is loaded by name and can't be found. The class treated them together as "class-not-found related" errors.
  • Build path ≈ classpath: Eclipse's Build Path is how the IDE builds the classpath for your project; the class used the two terms side by side.
  • Maven preview: Maven dependencies are normally declared in a pom.xml and downloaded from a repository — that's the next session's content, not yet taught.

💻 Examples & Commands

Note: the instructor's demo code wasn't visible in the transcript and he said the example was intentionally simple. The Java below is illustrative — it shows the idea (two projects, one JAR between them), not his exact code.

Inspecting and extracting a JAR:

# list what's inside (verify a class is really packaged)
jar -tvf payment-1.2.jar

# extract the contents so you can look at the classes/resources
jar -xvf payment-1.2.jar

Project 2 — Payment Service (becomes payment-1.2.jar):

package com.kodewala.payment;

public class PaymentService {

    public boolean makePayment(int orderId, double amount) {
        System.out.println("Payment of " + amount + " received for order " + orderId);
        return true;
    }
}

Project 1 — Order Management uses it (after the JAR is on the build path):

package com.kodewala.order;

import com.kodewala.payment.PaymentService;   // visible only because payment-1.2.jar is a dependency

public class OrderManagement {
    public static void main(String[] args) {
        PaymentService payment = new PaymentService();
        boolean paid = payment.makePayment(101, 4999.0);
        System.out.println(paid ? "Order confirmed" : "Payment failed");
    }
}

After the service changes — payment-1.3.jar adds a method:

// Added in payment-1.3.jar ONLY:
public String checkStatus(int orderId) {
    return "SUCCESS";
}

// Order Management can call payment.checkStatus(101) only after it
// replaces payment-1.2.jar with payment-1.3.jar on its build path.

📌 Important Points / Common Mistakes

  • Compiled classes → bundled into a JAR → used by other projects as a dependency.
  • A JAR in the lib folder does nothing until it's on the build path/classpath.
  • Add JAR = inside the project; Add External JAR = outside it.
  • Use jar -tvf first whenever a class can't be found.
  • The consumer only sees what's in the JAR version it uses — update it when the provider changes.
  • Local JAR paths don't travel via GitHub — a classic reason projects "work on my machine" only.
  • Real projects have hundreds of dependencies — hence the need for Maven.
  • Don't stop at mvn -version — build a Hello World Maven project.
