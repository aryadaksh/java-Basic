🧠 Key Concepts

What Is the Spring Framework?
  • Spring is an open-source, lightweight, web-development framework. With it you can build web / enterprise applications. The class starts with it to see "why Spring is so powerful and why everybody is talking about Spring and Spring Boot".
  • Open source: you can download and modify the source code.
  • Lightweight: before Spring there was EJB, which was heavyweight — even for a small piece of functionality you had to load many things (all the modules). Spring is plug and play: need only security → take the security module; need MVC → take the MVC module. You use only the modules you need, and the application runs in an application server such as Tomcat.
  • Spring has many modules — Spring Core (IoC and dependency injection), Web / MVC, Data JPA, Security, AOP (aspect-oriented programming), and AI integration. The class starts with Core and moves forward.
The Instructor's Study Rules
  • Do the homework every day — not "Monday to Friday I'll learn, the weekend I'll practise". Setup gets people stuck sometimes, and setup comes with experience; there is no fixed formula (Tomcat not starting → refresh; port problems; and so on).
  • If you can't set up Tomcat properly, there's no point learning the framework — make sure the setup works on your machine.
Bean — Just a New Word for a Managed Object

In Java we say "object". Inside Spring, an object that is managed by the Spring Framework is called a bean. A bean is nothing special — it's an object.

You never say "I'm unable to create an Employee object inside Spring". You say "create the bean for Employee". The terminology moves from object to bean.

🔥 Interview angle: "What is a bean?" — an object managed by the Spring container.

  • The responsibility for the object's life cycle has been transferred from the application to a container. That design is Inversion of Control.
  • You say "I want this bean", the container hands you the object, you call its methods — "you don't have to use the new keyword", and "forget the rest — the IoC container will manage it".

How the Container Works — What You Must Supply

The IoC container is just a process in memory (the JVM). Developers must give it information so anyone can get beans from it:

  1. For which class to create a bean — a POJO (plain old Java object): the class with fields and getters/setters, e.g. Employee.
  2. How to create and initialise it — in today's approach, an XML configuration.
  • The container then creates the object, gives it a unique ID and initialises its fields with the values from the configuration. The bean is now available inside the container.
  • To get one, you request it by name or ID — there may be thousands of beans, so every bean has a unique ID. You use it and it goes back to the container for the next person.
  • There are two ways to define beans: XML (today) and Java configuration — which, with annotations (as I read the recording), comes from the next class.

The Demo — Creating Beans with XML
  • Project: a standalone Maven project (the web part isn't needed yet) containing an Employee class with name and ID fields and getters/setters.
  • Dependency: the spring-context Maven dependency. The instructor said to use version 6.1 (as heard) and repeated his rule: never use the latest version — use N−1, where N is the newest; and in advanced Java, use the same version throughout instead of playing with versions.
  • Java version: his run failed because the project was on an older Java — Spring needs a minimum of Java 17. "Start from 17."
  • The XML file: any file name works. It starts with the <beans> schema header (the one from yesterday). Inside, a <bean> has an id (the name you'll request it by — emp1) and a class (the fully qualified class name), with a <property> for each field to initialise (name, ID).
  • Starting the container: create an ApplicationContext by passing the XML path — ClassPathXmlApplicationContext — which starts the container and builds the beans.
  • Getting the bean: getBean("emp1"). It returns a generic Object, so downcast to Employee.
  • Result: the object exists although nobody wrote new — "that is the bean"; the IoC container manages it and its memory.
What Happens With a Wrong ID, and Adding More Beans
  • Change the ID in getBean to one that isn't defined and you get a "no such bean definition" exception (NoSuchBeanDefinitionException) — the container has no bean with that name.
  • You can define hundreds of beans. He added a second one, emp2, with a different name (Aditya); request emp1 or emp2 to get the respective object.

💡 Added clarification:
  • Singleton by default: unless you say otherwise, the container creates one shared instance per bean ID — which is what "returned to the container so the next person can use it" really means. Asking twice for emp1 gives the same object (compare with ==). A prototype scope gives a fresh object each time.
  • Lazy vs eager: an ApplicationContext creates its singleton beans when it starts, so mistakes in the XML show up straight away; a BeanFactory creates them only when asked — the "lazy" the instructor mentioned. ApplicationContext builds on BeanFactory.
  • Avoid the cast: getBean("emp1", Employee.class) returns the right type directly (snippet 3).
  • Java 17: Spring Framework 6 and later require Java 17 or newer, which matches what he hit.

💻 Code Snippets / Examples

These snippets are my reconstruction — the package name (com.example.spring), file name (beans.xml) and the names/IDs are my choices. The structure (a bean with an id and class, property values, ApplicationContext, getBean with a downcast) is from the class. Nothing was run.

1. The Employee class (a POJO) and the Maven dependency:

package com.example.spring;

public class Employee {
    private String name;
    private String id;

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public String getId() { return id; }
    public void setId(String id) { this.id = id; }

    @Override
    public String toString() { return "Employee[id=" + id + ", name=" + name + "]"; }
}
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context</artifactId>
    <version>6.1.14</version>   <!-- a 6.1.x version, as in class (N-1 rule); copy the exact one from the Maven repository site -->
</dependency>

2. The XML configuration — tells the container which beans to create (src/main/resources/beans.xml):

<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
                           https://www.springframework.org/schema/beans/spring-beans.xsd">

    <!-- id = the name you request it by; class = which class to create a bean of -->
    <bean id="emp1" class="com.example.spring.Employee">
        <property name="name" value="Ravi"/>
        <property name="id"   value="101"/>
    </bean>

    <bean id="emp2" class="com.example.spring.Employee">
        <property name="name" value="Aditya"/>
        <property name="id"   value="102"/>
    </bean>
</beans>

3. Starting the container and requesting beans:

import org.springframework.context.ApplicationContext;
import org.springframework.context.support.ClassPathXmlApplicationContext;

public class App {
    public static void main(String[] args) {

        // start the IoC container and give it the XML (the container builds the beans now)
        ApplicationContext context = new ClassPathXmlApplicationContext("beans.xml");

        // request a bean by its id; getBean returns Object, so downcast (as in class)
        Employee emp1 = (Employee) context.getBean("emp1");
        System.out.println(emp1);                        // Employee[id=101, name=Ravi]

        Employee emp2 = (Employee) context.getBean("emp2");
        System.out.println(emp2);                        // Employee[id=102, name=Aditya]

        // an id that isn't defined:
        // context.getBean("emp9");   // NoSuchBeanDefinitionException: No bean named 'emp9' available
    }
}

4. Without the cast, and closing the container cleanly (added):

try (ClassPathXmlApplicationContext context = new ClassPathXmlApplicationContext("beans.xml")) {
    Employee emp1 = context.getBean("emp1", Employee.class);   // typed: no downcast
    Employee again = context.getBean("emp1", Employee.class);
    System.out.println(emp1 == again);                          // true: one shared (singleton) bean
}   // closing the context lets the container destroy its beans properly
