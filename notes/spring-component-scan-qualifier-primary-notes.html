🧠 Part B — The Technical Explanation (Beginner → Advanced)

Everything below is added by me, following the order of the topics above.

B1 · Component Scanning and @ComponentScan 🧠 Added

Beginner: marking a class with @Component only says "this class may be a bean". Nothing happens until Spring searches for such classes. Component scanning is that search; @ComponentScan tells Spring where to search.

How it works: Spring walks the classpath under the named package and every sub-package, finds concrete classes annotated with @Component (or a stereotype built on it — @Service, @Repository, @Controller), and registers a bean definition for each. The default bean name is the simple class name with a lowercase first letter (OrderService → orderService).

FormMeaning
@ComponentScan("com.kodewala.shop")Scan this package and its sub-packages
@ComponentScan(basePackages = {"com.a", "com.b"})Scan several packages
@ComponentScan(basePackageClasses = App.class)Scan the package of that class — safe against typos and package renames
@ComponentScan (no arguments)Scan the package of the class carrying the annotation — the usual trap when the config class sits in a sub-package such as config

Advanced: filters (includeFilters, excludeFilters) refine what is picked up; interfaces and abstract classes are never registered because they can't be instantiated. In Spring Boot, @SpringBootApplication already contains a @ComponentScan starting at the main class's package — which is why the main application class belongs in the root package.

B2 · Base Package, the Main Class and Package Structure 🧠 Added

Put the main class (and, in this setup, the scan configuration's reach) at the root of your own code, and keep features in sub-packages beneath it. The base package is then one meaningful, lowercase name that covers everything.

B3 · What the IoC Container Does — Execution Flow 🧠 Added
  1. new AnnotationConfigApplicationContext(AppConfig.class) registers AppConfig and processes its annotations.
  2. @ComponentScan is read: the container scans the classpath under the base package and all sub-packages.
  3. Every concrete class carrying @Component (or a stereotype) becomes a bean definition — a recipe saying which class to instantiate and under which name.
  4. The container then instantiates the singleton beans. For each one it resolves the dependencies — a constructor parameter of type PaymentService is searched for among bean definitions by type.
  5. Exactly one match → injected. None → NoSuchBeanDefinitionException. More than one and no tie-breaker → NoUniqueBeanDefinitionException.
  6. When startup completes, getBean(...) returns the ready beans.

B5 · Debugging Steps and Reading the Exception 🧠 Added

The instructor's advice — read the error, then check every class and package — as a procedure:

  1. Read the message for the missing type. No qualifying bean of type '…OrderService' available tells you exactly which bean is missing (his "clue").
  2. Check the config class passed to the container — is it this project's, and does it have @Configuration and @ComponentScan?
  3. Check the scan argument against the real package declaration at the top of the missing class (navigate to the class, as he said).
  4. Check the annotation on that class and that it is a concrete class.
  5. Print what the container actually holds — getBeanDefinitionNames() (snippet 9). If your class isn't listed, the scan never reached it.
MessageMeaning

B6 · Multiple Beans of the Same Type — NoUniqueBeanDefinitionException 🧠 Added

The scenario: an interface PaymentService has two implementations, UpiPaymentService and CardPaymentService, both @Component. A class asks Spring for a PaymentService. Both beans are PaymentServices, so Spring has no way to choose.

  • Why it happens: injection is by type first. Two candidates and no tie-breaker → NoUniqueBeanDefinitionException.
  • When it appears: singleton beans are created at startup, so the failure appears when the context starts — usually wrapped in UnsatisfiedDependencyException, with NoUniqueBeanDefinitionException as the cause.
  • Ways to resolve it:
OptionUse when
@Primary on one beanOne implementation is the default almost everywhere
@Qualifier("name") at the injection pointA specific consumer needs a specific bean
Match the parameter/field name to the bean nameA fallback that works but is fragile — avoid relying on it
Inject List<PaymentService> or Map<String, PaymentService>You want all implementations (strategy-style selection by key)
Register only one (@Profile, @Conditional, remove the annotation)Only one should exist in a given environment
B7 · @Primary 🧠 Added
  • Purpose: marks a bean as the preferred candidate when several beans of the same type qualify. It is a default, applied wherever no other selection is made.
  • Where: on a @Component class, or on a @Bean method.
  • Rule: at most one primary per type. Two primaries fail with NoUniqueBeanDefinitionException: more than one 'primary' bean found among candidates.
  • Effect: consumers need no change — the injection point stays PaymentService.
B8 · @Qualifier 🧠 Added
  • Purpose: at the injection point, names which bean you want. It narrows the candidates to the one(s) with that qualifier.
  • By bean name: @Qualifier("upiPaymentService") — the default name of a scanned class, or the method name of a @Bean.
  • By custom label: put @Qualifier("upi") on the bean class and the same label at the injection point — the consumer then doesn't depend on a class name.
  • Where: on a constructor parameter, a setter parameter or a field.
B9 · When Both @Qualifier and @Primary Are Present 🧠 Added

The lecture's last question. Answer: @Qualifier wins. @Primary is a general default; @Qualifier is an explicit choice at one particular injection point, and the explicit choice overrides the default. A @Primary bean is simply not selected at an injection point that qualifies a different bean.

Advanced nuance: qualifiers filter the candidates first; @Primary only breaks a tie among whatever is left. So if a qualifier matches several beans, a @Primary among them decides.

How Spring picks one bean when more than one matches the type
Candidates by type
→
@Qualifier at the injection point? → keep only matching beans
→
Still several? @Primary → that one
→
Still several? injection-point name = a bean name → that one
→
Otherwise → NoUniqueBeanDefinitionException

(Spring also honours @Priority between primary and the name fallback; it is rarely used and omitted from the flow.)

5. Fix A — @Primary (a default for everyone)

import org.springframework.context.annotation.Primary;

@Component
@Primary                                           // Card is now the default PaymentService
public class CardPaymentService implements PaymentService { /* ... */ }

// OrderService is unchanged -> its constructor receives CardPaymentService

6. Fix B — @Qualifier (a specific choice at the injection point)

import org.springframework.beans.factory.annotation.Qualifier;

// (a) by the default bean name
public OrderService(@Qualifier("upiPaymentService") PaymentService paymentService) { ... }

// (b) by a custom label - the consumer no longer depends on a class name
@Component @Qualifier("upi")  public class UpiPaymentService  implements PaymentService { ... }
@Component @Qualifier("card") public class CardPaymentService implements PaymentService { ... }

public OrderService(@Qualifier("upi") PaymentService paymentService) { ... }
// placeOrder(499)  ->  Paid 499.0 via UPI

7. Both together — and two primaries

@Component @Primary   public class CardPaymentService implements PaymentService { ... }
@Component            public class UpiPaymentService  implements PaymentService { ... }

public OrderService(@Qualifier("upiPaymentService") PaymentService paymentService) { ... }

// Card is @Primary, but the injection point explicitly asks for UPI:
// placeOrder(499)  ->  Paid 499.0 via UPI          (the @Qualifier wins)

// If BOTH classes are @Primary, startup fails:
// NoUniqueBeanDefinitionException: more than one 'primary' bean found among candidates:
//   [cardPaymentService, upiPaymentService]

8. The same ideas with @Bean methods

@Configuration
public class PaymentConfig {

    @Bean @Primary                                  // bean name = method name: cardPayment
    public PaymentService cardPayment() { return new CardPaymentService(); }

    @Bean                                           // bean name: upiPayment
    public PaymentService upiPayment() { return new UpiPaymentService(); }
}
// (remove @Component from the two classes, or you would register them twice)
// Select explicitly with @Qualifier("upiPayment") at the injection point.

💼 Part D — Interview Questions with Detailed Answers and Follow-Ups

🧠 Added All answers are standard Spring behaviour, not lecture statements. Cross-references point to Parts B and C.

Q1What does @ComponentScan do?
It tells the container which packages to search for classes annotated with @Component or its stereotypes. Spring scans the named package and all sub-packages, registers a bean definition for each concrete match, and later instantiates them. With no argument it scans the package of the class carrying the annotation.
Follow-ups: How do you scan several packages? (basePackages array.) Why prefer basePackageClasses? (It survives renames and typos.) How do you leave a class out? (excludeFilters.)
Q2My class has @Component but I get "no such bean". Why?
The annotation only marks the class; the scan must reach it. Check, in order: the config class passed to the context; the scan's base package against the class's real package; whether a bare @ComponentScan sits in a sub-package; that the class is concrete and annotated; and the name or type you request (B4, snippet 3).
Follow-ups: Does annotating an interface work? (No — only concrete classes become beans.) How would you prove the class was or wasn't scanned? (getBeanDefinitionNames().)
Q3What is the base package, and does Spring scan sub-packages?
The base package is the root package named in the scan — normally the package holding the main class. Spring scans it and every sub-package beneath it, so features can live in sub-packages. Classes outside that tree are never scanned. Use a meaningful, lowercase name such as com.company.project.
Follow-ups: Why does Spring Boot put the main class in the root package? (Its @SpringBootApplication scans from there.) What goes wrong if the config class is in config and the scan is bare?
Q4What happens if I pass the wrong configuration class to AnnotationConfigApplicationContext?
The container starts without complaint but builds only what that config defines. Beans from packages it doesn't scan don't exist, so getBean or an injection point fails with NoSuchBeanDefinitionException — the first student's problem.
Follow-ups: Can you pass several config classes? (Yes, as varargs.) Why doesn't Spring warn you? (A config is just a source of definitions; it can't know your intent.)
Q5How do NoSuchBeanDefinitionException and NoUniqueBeanDefinitionException differ?
The first means zero beans match the requested type or name — a scanning or configuration problem. The second means more than one matches and nothing breaks the tie — a selection problem. The second is a subclass of the first. Fix zero-match by correcting scanning; fix multi-match with @Primary, @Qualifier or by injecting a collection.
Follow-ups: Which one tells you the missing bean's type? (Both, in the message.) Which is wrapped by UnsatisfiedDependencyException at startup? (Either, when raised while creating a bean.)
Q6Two classes implement one interface. How does Spring choose which to inject?
It matches by type and finds two candidates. It then applies, in order: @Qualifier at the injection point to filter; @Primary to break a tie; and finally a fallback that matches the injection point's name to a bean name. If still ambiguous it throws NoUniqueBeanDefinitionException.
Follow-ups: Which of these would you rely on in production? (Explicit @Qualifier or @Primary; the name fallback is fragile.) Can you inject all implementations? (Q12.)
Q7What is @Primary?
An annotation on a bean class or @Bean method that marks it as the preferred candidate among beans of the same type. It supplies a default without changing consumers. Only one bean of a type may be primary, otherwise Spring reports "more than one 'primary' bean found among candidates".
Follow-ups: Can a consumer override it? (Yes, with @Qualifier.) Where would you put it for a production vs test implementation? (Combine with profiles.)
Q8What is @Qualifier and how do you use it?
It names the bean wanted at one injection point — on a constructor parameter, setter or field. By default the value is the bean name (upiPaymentService for a scanned class, the method name for a @Bean). You can also label a bean class with @Qualifier("upi") and use the same label at the injection point.
Follow-ups: Why use a custom label instead of the class name? (Consumers stay independent of implementation class names.) Does @Qualifier work with constructor injection? (Yes, on the parameter.)
Q9Both @Qualifier and @Primary are present — which takes priority?
@Qualifier. It is an explicit selection at the injection point and narrows the candidates first; @Primary is only a default used to break ties. A primary bean is bypassed where a different bean is qualified. If the qualifier itself matches several beans, a primary among them breaks that tie.
Follow-ups: What if the qualifier matches no bean? (NoSuchBeanDefinitionException.) Show it in code. (Snippet 7.)
Q10With no @Qualifier and no @Primary, can a field called upiPaymentService still resolve ambiguity?
Yes — as a last fallback Spring compares the injection point's field or parameter name with candidate bean names, so a parameter named upiPaymentService picks that bean. It works but is fragile: renaming a variable changes behaviour, and constructor-parameter names must be available at runtime. Prefer an explicit annotation.
Follow-ups: Why is this a bad habit? (Silent coupling between a variable name and a bean name.)
Q11How do you disambiguate two @Bean methods returning the same type?
The bean name is the method name, so you can select with @Qualifier("methodName"), or put @Primary on one method. You can also name beans explicitly with @Bean("name"). Don't also annotate the classes with @Component or you register duplicates.
Follow-ups: What is the default name of a @Bean? (The method name.) (Snippet 8.)
Q12How would you use all implementations of an interface?
Inject a collection: List<PaymentService> gives every bean of that type; Map<String, PaymentService> gives them keyed by bean name, handy for strategy-style selection ("upiPaymentService" → bean). No tie-breaker is needed because you are asking for all.
Follow-ups: How is the order of a list controlled? (@Order or Ordered.)
Q13How do @Service, @Repository and @Controller relate to @Component?
They are specialisations of @Component — the scan treats them the same way — but they express the layer's role, and some add behaviour (for example @Repository enables persistence exception translation). The lecture's earlier remark about "component-style" annotations for service, repository and controller layers refers to these.
Follow-ups: Does the scan need to know the difference? (No.) Why not tag everything @Component? (Clarity and extra layer-specific behaviour.)
Q14In a large project you see "no such bean". What is your debugging approach?
Read the exception for the missing type; confirm the right config class is passed to the container; compare the scan's base package with the missing class's real package declaration; verify the annotation and that the class is concrete; and list getBeanDefinitionNames() to see whether the scan reached it. This mirrors the instructor's "read the error, then check every class and package" (B5).
Follow-ups: Where would a package rename bite you? (A hard-coded string scan — use basePackageClasses.)
Q15Why does NoUniqueBeanDefinitionException appear when the context starts, not at getBean?
Singleton beans are created eagerly during startup. While building OrderService the container resolves its constructor parameter, finds two candidates and fails then — wrapped in UnsatisfiedDependencyException. This fail-fast behaviour is intentional: configuration mistakes show up at boot, not at the first request.
Follow-ups: Would a lazy bean fail later? (Yes — at its first use.)
