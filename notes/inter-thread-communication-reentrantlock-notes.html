🧠 Key Concepts

Recap: wait() Has Multiple Versions

wait() is defined in the Object class and comes in several overloaded versions (visible by opening the Object class in Eclipse). They fall into two categories: wait without time and wait with time.

wait() With Time — Comes Back on Its Own

A thread that calls wait(time) goes into a waiting state for that specific duration. Once the time is over, it automatically comes back to RUNNABLE. Analogy: "Go get coffee — wait one minute; if it's ready, bring it."

wait() Without Time — Comes Back Only If Somebody Notifies

A thread that calls plain wait() also goes to the waiting state — but there is no timer. It moves from waiting back to RUNNABLE only if somebody calls notify. Analogy: "Wait there — I'll call you later." You might wait an hour; the call from the other person is the notification.

notify() and notifyAll()

These are the methods that send the notification. If a thread is in the waiting state on a particular object, notify() tells it: "Hey, wake up — you need to do your work." The woken thread moves back to RUNNABLE, then gets CPU time again like any other RUNNABLE thread. (notifyAll() is the variant that notifies all the threads waiting on that object.)

Inter-Thread Communication (ITC)

A thread goes to the waiting state (wait), and there is a mechanism to call it back to RUNNABLE (notify), after which it gets CPU time and continues. Whenever the situation demands, it can be told to wait again and be notified when required. This wait + notify mechanism is what we call inter-thread communication — two threads talking to each other.

Interviewers commonly ask: "Can you write code to establish inter-thread communication?", "What is ITC / IPC?", or "How do you use wait and notify?" The Producer–Consumer Example (The Classic)

One thread produces data; another thread consumes it. Once the producer produces, it sends a message to the consumer (who is waiting for data) — the consumer consumes, then sends a message back to the producer: "please produce more." Both threads work on the same shared object.

The Protocol, Step by Step
  1. A shared Task object holds a boolean flag, dataAvailable, which is false by default.
  2. produce(): if data is already available (not yet consumed) → wait. Otherwise → produce the data, set dataAvailable = true, and notify the consumer.
  3. consume(): if data is not available → wait. Otherwise → consume the data, set dataAvailable = false, and notify the producer.
  4. Both methods are synchronized, and both threads use the same Task object.
Reading the Output

With thread names printed, the picture becomes clear: Producer produced 1 → Consumer consumed 1 → Consumer goes to waiting until the Producer produces again → Producer produced 2 → Consumer consumed 2 → ... Who starts first doesn't matter (the CPU decides that, as always) — if the consumer runs first, it simply finds no data and waits. The mechanism guarantees the alternation even though the start order is unpredictable.

Why the Shared Object and synchronized Matter Here

All the waiting and notifying happens on the shared object. Since wait() and notify() need the object's lock (covered last class), the produce/consume methods are synchronized — and both threads must be using the same Task object for the communication to work at all.

When the Program Seems Not to Finish

A student's run kept waiting at the end instead of shutting down. Instructor's explanation: there is no technical failure — a thread in the waiting state is simply waiting for a notification that nobody is going to send anymore (its partner has nothing left to do). It can be ended with a stop/interrupt signal. Analogy: if one person has 10 books and you take 5, the remaining 5 don't vanish — the other side just isn't producing/consuming any further.

Recap: synchronized — Advantage and Limitations

What it does: allows one thread at a time to access a particular method on a shared object. Advantage: lock acquisition and lock release are both handled by the JVM — the developer just writes synchronized and it works. Disadvantage: chances of deadlock — if a thread gets stuck, it stays stuck; and if T1 gets stuck holding the lock, T2 waits outside forever, because there is no timeout mechanism with synchronized.

ReentrantLock — The Manual Alternative (Java 5)

Introduced in Java 1.5 (Java 5), ReentrantLock is the manual way of locking and unlocking: the developer writes code to lock() and unlock() wherever needed. The end result is the same — thread safety — but the developer is in control instead of the JVM. As taught in class, it also lets you acquire the lock multiple times on the same object (for example, across two loops), whereas synchronized was described as acquiring the lock only once, JVM-controlled.

tryLock() — Don't Wait Forever

The big fix ReentrantLock brings: tryLock() (attempt to get the lock) and the timed version tryLock(time). Example: "I'll try to get the lock for 5 milliseconds. If I get it within 5 ms, I execute; otherwise I don't hang around — I do my other work and come back later." With plain synchronized there is no such timeout: if the other thread never releases the lock, you wait indefinitely.

The Price of Manual Control

If the developer forgets to unlock, the lock is never released — and other threads get stuck forever. The instructor's summary: the advantage of manual locking is flexibility; the disadvantage is that forgetting to unlock causes a problem.

A Small Lesson From the Live Demo: Use sleep(), Not wait(), to Simulate a Stuck Thread

To create a "thread stuck inside a synchronized method" situation, the instructor first tried wait() — and both threads entered the method. He then corrected himself: wait() releases the lock, so to simulate a thread that gets stuck while still holding the lock, he switched to sleep(). The native Keyword

native means the method is not written in Java — it's implemented in another language (such as C/C++), and Java lets you use it. Example: hashCode() in the Object class is native — open the Object class and you won't find a Java implementation. Java supports this for cases where efficient code already exists in another language and there is no alternative. The instructor was clear that ordinary developers never write native code (Java's own developers may, when introducing features), and he personally doesn't advise going down that path — though you can explore it if you're curious. Native methods are loaded into the native area of memory, alongside heap and stack.

Why Are wait() and notify() in the Object Class?

Because they are called on an object — the shared object whose lock is involved. Inside a synchronized method, a plain wait() is really "wait on the current object." If these methods lived in the Thread class, you'd need a thread object to call them — but the coordination here happens on the shared task object, not on a thread. So by design they sit in the Object class, making them available on every object.

⚠️ Technical Nuances Worth Verifying (Not Stated This Way in Class)
  • Reentrancy: the class contrasted ReentrantLock ("acquire multiple times") with synchronized ("only once"). In standard Java, synchronized is also reentrant — a thread already holding an object's lock can re-enter another synchronized method on that same object. The practical differences taught here are manual control and tryLock timeouts. Please confirm the exact framing with your instructor before using it in an interview.
  • "Deadlock": in class this word was used loosely for "a thread stuck waiting forever." Formally, deadlock means two or more threads waiting on each other in a cycle. Both usages appear in interviews — know the formal definition too.
  • ITC vs IPC: the instructor grouped "inter-thread communication" and "inter-process communication" as one interview answer (wait/notify). Formally, IPC usually refers to communication between separate processes. Give the wait/notify answer as taught, but be aware of the distinction.
  • if vs while, and finally: the wait condition was described verbally as an "if" check; the standard, safer practice is a while loop (the code below uses it). Likewise, unlock() is normally placed in a finally block so it always runs.

wait() with and without time:

synchronized (task) {
    task.wait(5000);  // waits up to 5 seconds, then returns to RUNNABLE on its own
}

synchronized (task) {
    task.wait();      // waits until someone calls notify() on the same object
}

Producer–Consumer — the shared Task object:

class Task {
    private boolean dataAvailable = false; // false by default
    private int data = 0;

    public synchronized void produce() {
        while (dataAvailable) {                 // previous data not consumed yet
            try {
                wait();                         // release the lock, go to waiting state
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
        data++;                                 // produce the data
        System.out.println(Thread.currentThread().getName() + " produced: " + data);
        dataAvailable = true;                   // data is now available
        notify();                               // wake up the waiting consumer
    }

    public synchronized void consume() {
        while (!dataAvailable) {                // nothing to consume yet
            try {
                wait();
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
        System.out.println(Thread.currentThread().getName() + " consumed: " + data);
        dataAvailable = false;                  // data consumed
        notify();                               // wake up the waiting producer
    }
}

The two threads (both use the SAME Task object):

class ProducerThread extends Thread {
    Task task;

    ProducerThread(Task task) {
        super("Producer");
        this.task = task;
    }

    @Override
    public void run() {
        for (int i = 0; i < 10; i++) {
            task.produce();
        }
    }
}

class ConsumerThread extends Thread {
    Task task;

    ConsumerThread(Task task) {
        super("Consumer");
        this.task = task;
    }

    @Override
    public void run() {
        for (int i = 0; i < 10; i++) {
            task.consume();
        }
    }
}
class Driver {
    public static void main(String[] args) {
        Task task = new Task();                 // ONE shared object

        new ProducerThread(task).start();
        new ConsumerThread(task).start();
        // Output alternates:
        // Producer produced: 1
        // Consumer consumed: 1
        // Producer produced: 2
        // Consumer consumed: 2
        // ...
    }
}

Simulating a stuck thread under synchronized — use sleep(), not wait():

class SlowTask {
    public synchronized void doWork() {
        System.out.println(Thread.currentThread().getName() + " entered");
        try {
            Thread.sleep(5000);  // holds the lock the whole time — the other thread must wait
            // (wait() here would RELEASE the lock, and the second thread would walk in)
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        System.out.println(Thread.currentThread().getName() + " leaving");
    }
}

ReentrantLock — manual lock and unlock:

import java.util.concurrent.locks.ReentrantLock;

class Task {
    private final ReentrantLock lock = new ReentrantLock();

    public void doWork() {
        lock.lock();                   // manual acquire
        try {
            System.out.println(Thread.currentThread().getName() + " has the lock");
            // critical work here
        } finally {
            lock.unlock();             // manual release — forget this and other threads hang forever
        }
    }
}

tryLock with a timeout — don't wait forever:

import java.util.concurrent.TimeUnit;

public void doWork() throws InterruptedException {
    if (lock.tryLock(5, TimeUnit.MILLISECONDS)) {   // try for 5 ms
        try {
            // got the lock in time — do the critical work
        } finally {
            lock.unlock();
        }
    } else {
        // did NOT get the lock within 5 ms — do other work and come back later
    }
}

📌 Important Points / Common Mistakes

  • wait(time) returns to RUNNABLE automatically; plain wait() returns only when notified.
  • notify() doesn't make the thread run instantly — it moves it to RUNNABLE, and it still needs CPU time.
  • Producer–consumer needs a shared object, a flag, synchronized methods, and wait/notify used together — it's the standard answer for ITC questions.
  • Who starts first is still up to the CPU — the wait/notify protocol is what enforces the produce-then-consume alternation.
  • To simulate a thread stuck holding a lock, use sleep() — wait() would release the lock.
  • ReentrantLock gives manual control and tryLock timeouts, but forgetting unlock() leaves other threads stuck forever.
  • Native methods (like hashCode()) are implemented outside Java; you'll use them constantly but should never need to write one.
